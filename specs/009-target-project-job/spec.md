# Feature Specification: 타깃·프로젝트·잡 모델

**Feature Branch**: `009-target-project-job`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "workspace, project, run 개념을 도입합니다. Workspace(SDM/CDM/ADMET)는 파이프라인 정의·매핑 사전·권한 앵커이고, 그 아래에 Target(물리 스키마와 1:1, 장기 유지되는 산출물 — SDM은 sdm 1벌 rolling, CDM은 cdm_rolling(monthly, rolling)과 cdm_2024·cdm_2025…(yearly, frozen)), Project(목적/요청 단위, 산출물은 Extract), Run(실행 1회, target_id 필수 / project_id 선택)을 둔다. Target과 Extract를 구분하라 — 두 개념이 섞이면 보존 정책과 권한이 엉킨다. Target은 Workspace 소유(cdm_2025, sdm), 연 단위 보존 정책, 역할 기반 접근이고, Extract는 Project 소유(가명 SDM 반출본, 코호트 추출본), 요청 종료 후 파기 기한, 프로젝트 멤버만 접근이다. 이 틀에서 SDM은 Target 1개 + 요청별 Extract 다수, CDM은 Target 다수 + 요청별 Extract 다수로 정리된다. 앱 코드에 물리 스키마명을 하드코딩하지 말고 Target 레지스트리 테이블(id, workspace, name, physical_schema, mode(rolling|frozen), cadence(monthly|yearly|on_demand), frozen_at, provenance(vocab_version, dbt_commit, source_extracted_at, cdm_version), retention_until, status)로 관리하라. provenance가 특히 중요하다 — 스냅샷의 존재 이유는 재현성인데, 어떤 vocabulary 버전과 어떤 변환 정의로 만들어졌는지 없으면 스냅샷은 그냥 오래된 데이터다." (후속 지시: 이 모델에서 Run이라 부르던 개념의 이름을 Job으로 바꾼다.)

### Session 2026-09-01

- Q: 추출물(Extract)을 소유·보존 모델로만 정의하나요, 연구자에게 전달하는 내부 제공
  절차까지 포함하나요? → A: 소유·보존 모델만. 추출물은 워크스페이스 계층 안에 놓인
  프로젝트 소유 데이터이며 승인·전달·수령 기록을 갖는 제공 절차는 두지 않는다. 기능
  008이 제공 절차를 제거한 결정과 정합을 유지한다.
- Q: 추출물 접근은 프로젝트 멤버십만으로 충분한가요, 워크스페이스 롤도 함께 요구하나요?
  → A: 워크스페이스 멤버십이 선행 조건이다. 워크스페이스에 배정되지 않은 사용자는
  프로젝트를 개설할 수도, 프로젝트에 초대될 수도 없다. 워크스페이스 멤버 배정은 운영자가
  한다. 프로젝트 개설자는 같은 워크스페이스의 다른 멤버를 초대할 수 있다. 개설자가 아닌
  멤버는 프로젝트와 그 추출물을 조회하고 복제할 수 있으나 수정할 수 없다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 타깃 레지스트리 등록과 물리 스키마 분리 (Priority: P1)

운영자가 워크스페이스 안에 장기 유지되는 산출물 단위를 등록한다. 이 단위를 타깃이라
부른다. 타깃에는 사람이 부르는 논리 이름(`cdm_2025`, `sdm`)과 실제 데이터가 놓이는 물리
스키마 이름(`cdm_b`)이 따로 있고, 갱신 방식(rolling/frozen)과 갱신 주기(monthly/yearly/
on_demand)가 함께 기록된다.

논리 이름과 물리 스키마를 분리하는 이유는 물리 스키마를 갈아 끼울 수 있어야 하기
때문이다. 무중단 교체나 재구축을 할 때 `cdm_2025`가 가리키는 물리 스키마를 `cdm_a`에서
`cdm_b`로 바꾸면 되고, 그 이름을 쓰는 쪽은 아무것도 고치지 않는다. 시스템의 어떤 부분도
물리 스키마 이름을 스스로 알고 있어서는 안 되며, 반드시 레지스트리에서 해석해 얻어야
한다.

**Why this priority**: 타깃이 없으면 실행이 어디에 쓰는지, 산출물이 무엇에 귀속되는지
말할 수 없다. 이 스토리만 구현해도 "산출물 목록을 한 곳에서 보고, 물리 스키마를 코드
수정 없이 교체한다"는 가치가 독립적으로 성립한다.

**Independent Test**: 운영자가 CDM 워크스페이스에 `cdm_rolling`(monthly, rolling)과
`cdm_2025`(yearly, frozen)를 등록하고, `cdm_2025`의 물리 스키마를 다른 값으로 교체한
뒤에도 논리 이름으로 하는 조회가 새 물리 스키마를 가리키는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 활성 워크스페이스가 있을 때, **When** 운영자가 논리 이름, 물리 스키마,
   갱신 방식, 갱신 주기를 입력해 타깃을 등록하면, **Then** 타깃이 그 워크스페이스에
   귀속되어 생성되고 목록에 나타난다.
2. **Given** 타깃이 등록되었을 때, **When** 논리 이름으로 대상 스키마를 조회하면,
   **Then** 레지스트리에 기록된 물리 스키마가 반환된다.
3. **Given** 타깃의 물리 스키마를 다른 값으로 교체했을 때, **When** 같은 논리 이름으로
   다시 조회하면, **Then** 교체된 물리 스키마가 반환되고 이전 값은 이력으로 남는다.
4. **Given** 같은 워크스페이스에 이미 있는 논리 이름을 입력했을 때, **When** 등록을
   시도하면, **Then** 등록이 거부된다.
5. **Given** 다른 타깃이 이미 사용 중인 물리 스키마를 입력했을 때, **When** 등록을
   시도하면, **Then** 등록이 거부된다.
6. **Given** 타깃이 등록되었을 때, **When** 소속 워크스페이스 변경을 시도하면,
   **Then** 변경이 거부된다.
7. **Given** SDM 워크스페이스일 때, **When** 두 번째 rolling 타깃 등록을 시도하면,
   **Then** 등록이 거부되고 SDM은 rolling 타깃을 하나만 갖는다는 사유가 안내된다.
8. **Given** 레지스트리에 없는 물리 스키마를 대상으로 실행이나 조회가 요청되었을 때,
   **When** 그 요청을 처리하면, **Then** 요청이 거부된다.

### User Story 2 - 잡의 타깃·프로젝트 귀속 (Priority: P2)

실행을 걸 때 어느 타깃에 쓰는지를 반드시 지정한다. 워크스페이스만 지정하는 것으로는
부족하다. CDM 워크스페이스에는 타깃이 여럿 있고, 같은 파이프라인이 `cdm_rolling`을
갱신할 수도 `cdm_2025`를 만들 수도 있기 때문이다.

프로젝트는 선택이다. 정기 갱신처럼 특정 요청과 무관한 실행은 프로젝트 없이 돌고,
연구 요청을 처리하는 실행은 그 프로젝트에 귀속된다. 프로젝트에 귀속된 실행이 만든
산출물은 프로젝트 소유가 된다.

동결(frozen)된 타깃은 더 이상 쓰기 대상이 아니다. 동결 타깃을 대상으로 하는 갱신 실행은
접수되지 않고, 읽기 대상으로만 지정할 수 있다.

**Why this priority**: 타깃이 있어도 실행이 그것을 가리키지 않으면 산출물의 귀속이
결정되지 않는다. 실행 귀속이 정해져야 이후의 보존·권한·계보가 전부 성립한다.

**Independent Test**: 타깃을 지정하지 않은 실행 요청이 거부되고, 타깃을 지정한 실행이
그 타깃과 워크스페이스에 귀속되어 조회되며, 동결 타깃 대상 갱신 실행이 거부되는 것을
확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 실행 권한이 있는 사용자가 활성 워크스페이스를 볼 때, **When** 타깃을
   지정하지 않고 실행을 요청하면, **Then** 요청이 거부된다.
2. **Given** 실행이 접수되었을 때, **When** 그 잡을 조회하면, **Then** 워크스페이스
   식별자, 타깃 식별자, 프로젝트 식별자(있는 경우)가 함께 확인된다.
3. **Given** 다른 워크스페이스에 속한 타깃을 지정했을 때, **When** 실행을 요청하면,
   **Then** 요청이 거부된다.
4. **Given** 동결 상태인 타깃일 때, **When** 그 타깃을 갱신하는 실행을 요청하면,
   **Then** 요청이 거부된다.
5. **Given** 프로젝트를 지정하지 않은 실행일 때, **When** 실행이 성공하면, **Then**
   산출물은 타깃에 귀속되고 어떤 프로젝트에도 귀속되지 않는다.
6. **Given** 프로젝트를 지정한 실행일 때, **When** 실행이 성공하면, **Then** 산출물
   중 추출물은 그 프로젝트에 귀속된다.
7. **Given** 종료된 프로젝트를 지정했을 때, **When** 실행을 요청하면, **Then** 요청이
   거부된다.
8. **Given** 같은 타깃에 대해 실행이 진행 중일 때, **When** 같은 타깃을 갱신하는 실행이
   추가로 요청되면, **Then** 요청은 그 타깃의 대기열에 쌓이고 앞선 실행 종료 후 시작된다.

### User Story 3 - 생성 조건 기록과 타깃 동결 (Priority: P3)

타깃에는 그것이 어떤 조건에서 만들어졌는지가 함께 기록된다. 용어사전 버전, 변환 정의
버전, 원천 추출 시각, 대상 표준 버전, 그리고 AI가 개입한 경우 모델 버전과 프롬프트
버전이다. 이 기록이 생성 조건 기록이다.

스냅샷을 남기는 이유는 재현성이다. 어떤 용어사전과 어떤 변환 정의로 만들어졌는지 알 수
없는 스냅샷은 재현의 근거가 되지 못하고 그냥 오래된 데이터다. 그래서 생성 조건 기록이
비어 있는 타깃은 동결할 수 없다.

동결은 되돌릴 수 없다. `cdm_2025`처럼 특정 시점의 상태를 고정해 보존하기로 한 타깃은
동결 시각과 함께 확정되고, 이후 값이 바뀌지 않는다.

**Why this priority**: 등록과 실행 귀속이 있으면 타깃은 이미 동작한다. 생성 조건 기록과
동결은 그 산출물을 장기 자산으로 만드는 단계다. 다만 기록 없이 쌓인 스냅샷은 사후에
복원할 수 없으므로 뒤로 미루더라도 실행 귀속과 함께 설계되어야 한다.

**Independent Test**: 실행이 성공한 뒤 타깃의 생성 조건 기록에 용어사전 버전·변환 정의
버전·원천 추출 시각·대상 표준 버전이 채워지는 것을 확인하고, 항목이 비어 있는 타깃의
동결 시도가 거부되며, 동결된 타깃의 값 변경 시도가 거부되는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 타깃을 갱신하는 실행이 성공했을 때, **When** 타깃을 조회하면, **Then**
   용어사전 버전, 변환 정의 버전, 원천 추출 시각, 대상 표준 버전이 확인된다.
2. **Given** AI 컴포넌트가 개입한 실행이었을 때, **When** 타깃의 생성 조건 기록을
   조회하면, **Then** 모델 버전과 프롬프트 버전이 함께 확인된다.
3. **Given** 생성 조건 기록 항목 중 하나라도 비어 있을 때, **When** 동결을 시도하면,
   **Then** 동결이 거부되고 어떤 항목이 비었는지 안내된다.
4. **Given** rolling 타깃이 동결되었을 때, **When** 타깃을 조회하면, **Then** 상태가
   동결로 바뀌고 동결 시각이 기록된다.
5. **Given** 동결된 타깃일 때, **When** 동결 해제를 시도하면, **Then** 거부된다.
6. **Given** 동결된 타깃일 때, **When** 생성 조건 기록 수정을 시도하면, **Then**
   거부된다.
7. **Given** rolling 타깃이 여러 번 갱신되었을 때, **When** 생성 조건 기록을 조회하면,
   **Then** 최신 갱신의 조건이 표시되고 이전 갱신들의 조건도 이력으로 조회된다.
8. **Given** 과거에 동결된 타깃이 있을 때, **When** 그 타깃과 같은 조건으로 재생성을
   시도하면, **Then** 생성 조건 기록만으로 필요한 입력 조건이 모두 확인된다.

### User Story 4 - 프로젝트와 추출물의 소유·접근 (Priority: P4)

연구 요청이나 특정 목적의 작업은 프로젝트 단위로 묶인다. 프로젝트에는 목적, 요청자,
기간, 개설자, 멤버가 있다. 프로젝트가 만들어 내는 산출물은 추출물이며, 코호트
추출본처럼 그 요청을 위해 만들어진 데이터다.

프로젝트는 워크스페이스 멤버만 개설할 수 있다. 워크스페이스 멤버 배정은 운영자가 하고,
프로젝트 개설은 그 위에서 일어난다. 개설자는 같은 워크스페이스에 배정된 다른 사용자를
프로젝트에 초대할 수 있고, 워크스페이스 밖의 사용자는 초대할 수 없다. 프로젝트가
워크스페이스 접근 통제의 우회로가 되어서는 안 되기 때문이다.

프로젝트 안에서도 권한이 갈린다. 개설자는 프로젝트 설정을 바꾸고 멤버를 초대·해제하고
실행을 걸고 추출물을 파기할 수 있다. 개설자가 아닌 멤버는 프로젝트와 그 추출물을
조회하고 복제할 수 있지만 원본을 바꿀 수 없다. 복제하면 복제한 사람이 개설자인 새
프로젝트가 만들어지고, 원본은 그대로 남는다.

추출물은 타깃과 소유·수명·접근이 전부 다르다. 타깃은 워크스페이스가 소유하고 역할로
접근을 통제하며 연 단위 보존 정책을 따르지만, 추출물은 프로젝트가 소유하고 프로젝트
멤버만 접근하며 요청 종료 후 파기 기한을 따른다. 두 개념이 섞이면 보존 정책과 권한이
동시에 엉킨다.

추출물도 병원 내부망 안에만 존재한다. 추출물을 병원 밖으로 내보내는 경로는 만들지
않는다.

**Why this priority**: 프로젝트와 추출물은 요청 처리 흐름의 단위이지만, 타깃과 실행
귀속이 자리 잡기 전에는 소유를 말할 대상이 없다.

**Independent Test**: 워크스페이스 멤버가 프로젝트를 개설해 같은 워크스페이스의 다른
멤버를 초대하고, 그 프로젝트에 귀속된 실행이 만든 추출물을 멤버가 조회하고 비멤버가
조회하지 못하며, 개설자가 아닌 멤버의 수정은 거부되고 복제는 허용되는 것을 확인하면
검증 완료.

**Acceptance Scenarios**:

1. **Given** 워크스페이스에 배정된 사용자가 있을 때, **When** 목적, 요청자, 기간을
   입력해 프로젝트를 생성하면, **Then** 프로젝트가 그 워크스페이스에 귀속되어 생성되고
   생성한 사용자가 개설자로 기록된다.
2. **Given** 워크스페이스에 배정되지 않은 사용자일 때, **When** 그 워크스페이스에
   프로젝트 생성을 시도하면, **Then** 요청이 거부된다.
3. **Given** 개설자가 프로젝트를 볼 때, **When** 같은 워크스페이스에 배정된 사용자를
   초대하면, **Then** 그 사용자가 프로젝트 멤버가 된다.
4. **Given** 개설자가 프로젝트를 볼 때, **When** 그 워크스페이스에 배정되지 않은
   사용자를 초대하면, **Then** 초대가 거부된다.
5. **Given** 프로젝트에 귀속된 실행이 추출물을 만들었을 때, **When** 추출물을 조회하면,
   **Then** 소유 프로젝트, 생성 잡, 파기 예정일이 확인된다.
6. **Given** 프로젝트 멤버가 아닌 사용자일 때, **When** 그 프로젝트의 추출물 조회를
   시도하면, **Then** 접근이 거부된다.
7. **Given** 프로젝트 멤버이지만 소속 워크스페이스의 해당 계층 접근 롤이 없는 사용자일
   때, **When** 추출물 조회를 시도하면, **Then** 접근이 거부된다.
8. **Given** 개설자가 아닌 프로젝트 멤버일 때, **When** 프로젝트 설정 변경, 멤버 초대,
   실행 요청, 추출물 파기를 시도하면, **Then** 요청이 거부된다.
9. **Given** 개설자가 아닌 프로젝트 멤버일 때, **When** 프로젝트와 그 추출물을 복제하면,
   **Then** 복제자를 개설자로 하는 새 프로젝트에 복제본이 귀속되고 원본은 변경되지 않으며
   원본과의 계보가 기록된다.
10. **Given** 프로젝트 멤버였다가 배정이 해제된 사용자일 때, **When** 추출물 조회를
    시도하면, **Then** 접근이 거부된다.
11. **Given** 추출물이 있을 때, **When** 그것을 타깃으로 승격하거나 타깃 목록에서
    조회하려 하면, **Then** 두 목록은 섞이지 않고 추출물은 타깃으로 다뤄지지 않는다.
12. **Given** 추출물이 있을 때, **When** 병원 내부망 밖 목적지로 내보내는 요청을 하면,
    **Then** 그런 경로가 제공되지 않는다.
13. **Given** 프로젝트가 종료되었을 때, **When** 그 프로젝트의 추출물을 조회하면,
    **Then** 파기 기한이 확정되어 표시되고 복제가 허용되지 않는다.
14. **Given** 추출물 생성·조회·복제·파기가 일어났을 때, **When** 감사 이력을 조회하면,
    **Then** 실행자, 대상 추출물, 시각이 확인된다.

### User Story 5 - 보존 정책 분리와 만료 처리 (Priority: P5)

타깃과 추출물은 서로 다른 시계를 따른다. 타깃은 연 단위 보존 정책에 따라 보존 만료일을
갖고, 만료일이 되어도 자동으로 사라지지 않는다. 재생성할 수 없는 자산이 있기 때문이다.
만료된 타깃은 폐기 후보로 표시되고 운영자 승인을 거쳐야 제거된다.

추출물은 요청이 끝나면 파기된다. 프로젝트 종료 시점에 파기 기한이 확정되고, 기한이
지나면 파기가 수행된다. 파기 후에도 무엇이 언제 파기되었는지의 기록은 남는다.

**Why this priority**: 보존과 파기는 되돌릴 수 없는 방향의 동작이라 마지막에 신중히
구현한다. 앞의 네 스토리 없이는 보존 대상 자체가 없다.

**Independent Test**: 보존 만료일이 지난 타깃이 자동 삭제되지 않고 폐기 후보로만
표시되는 것과, 프로젝트 종료 후 파기 기한이 지난 추출물이 파기되고 파기 기록이 남는
것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 타깃이 등록될 때, **When** 보존 정책이 적용되면, **Then** 보존 만료일이
   확정되어 타깃에 기록된다.
2. **Given** 보존 만료일이 지난 타깃이 있을 때, **When** 만료 처리가 수행되면,
   **Then** 타깃이 폐기 후보로 표시되고 데이터는 그대로 남는다.
3. **Given** 폐기 후보 타깃이 있을 때, **When** 운영자가 폐기를 승인하면, **Then**
   물리 스키마가 제거되고 타깃 레지스트리 항목은 폐기 상태로 남는다.
4. **Given** 폐기된 타깃이 있을 때, **When** 그 타깃을 참조하는 과거 실행 이력을
   조회하면, **Then** 이력과 생성 조건 기록은 그대로 조회된다.
5. **Given** 프로젝트가 종료되었을 때, **When** 그 프로젝트의 추출물을 확인하면,
   **Then** 파기 예정일이 확정되어 고정된다.
6. **Given** 추출물의 파기 예정일이 지났을 때, **When** 파기가 수행되면, **Then**
   추출물 데이터가 제거되고 파기 기록이 남는다.
7. **Given** 보존 정책 설정이 변경되었을 때, **When** 이미 확정된 만료일과 파기
   예정일을 확인하면, **Then** 기존 값은 바뀌지 않는다.
8. **Given** 워크스페이스가 소프트 삭제되었을 때, **When** 그 워크스페이스의 타깃과
   추출물을 확인하면, **Then** 워크스페이스 정리 시점에 함께 정리 대상이 된다.

### Edge Cases

- 워크스페이스에 타깃이 하나도 없는 상태에서 실행을 요청하면 어떻게 되는가? 실행이
  거부된다. 타깃 없는 실행은 존재할 수 없다.
- 물리 스키마 교체 도중 그 타깃을 읽는 실행이 진행 중이면 어떻게 되는가? 진행 중 실행은
  시작 시점에 해석된 물리 스키마를 끝까지 사용하고, 교체는 이후 실행부터 적용된다.
- 레지스트리에 등록된 물리 스키마가 실제 데이터 저장소에 없으면 어떻게 되는가? 타깃이
  불일치 상태로 표시되고 그 타깃을 대상으로 하는 실행이 거부된다.
- rolling 타깃을 동결하는 도중 정기 갱신 일정이 도래하면 어떻게 되는가? 동결이 우선하며
  동결 이후의 갱신 실행은 거부된다.
- 동결하려는 시점에 그 타깃을 대상으로 실행이 진행 중이면 어떻게 되는가? 진행 중 실행이
  끝난 뒤에만 동결할 수 있다.
- 실행이 실패했을 때 타깃의 생성 조건 기록은 어떻게 되는가? 실패한 실행의 조건은 타깃에
  반영되지 않고, 타깃은 직전 성공 실행의 조건을 유지한다.
- 같은 논리 이름이 서로 다른 워크스페이스에 있으면 어떻게 되는가? 허용된다. 논리 이름의
  유일성은 워크스페이스 범위 안에서만 요구된다.
- 프로젝트를 지정한 실행이 타깃도 갱신하면 산출물의 소유는 어떻게 나뉘는가? 타깃에 쓰인
  데이터는 워크스페이스 소유이고, 그 실행이 별도로 만든 추출물만 프로젝트 소유다.
- 프로젝트가 종료된 뒤 같은 목적의 후속 요청이 오면 어떻게 되는가? 새 프로젝트를 만든다.
  종료된 프로젝트는 재개되지 않는다.
- 프로젝트 멤버가 워크스페이스에서 롤을 잃으면 추출물 접근은 어떻게 되는가? 워크스페이스
  접근 통제가 먼저 적용되어 차단된다. 프로젝트 멤버십 기록 자체는 남는다.
- 개설자가 워크스페이스 배정에서 빠지면 프로젝트는 어떻게 되는가? 개설자 권한을 행사할
  사람이 없으므로 운영자가 남은 프로젝트 멤버 중 한 명에게 개설자 권한을 이관한다.
  이관 전까지 그 프로젝트는 수정할 수 없다.
- 종료된 프로젝트의 추출물을 멤버가 복제하려 하면 어떻게 되는가? 거부된다. 복제로 파기
  기한을 새로 받는 것을 허용하면 보존 정책이 무력화되기 때문이다.
- 복제본의 파기 기한은 무엇을 따르는가? 복제본이 귀속된 새 프로젝트의 기한을 따른다.
  원본이 파기되어도 복제본은 자기 기한까지 남는다.
- 복제로 원본보다 넓은 데이터에 접근할 수 있는가? 없다. 복제는 복제자가 원본에 대해
  이미 가진 접근 범위 안에서만 이루어진다.
- 폐기 승인 대기 중인 타깃을 다시 쓰려고 하면 어떻게 되는가? 운영자가 폐기 후보 표시를
  해제하면 보존 만료일이 새로 산정되어 재사용할 수 있다.
- 파기 대상 추출물이 다른 프로젝트의 산출물 계보에 참조되어 있으면 어떻게 되는가? 데이터는
  기한대로 파기되고 계보 참조는 파기 표시가 붙은 채로 남는다.
- 폐기·파기 작업이 중간에 실패하면 어떻게 되는가? 대상은 실패 상태로 남고 어디까지
  제거되었는지 기록되며 운영자에게 알림이 간다.

## Requirements *(mandatory)*

### Functional Requirements

**타깃 레지스트리**

- **FR-001**: 시스템은 타깃을 워크스페이스에 귀속된 항목으로 등록할 수 있어야 하며,
  각 타깃은 고유 식별자, 소속 워크스페이스, 논리 이름, 물리 스키마, 갱신 방식, 갱신
  주기, 상태를 가져야 한다.
- **FR-002**: 시스템은 타깃의 논리 이름과 물리 스키마를 분리해 관리해야 하며, 논리
  이름을 유지한 채 물리 스키마를 교체할 수 있어야 한다.
- **FR-003**: 시스템은 데이터 대상 스키마를 결정할 때 타깃 레지스트리 조회를 통해서만
  해석해야 하며, 레지스트리 밖에 고정된 물리 스키마 이름에 의존해서는 안 된다.
- **FR-004**: 시스템은 레지스트리에 등록되지 않은 물리 스키마를 대상으로 하는 실행과
  조회를 거부해야 한다.
- **FR-005**: 시스템은 같은 워크스페이스 안에서 논리 이름의 중복 등록을 거부해야 한다.
- **FR-006**: 시스템은 이미 다른 타깃에 배정된 물리 스키마의 중복 등록을 거부해야 한다.
- **FR-007**: 시스템은 타깃의 소속 워크스페이스 변경을 거부해야 한다.
- **FR-008**: 시스템은 갱신 방식을 rolling과 frozen 중 하나로, 갱신 주기를 monthly,
  yearly, on_demand 중 하나로 한정해야 한다.
- **FR-009**: 시스템은 SDM 유형 워크스페이스에 rolling 타깃이 둘 이상 등록되는 것을
  거부해야 한다.
- **FR-010**: 시스템은 물리 스키마 교체를 포함한 모든 타깃 속성 변경에 대해 변경자,
  변경 시각, 이전 값, 새 값을 기록해야 한다.

**실행 귀속**

- **FR-011**: 시스템은 모든 실행 요청에 대상 타깃 지정을 필수로 요구해야 하며, 지정이
  없는 요청을 거부해야 한다.
- **FR-012**: 시스템은 실행 요청 시 프로젝트 지정을 선택 항목으로 허용해야 한다.
- **FR-013**: 시스템은 잡에 워크스페이스 식별자, 타깃 식별자, 그리고 지정된 경우
  프로젝트 식별자를 기록하고 조회할 수 있게 해야 한다.
- **FR-014**: 시스템은 실행 요청의 워크스페이스와 지정된 타깃의 소속 워크스페이스가
  다르면 요청을 거부해야 한다.
- **FR-015**: 시스템은 동결 상태 타깃을 갱신하는 실행 요청을 거부해야 하며, 동결 타깃을
  읽기 대상으로 지정하는 것은 허용해야 한다.
- **FR-016**: 시스템은 종료된 프로젝트를 지정한 실행 요청을 거부해야 한다.
- **FR-017**: 시스템은 실행이 만든 데이터의 저장 위치를 워크스페이스와 타깃으로 식별할
  수 있게 해야 한다.
- **FR-018**: 시스템은 같은 타깃을 갱신하는 실행이 동시에 둘 이상 진행되지 않도록
  직렬화해야 한다.

**생성 조건 기록과 동결**

- **FR-019**: 시스템은 타깃마다 생성 조건 기록으로 용어사전 버전, 변환 정의 버전,
  원천 추출 시각, 대상 표준 버전을 보관해야 한다.
- **FR-020**: 시스템은 AI 컴포넌트가 개입한 갱신에 대해 모델 버전과 프롬프트 버전을
  생성 조건 기록에 함께 보관해야 한다.
- **FR-021**: 시스템은 타깃을 갱신한 실행이 성공했을 때 그 실행의 조건으로 생성 조건
  기록을 갱신해야 하며, 실패한 실행의 조건을 반영해서는 안 된다.
- **FR-022**: 시스템은 rolling 타깃의 갱신마다 생성 조건 기록의 이력을 보존해야 하며,
  최신 값과 과거 값을 모두 조회할 수 있게 해야 한다.
- **FR-023**: 시스템은 생성 조건 기록 항목 중 하나라도 비어 있는 타깃의 동결을 거부해야
  하며, 비어 있는 항목을 안내해야 한다.
- **FR-024**: 시스템은 동결 시 동결 시각을 기록하고 상태를 동결로 전환해야 한다.
- **FR-025**: 시스템은 동결된 타깃의 동결 해제, 데이터 갱신, 생성 조건 기록 수정을
  거부해야 한다.

**프로젝트와 추출물**

- **FR-026**: 시스템은 프로젝트를 워크스페이스에 귀속된 항목으로 생성할 수 있어야 하며,
  각 프로젝트는 고유 식별자, 소속 워크스페이스, 목적, 요청자, 기간, 상태, 개설자,
  멤버 목록을 가져야 한다.
- **FR-027**: 시스템은 추출물을 프로젝트 소유 산출물로 관리해야 하며, 각 추출물은 소유
  프로젝트, 생성 잡, 생성 시각, 파기 예정일을 가져야 한다.
- **FR-028**: 시스템은 추출물을 타깃 레지스트리와 분리해 관리해야 하며, 추출물이 타깃
  목록에 나타나거나 타깃으로 전환되어서는 안 된다.
- **FR-029**: 시스템은 추출물 접근을 허용할 때 소유 프로젝트의 멤버십과 소속
  워크스페이스의 해당 계층 접근 롤을 모두 요구해야 한다. 둘 중 하나라도 없으면 접근을
  거부해야 한다.
- **FR-030**: 시스템은 프로젝트 멤버 배정이 해제되면 그 사용자의 추출물 접근을 즉시
  차단해야 한다.
- **FR-031**: 시스템은 추출물을 병원 내부망 밖 목적지로 내보내는 기능·경로를 제공해서는
  안 된다.
- **FR-032**: 시스템은 추출물 생성, 조회, 복제, 파기에 대해 실행자, 대상, 시각을 감사
  이력으로 기록해야 한다.
- **FR-033**: 시스템은 추출물을 워크스페이스 계층 안에 놓이는 프로젝트 소유 데이터로만
  정의해야 하며, 제공 승인, 제공 데이터셋 지정, 제공 전용 계층, 제공 롤, 제공 이력을
  포함하는 별도의 제공 절차를 제공해서는 안 된다. 연구자는 프로젝트 멤버십과 워크스페이스
  롤로 원내에서 직접 접근한다.
- **FR-045**: 시스템은 프로젝트 생성을 해당 워크스페이스에 배정된 사용자로 제한해야 하며,
  배정되지 않은 사용자의 생성 요청을 거부해야 한다.
- **FR-046**: 시스템은 프로젝트 생성 시 생성한 사용자를 개설자로 기록해야 하며,
  프로젝트마다 개설자가 정확히 1명 유지되어야 한다.
- **FR-047**: 시스템은 프로젝트 멤버 초대 대상을 같은 워크스페이스에 배정된 사용자로
  제한해야 하며, 배정되지 않은 사용자의 초대를 거부해야 한다.
- **FR-048**: 시스템은 프로젝트 설정 변경, 멤버 초대·해제, 프로젝트를 지정한 실행 요청,
  추출물 파기 요청을 개설자에게만 허용해야 한다.
- **FR-049**: 시스템은 개설자가 아닌 프로젝트 멤버에게 프로젝트와 그 추출물의 조회와
  복제를 허용해야 하며, 원본에 대한 수정은 거부해야 한다.
- **FR-050**: 시스템은 복제본을 복제자를 개설자로 하는 새 프로젝트의 추출물로 생성해야
  하며, 원본 프로젝트·추출물과의 계보를 기록하고 새 프로젝트 기준으로 파기 예정일을
  산정해야 한다. 복제는 복제자가 원본에 대해 가진 접근 범위를 넓혀서는 안 된다.
- **FR-051**: 시스템은 종료된 프로젝트의 추출물 복제를 거부해야 한다.
- **FR-052**: 시스템은 사용자의 워크스페이스 배정이 해제되면 그 사용자의 프로젝트 멤버십
  기록을 유지한 채 접근을 차단해야 한다. 개설자의 배정이 해제된 경우 운영자는 남은 멤버
  중 한 명에게 개설자 권한을 이관할 수 있어야 하며, 이관 전까지 그 프로젝트는 수정할 수
  없어야 한다.

**보존과 만료**

- **FR-034**: 시스템은 타깃 등록 시 보존 정책에 따라 보존 만료일을 확정해 기록해야 한다.
- **FR-035**: 시스템은 보존 만료일이 지난 타깃을 폐기 후보로 표시해야 하며, 자동으로
  데이터를 제거해서는 안 된다.
- **FR-036**: 시스템은 폐기 후보 타깃에 대한 운영자 폐기 승인이 있어야만 물리 스키마를
  제거해야 하며, 제거 후에도 레지스트리 항목을 폐기 상태로 보존해야 한다.
- **FR-037**: 시스템은 프로젝트 종료 시점에 그 프로젝트 추출물의 파기 예정일을 확정하고
  고정해야 한다.
- **FR-038**: 시스템은 파기 예정일이 지난 추출물을 파기해야 하며, 파기 대상, 실행 시각,
  결과를 기록해야 한다.
- **FR-039**: 시스템은 보존 정책 설정이 변경되어도 이미 확정된 보존 만료일과 파기
  예정일을 변경해서는 안 된다.
- **FR-040**: 시스템은 폐기·파기 실패 시 대상을 실패 상태로 유지하고 제거 범위를
  기록하며 운영자에게 알려야 한다.
- **FR-041**: 시스템은 폐기·파기 이후에도 실행 이력, 생성 조건 기록, 감사 이력을
  보존해야 한다.

**전 기능 공통**

- **FR-042**: 시스템은 타깃·프로젝트·추출물의 등록, 변경, 동결, 폐기, 파기 각각에
  대해 실행자와 시각을 포함한 감사 이력을 남겨야 한다.
- **FR-043**: 시스템은 타깃·프로젝트·추출물 관련 화면과 오류 메시지에 원천 데이터 값이나
  환자 식별정보가 포함되지 않도록 해야 한다.
- **FR-044**: 시스템은 워크스페이스가 소프트 삭제되면 그 워크스페이스의 타깃 갱신 실행과
  프로젝트 신규 실행을 중단해야 하고, 워크스페이스 정리 시 타깃과 추출물을 함께 정리해야
  한다.

### Key Entities

- **워크스페이스**: 기존 개념(기능 001). 파이프라인 정의, 매핑 사전, 권한의 귀속점이다.
  이 기능에서 워크스페이스는 타깃과 프로젝트의 소유자 역할을 새로 갖는다.
- **타깃**: 워크스페이스가 소유하는 장기 유지 산출물 단위. 물리 스키마와 1:1로 대응한다.
  고유 식별자, 소속 워크스페이스, 논리 이름, 물리 스키마, 갱신 방식, 갱신 주기, 동결
  시각, 생성 조건 기록, 보존 만료일, 상태를 갖는다.
- **갱신 방식**: rolling 또는 frozen. rolling은 계속 갱신되는 1벌이고, frozen은 특정
  시점에 고정되어 더 이상 바뀌지 않는다.
- **갱신 주기**: monthly, yearly, on_demand 중 하나. 타깃이 어떤 리듬으로 갱신되는지를
  나타낸다.
- **생성 조건 기록(provenance)**: 타깃이 만들어진 조건. 용어사전 버전, 변환 정의 버전,
  원천 추출 시각, 대상 표준 버전을 담고, AI가 개입한 경우 모델 버전과 프롬프트 버전을
  포함한다. 기능 004의 스냅샷 manifest가 담던 정보를 타깃 속성으로 흡수한 것이다.
- **타깃 상태**: 활성, 동결, 폐기 후보, 폐기 완료, 불일치(레지스트리와 실제 스키마
  불일치), 폐기 실패 중 하나.
- **프로젝트**: 목적·요청 단위 작업 묶음. 고유 식별자, 소속 워크스페이스, 목적, 요청자,
  기간, 상태(진행/종료), 개설자, 멤버 목록을 갖는다. 워크스페이스 멤버만 개설할 수 있다.
- **개설자**: 프로젝트마다 1명. 설정 변경, 멤버 초대·해제, 실행 요청, 추출물 파기 권한을
  갖는다. 배정 해제 등으로 공석이 되면 운영자가 다른 멤버에게 이관한다.
- **프로젝트 멤버십**: 사용자와 프로젝트의 연결. 역할은 개설자와 참여자로 나뉘며, 참여자는
  조회와 복제만 할 수 있다. 사용자 계정 자체는 통합 인증·권한 서비스가 소유하고, 워크스페이스
  배정은 기능 001이 소유하며, 이 기능은 프로젝트와 사용자의 연결만 소유한다.
- **복제 계보**: 복제본 추출물이 어느 프로젝트의 어느 추출물에서 복제되었는지의 기록.
  복제자, 복제 시각을 포함하며 원본이 파기된 뒤에도 남는다.
- **잡(Job)**: 실행 1회. 고유 식별자, 소속 워크스페이스, 대상 타깃(필수), 프로젝트(선택),
  상태, 요청자, 요청·시작·종료 시각을 갖는다. 기능 002가 "실행 건(flow run)"이라 부르는
  대상과 같으며, 이 모델에서의 이름이 잡이다. flow run은 오케스트레이션 계층의 용어이고
  잡은 이 모델의 용어다.
- **추출물(Extract)**: 프로젝트가 소유하는 산출물. 소유 프로젝트, 생성 잡, 생성
  시각, 파기 예정일, 상태를 갖는다. 타깃과 소유·수명·접근이 모두 다르며 타깃 목록과
  섞이지 않는다.
- **보존 정책**: 타깃의 보존 만료일 산정 규칙과 추출물의 파기 기한 산정 규칙. 둘은
  별개이며 서로 영향을 주지 않는다.
- **폐기 승인**: 폐기 후보 타깃을 실제로 제거하기 위한 운영자 승인 기록. 승인자, 승인
  시각, 대상 타깃을 갖는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새로운 타깃을 추가할 때 소프트웨어 변경 없이 등록만으로 실행 대상이
  된다. 타깃 추가를 위해 코드나 배포가 필요한 사례가 0건이다.
- **SC-002**: 논리 이름을 유지한 채 물리 스키마를 교체한 뒤, 그 이름을 사용하는 기능이
  수정 없이 새 스키마를 사용하는 비율이 100%다.
- **SC-003**: 대상 타깃이 지정되지 않은 실행이 접수된 사례가 0건이다.
- **SC-004**: 임의의 잡 하나를 골랐을 때 그것이 어느 워크스페이스의 어느 타깃에
  귀속되는지 1분 이내에 확인할 수 있다.
- **SC-005**: 동결된 타깃 100%가 용어사전 버전, 변환 정의 버전, 원천 추출 시각, 대상
  표준 버전을 모두 갖는다. 항목이 비어 있는 동결 타깃은 0건이다.
- **SC-006**: 임의의 동결 타깃에 대해 그것을 만든 조건 전부를 5분 이내에 확인할 수 있다.
- **SC-007**: 동결 이후 값이 바뀐 타깃이 0건이다.
- **SC-008**: 프로젝트 멤버가 아닌 사용자의 추출물 접근 시도가 100% 차단된다. 허용된
  접근이 잘못 차단되는 경우는 0건이다.
- **SC-009**: 타깃 목록에 추출물이, 추출물 목록에 타깃이 나타난 사례가 0건이다.
- **SC-010**: 보존 만료일이 지났다는 이유만으로 운영자 승인 없이 제거된 타깃이 0건이다.
- **SC-011**: 프로젝트 종료 후 파기 기한이 지난 추출물의 파기가 기한으로부터 24시간
  이내에 시작된다.
- **SC-012**: 폐기·파기된 타깃과 추출물 100%에 대해 무엇이 언제 누구에 의해 제거되었는지
  감사 이력에서 조회할 수 있다.
- **SC-013**: 운영자가 워크스페이스 하나의 전체 타깃 구성(논리 이름, 물리 스키마, 갱신
  방식, 상태, 보존 만료일)을 한 화면에서 2분 이내에 파악할 수 있다.
- **SC-014**: 워크스페이스에 배정되지 않은 사용자가 그 워크스페이스의 프로젝트를
  개설하거나 프로젝트 멤버가 된 사례가 0건이다.
- **SC-015**: 개설자가 아닌 멤버에 의해 프로젝트 설정이나 추출물 원본이 변경된 사례가
  0건이다. 같은 멤버의 조회·복제 요청이 잘못 차단되는 경우도 0건이다.
- **SC-016**: 복제로 만들어진 추출물 100%가 원본과의 계보와 자체 파기 예정일을 갖는다.

## Assumptions

- 워크스페이스 유형은 기능 001의 결정을 따라 SDM과 CDM만 대상으로 한다. 입력에 언급된
  ADMET은 기능 001 FR-008에서 이번 범위 밖으로 정해졌으므로 여기서도 제외한다. 타깃·
  프로젝트·실행 모델 자체는 유형에 중립적이므로 ADMET이 추가되어도 구조는 그대로 쓸 수
  있다.
- SDM 워크스페이스는 rolling 타깃 하나(`sdm`)를 갖고, CDM 워크스페이스는 rolling 타깃
  하나(`cdm_rolling`)와 연도별 frozen 타깃 다수(`cdm_2024`, `cdm_2025` …)를 갖는다.
  이는 입력에 제시된 구성이며, 타깃 개수 자체를 시스템이 강제하지는 않는다. 강제하는
  것은 SDM의 rolling 타깃 단일성(FR-009)뿐이다.
- 기존 스펙과의 관계는 개정이다. 기능 001의 워크스페이스는 그대로 유지되고, 기능 002의
  잡에 타깃·프로젝트 귀속이 추가되며, 기능 004의 CDM 스냅샷과 manifest는 frozen
  타깃과 생성 조건 기록으로 대체된다. 이 저장소에는 아직 구현 코드가 없으므로 운영
  데이터 마이그레이션은 고려하지 않는다.
- 기존 워크스페이스에는 유형에 맞는 기본 rolling 타깃 하나가 생성 시점에 함께 등록된다.
  타깃 없는 워크스페이스는 실행할 수 없기 때문이다.
- 생성 조건 기록의 항목은 입력의 `vocab_version`, `dbt_commit`, `source_extracted_at`,
  `cdm_version`에 각각 용어사전 버전, 변환 정의 버전, 원천 추출 시각, 대상 표준 버전으로
  대응한다. 변환 정의 버전은 특정 변환 도구에 묶이지 않는 논리적 식별자로 다룬다.
- 타깃의 보존 만료일은 기능 001의 워크스페이스 소프트 삭제 보존 기간(기본 30일)과 다른
  별개의 정책이다. 워크스페이스 보존 기간은 운영자 실수를 되돌리기 위한 복구 유예이고,
  타깃 보존 만료일은 데이터 자산의 연 단위 보존 정책이다.
- 타깃 만료 시 자동 삭제하지 않고 운영자 승인을 요구하는 이유는, 기능 004가 정한 대로
  CDM 스냅샷이 재생성할 수 없는 원본 자산이기 때문이다. 자동 삭제는 되돌릴 수 없는
  손실을 만든다.
- 추출물은 헌법 v2.0.0 원칙 II에 따라 병원 내부망 안에만 존재한다. 입력의 "가명 SDM
  반출본"이라는 표현은 원외 반출을 뜻하지 않는 것으로 해석하며, 이 스펙은 "반출"이라는
  이름을 쓰지 않는다.
- 추출물에 대한 접근 통제는 워크스페이스의 계층별 제한(기능 001 FR-016, FR-017)을
  대체하지 않고 그 위에 얹힌다. 워크스페이스 수준에서 차단된 사용자는 프로젝트 멤버여도
  접근할 수 없다. 워크스페이스 멤버 배정은 운영자의 권한이고(기능 001 FR-014), 프로젝트
  개설과 초대는 그 배정 위에서만 일어난다. 프로젝트가 워크스페이스 접근 통제의 우회로가
  되지 않게 하기 위해서다.
- 프로젝트의 권한 모델은 개설자와 참여자 둘로만 나눈다. 개설자는 쓰기, 참여자는 조회와
  복제다. 세분화된 프로젝트 롤 체계는 두지 않는다.
- 복제는 참여자가 원본을 건드리지 않고 자기 작업을 이어 가기 위한 수단이다. 복제본은
  독립된 새 프로젝트의 산출물이 되며 원본과 수명을 공유하지 않는다.
- 종료된 프로젝트의 추출물 복제를 막는 것은 보존 정책 우회를 방지하기 위한 판단이다.
  이를 허용하면 파기 직전 복제로 기한을 무한히 갱신할 수 있다. 종료된 프로젝트의 데이터가
  계속 필요하면 새 프로젝트로 요청을 다시 접수한다.
- 추출물에는 별도의 제공 절차를 두지 않는다(FR-033). 기능 008이 가명 연구용 SDM에 대해
  제공 승인·제공 데이터셋·제공 전용 계층·제공 롤·제공 이력을 모두 제거하기로 확정한
  결정과 정합을 맞춘 것이다. 헌법 v2.0.0의 TODO(INTERNAL_RELEASE_PROCEDURE)는 이
  기능에서 확정하지 않고 그대로 남는다.
- 프로젝트와 타깃은 다대다로 연결될 수 있다. 하나의 프로젝트가 여러 타깃을 읽을 수 있고,
  하나의 타깃이 여러 프로젝트에 읽힌다. 잡 하나는 타깃 하나를 대상으로 한다.
- 타깃의 데이터 계층 구조(landing, work, mart)는 기능 001의 정의를 그대로 따르며, 이
  기능은 계층 위에 타깃 단위의 귀속을 얹을 뿐 계층 자체를 바꾸지 않는다.
- 물리 스키마 교체는 무중단 교체(별칭 전환)를 위한 것이며, 교체 자체가 데이터를
  이동시키지는 않는다. 새 물리 스키마는 이미 준비된 상태로 등록된다.
- 프로젝트 멤버와 워크스페이스 롤 모두 통합 인증·권한 서비스의 사용자 계정을 참조하며,
  이 기능은 계정이나 롤 정의를 만들지 않는다.
- 실행 1회를 가리키는 이름은 잡(Job)이다. 처음 도입할 때 쓰던 Run이라는 이름을 바꾼
  것이며, 가리키는 대상과 속성은 그대로다. 기능 002의 "실행 건(flow run)"과 같은 대상이고,
  flow run은 오케스트레이션 계층이 부르는 이름이다. 이 명칭 변경은 이름만 바꾼 것이며,
  잡 아래에 재시도(attempt)를 따로 두는 구조 변경은 포함하지 않는다. 취소·재실행은 기능
  002가 정한 대로 새 잡을 만드는 방식을 그대로 따른다.
- 다기관 간 타깃·프로젝트 공유는 범위 밖이다.
