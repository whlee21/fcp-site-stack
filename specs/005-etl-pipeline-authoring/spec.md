  않는다. 기능 010이 참조 자산 바인딩에 적용한 원칙(FR-030)과 같다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 소스 스키마 조사와 소스 명세 작성 (Priority: P1)

운영자가 워크스페이스의 소스 커넥션에서 변환 대상이 되는 테이블의 스키마를 읽어온다.
시스템이 테이블 목록과 각 테이블의 컬럼 명세를 수집해 소스 명세로 만든다. 이 명세는
"이 병원의 원천 시스템에 무엇이 어떤 형태로 있는가"에 대한 기록이며, 이후 모든 저작
단계의 입력이다. 조사는 스키마 메타데이터만 읽고 환자 데이터 행은 읽지 않는다.

**Why this priority**: 목표 스키마로 가는 변환을 쓰려면 출발점이 무엇인지부터 알아야
한다. 이 스토리만 있어도 "원천에 무엇이 있는지 문서화된다"는 가치가 성립하며, 이후
스토리는 전부 이 명세를 입력으로 받는다.

**Independent Test**: 소스 커넥션이 설정된 워크스페이스에서 스키마 조사를 실행해 테이블
목록과 컬럼 명세가 수집되고, 조사 과정에서 환자 데이터 행이 읽히지 않은 것이 확인되면
검증 완료.

**Acceptance Scenarios**:

1. **Given** 소스 커넥션이 설정된 워크스페이스일 때, **When** 스키마 조사를 요청하면,
   **Then** 대상 테이블 목록과 각 테이블의 컬럼 명세가 수집된다.
2. **Given** 스키마 조사가 수행될 때, **When** 조사 동작을 확인하면, **Then** 스키마
   메타데이터만 읽고 환자 데이터 행을 읽지 않는다.
3. **Given** 컬럼 명세가 수집되었을 때, **When** 내용을 확인하면, **Then** 컬럼 이름,
   자료형, 널 허용 여부, 키 여부가 포함된다.
4. **Given** 소스 명세가 만들어졌을 때, **When** 명세를 조회하면, **Then** 조사 시각과
   소스 커넥션 식별자가 함께 확인된다.
5. **Given** 일부 테이블에 접근할 수 없을 때, **When** 조사를 수행하면, **Then** 해당
   테이블은 조사 실패로 기록되고 성공한 테이블만 명세에 포함된다.
6. **Given** 이전에 조사한 소스 명세가 있을 때, **When** 다시 조사하면, **Then** 이전
   명세와 비교해 추가·삭제·변경된 테이블과 컬럼이 확인된다.
7. **Given** 워크스페이스 롤이 없는 사용자일 때, **When** 소스 명세 조회를 시도하면,
   **Then** 접근이 거부된다.

### User Story 2 - 워크스페이스 유형별 프로세스와 태스크 정의 (Priority: P2)

워크스페이스 유형에 따라 수행할 프로세스 구성이 정해진다. 운영자는 그 구성 안의 각
프로세스에 대해 실제로 수행될 태스크 목록을 정의한다. 태스크는 어떤 소스 테이블 또는
어떤 선행 산출물을 입력으로 받아 무엇을 만드는지의 단위다. 유형이 정한 프로세스 구성
자체는 바꿀 수 없고, 그 안의 태스크 구성만 정의 대상이다.

**Why this priority**: 소스에 무엇이 있는지 알았으면 그것을 어떤 단위로 처리할지 정해야
한다. 태스크 단위가 정해져야 AI 에이전트에게 "이 태스크의 정의를 써라"고 시킬 수 있다.

**Independent Test**: CDM 워크스페이스와 SDM 워크스페이스를 각각 열어 유형에 맞는 프로세스
구성이 표시되고, 각 프로세스에 태스크를 정의할 수 있으며, 프로세스 구성 자체는 변경할
수 없는 것이 확인되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** CDM 유형 워크스페이스일 때, **When** 프로세스 구성을 조회하면, **Then**
   CDM 유형에 정해진 프로세스가 정해진 순서로 표시된다.
2. **Given** SDM 유형 워크스페이스일 때, **When** 프로세스 구성을 조회하면, **Then**
   SDM 유형에 정해진 프로세스가 정해진 순서로 표시된다.
3. **Given** 프로세스가 표시되었을 때, **When** 태스크를 정의하면, **Then** 해당
   프로세스에 속한 태스크로 등록된다.
4. **Given** 태스크가 등록되었을 때, **When** 내용을 확인하면, **Then** 소속 프로세스,
   프로세스 안에서의 순서, 입력 대상이 확인된다.
5. **Given** 사용자가 프로세스 구성을 바꾸려 할 때, **When** 프로세스를 추가·삭제·
   재배치하려 하면, **Then** 변경이 거부된다.
6. **Given** 태스크가 하나도 정의되지 않은 프로세스가 있을 때, **When** 파이프라인
   정의 상태를 조회하면, **Then** 해당 프로세스가 미완성으로 표시된다.
7. **Given** 태스크의 입력 대상이 소스 명세에 없는 테이블일 때, **When** 태스크를
   등록하려 하면, **Then** 등록이 거부된다.

### User Story 3 - AI 에이전트의 정의 초안 작성 (Priority: P3)

각 태스크에 대해 AI 에이전트가 적재 정의와 변환 정의의 초안을 작성한다. 입력은 소스
명세와 워크스페이스의 목표 스키마이고, 출력은 사람이 읽고 고칠 수 있는 정의 초안이다.
초안에는 어떤 모델과 어떤 프롬프트로 만들어졌는지가 함께 기록된다. 초안은 그 자체로는
실행 대상이 아니다.

**Why this priority**: 저작 비용의 대부분이 여기 있다. 앞의 두 스토리가 입력을 갖춰
놓으면 이 스토리가 실제 작업량을 줄인다.

**Independent Test**: 소스 명세와 목표 스키마가 준비된 태스크에 초안 작성을 요청해
적재 정의와 변환 정의 초안이 생성되고, 모델 버전과 프롬프트 버전이 함께 기록되며,
초안 상태로는 실행 대상이 되지 않는 것이 확인되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 소스 명세와 목표 스키마가 준비된 태스크일 때, **When** 초안 작성을
   요청하면, **Then** 적재 정의와 변환 정의의 초안이 생성된다.
2. **Given** 초안이 생성되었을 때, **When** 초안을 조회하면, **Then** 사용된 모델
   버전과 프롬프트 버전이 함께 확인된다.
3. **Given** 모델 버전이나 프롬프트 버전을 확인할 수 없을 때, **When** 초안을
   저장하려 하면, **Then** 초안이 저장되지 않는다.
4. **Given** 초안 작성이 수행될 때, **When** 실행 기록을 확인하면, **Then** AI
   에이전트가 직접 호출되지 않고 정해진 경유 지점을 통해 호출된 것이 확인된다.
5. **Given** 초안 상태의 정의가 있을 때, **When** 그 정의로 ETL 실행을 시도하면,
   **Then** 실행이 거부된다.
6. **Given** 목표 스키마의 어느 항목에도 대응하지 않는 소스 컬럼이 있을 때, **When**
   초안을 확인하면, **Then** 임의의 대응이 만들어지지 않고 미매핑으로 표시된다.
7. **Given** AI 응답을 받지 못했을 때, **When** 결과를 확인하면, **Then** 초안 작성이
   실패로 기록되고 부분 초안이 저장되지 않는다.

### User Story 4 - AI 에이전트의 dry-run 검증 (Priority: P4)

AI 에이전트가 작성한 초안을 스스로 시험 실행한다. 시험 실행은 소스의 실제 데이터를
표본으로 소량 읽어 수행하되, 워크스페이스의 데이터 계층에는 아무 변경도 남기지 않는다.
실패하면 에이전트가 초안을 고쳐 다시 시도하고, 정해진 재시도 한도에 도달하면 자동 수정을
멈추고 운영자에게 넘긴다. 표본은 시험이 끝나면 남지 않으며, 시험 결과를 화면에 보여줄 때
표본에서 온 원본 데이터 값이 그대로 노출되지 않는다.

**Why this priority**: 사람에게 넘기기 전에 명백한 오류를 걸러 내는 단계다. 이게 없으면
운영자가 문법 오류 수준의 문제까지 검토하게 되어 human-in-the-loop의 가치가 떨어진다.

**Independent Test**: 오류가 있는 초안에 dry-run을 걸어 에이전트가 수정 후 재시도하는
것과, 한도 도달 시 운영자 검토 대상으로 넘어가는 것, 데이터 계층에 아무 변경도 남지 않은
것, 그리고 읽은 표본이 시험 종료 후 남지 않은 것이 확인되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 초안이 있을 때, **When** dry-run을 수행하면, **Then** 워크스페이스의
   데이터 계층에 어떤 변경도 남지 않는다.
2. **Given** dry-run이 수행될 때, **When** 소스 읽기 동작을 확인하면, **Then** 정해진
   표본 크기 상한 이내로만 실제 데이터를 읽는다.
3. **Given** dry-run이 끝났을 때, **When** 표본의 보관 여부를 확인하면, **Then** 표본이
   남아 있지 않다.
4. **Given** dry-run이 실패했을 때, **When** 에이전트가 처리하면, **Then** 초안을
   수정해 다시 시도한다.
5. **Given** 재시도 한도에 도달했을 때, **When** 결과를 확인하면, **Then** 자동 수정이
   중단되고 해당 초안이 운영자 검토 대상으로 넘어간다.
6. **Given** dry-run이 수행되었을 때, **When** 결과를 조회하면, **Then** 시도 횟수와
   각 시도의 실패 사유 요약이 확인된다.
7. **Given** dry-run 결과를 화면에 표시할 때, **When** 내용을 확인하면, **Then** 표본에서
   온 원본 데이터 값이 실패 사유 요약을 포함해 어디에도 그대로 노출되지 않는다.
8. **Given** dry-run을 통과하지 못한 초안일 때, **When** 확정을 시도하면, **Then**
   확정이 거부된다.
9. **Given** dry-run이 성공했을 때, **When** 정의 상태를 확인하면, **Then** 확정
   대기 상태가 되고 아직 실행 대상은 아니다.

### User Story 5 - 운영자 검토와 확정 (Priority: P5)

dry-run을 통과한 초안을 운영자가 검토한다. 운영자는 소스 명세, 초안 내용, dry-run 결과를
함께 보고 확정하거나 반려한다. 초안을 직접 고칠 수도 있는데, 고친 정의는 dry-run을 다시
통과해야 확정할 수 있다. 확정된 정의만 ETL 실행 대상이 된다. 확정 이력에는 누가 언제 어떤
버전을 확정했는지, 그 정의가 어떤 모델·프롬프트에서 나왔는지, 그리고 AI 초안 이후 사람이
손을 댔는지가 남는다. dry-run 통과는 확정을 대신하지 않는다.

**Why this priority**: 사람이 책임지는 지점이다. 앞의 자동화가 전부 갖춰진 뒤 마지막에
붙어야 검토 대상이 충분히 정제된 상태로 올라온다.

**Independent Test**: dry-run을 통과한 초안을 검토 권한자가 확정해 실행 대상이 되고,
권한이 없는 사용자는 확정할 수 없으며, 초안을 편집한 경우 dry-run을 다시 통과해야만
확정되고, 확정 이력에 검토자·시각·정의 버전·모델 버전·사람 편집 여부가 남으면 검증 완료.

**Acceptance Scenarios**:

1. **Given** dry-run을 통과한 초안일 때, **When** 검토 권한자가 확정하면, **Then**
   해당 정의가 실행 대상이 된다.
2. **Given** 검토 권한이 없는 사용자일 때, **When** 확정을 시도하면, **Then** 요청이
   거부된다.
3. **Given** 검토 중인 초안일 때, **When** 운영자가 반려하면, **Then** 초안 상태로
   돌아가고 반려 사유가 기록된다.
4. **Given** 검토 중인 초안일 때, **When** 운영자가 내용을 직접 편집하면, **Then**
   편집이 반영되고 해당 정의가 dry-run 미통과 상태로 되돌아간다.
5. **Given** 운영자가 편집한 정의일 때, **When** dry-run을 다시 통과하지 않고 확정을
   시도하면, **Then** 확정이 거부된다.
6. **Given** 운영자가 정의를 편집했을 때, **When** 편집 이력을 조회하면, **Then**
   편집자, 편집 시각, 편집 전후 내용이 확인된다.
7. **Given** 정의가 확정되었을 때, **When** 확정 이력을 조회하면, **Then** 검토자,
   검토 시각, 확정된 정의 버전, 사용된 모델 버전과 프롬프트 버전, 그리고 AI 초안 이후
   사람 편집이 있었는지가 확인된다.
8. **Given** dry-run을 통과했으나 운영자가 오류를 발견했을 때, **When** 반려하면,
   **Then** 반려가 받아들여지고 자동 통과가 확정을 대신하지 않는다.
9. **Given** 확정된 정의가 있을 때, **When** 소스 명세가 다시 조사되어 관련 테이블이나
   컬럼이 바뀌면, **Then** 영향받는 정의가 재검토 대상으로 표시된다.
10. **Given** 확정된 정의를 수정할 때, **When** 수정 내용을 저장하면, **Then** 새 버전이
    되고 dry-run과 확정을 다시 거쳐야 실행 대상이 된다.
11. **Given** 운영자가 검토 화면을 열었을 때, **When** 화면을 확인하면, **Then** 소스
    명세, 정의 초안, dry-run 결과가 함께 확인된다.

### User Story 6 - 정의의 파라미터화 (Priority: P6)

같은 일을 하는 정의를 워크스페이스마다 따로 만들면, 워크스페이스가 늘어날 때마다 같은
로직이 복제되고 한 곳을 고치면 나머지를 찾아 고쳐야 한다. 그래서 정의는 본문과 파라미터로
나뉜다. 본문은 무엇을 어떻게 처리하는지를 담고, 워크스페이스마다 달라지는 값은 파라미터로
바깥에서 주입된다.

파라미터로 빠져야 하는 대표적인 것이 물리 스키마 이름, 소스 접속 정보, 대상 타깃
식별자다. 이 값들이 본문에 박히면 타깃 레지스트리로 스키마를 교체할 수 있게 만든 의미가
사라진다.

정의는 자기가 어떤 파라미터를 요구하는지 선언한다. 이름, 의미, 필수 여부, 기본값이다.
선언하지 않은 파라미터가 들어오거나 필수 파라미터가 비어 있으면 확정도 실행도 되지 않는다.

파라미터 값은 운영자가 화면에서 바꿀 수 있고, 바꾸면 시스템이 그 변경을 저장소에 커밋한다.
화면의 편의와 저장소의 이력을 둘 다 얻는 방식이다. 다만 계정이나 암호처럼 비밀인 값은
저장소에 들어가지 않는다. 커밋은 지우기 어렵기 때문에, 비밀 파라미터는 값 대신 어디에서
가져올지의 참조만 커밋하고 실제 값은 저장소 밖에 둔다.

**Why this priority**: 저작 절차가 먼저 서야 파라미터로 뺄 대상이 정해진다. 다만 이것이
서지 않으면 워크스페이스가 늘어날수록 유지 비용이 선형으로 늘어난다.

**Independent Test**: 정의 하나를 두 워크스페이스가 서로 다른 파라미터 값으로 사용해
각자의 타깃에 적재되는 것을 확인하고, 필수 파라미터가 비었을 때 확정과 실행이 거부되는
것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 정의가 작성되었을 때, **When** 그 정의를 조회하면, **Then** 요구하는 파라미터의
   이름, 의미, 필수 여부, 기본값이 선언되어 있다.
2. **Given** 두 워크스페이스가 같은 정의를 사용할 때, **When** 각자의 파라미터 값으로
   실행하면, **Then** 정의 본문은 하나이고 각자의 대상에 처리된다.
3. **Given** 필수 파라미터에 값이 없을 때, **When** 확정이나 실행을 시도하면, **Then**
   거부되고 어떤 파라미터가 비었는지 안내된다.
4. **Given** 정의가 선언하지 않은 파라미터가 주어졌을 때, **When** 실행을 시도하면,
   **Then** 거부된다.
5. **Given** 정의 본문을 확인할 때, **When** 물리 스키마 이름이나 소스 접속 정보를
   찾으면, **Then** 본문에 고정된 값이 없고 파라미터로만 주입된다.
6. **Given** 파라미터 값에 계정이나 암호가 포함될 때, **When** 화면이나 이력을 조회하면,
   **Then** 그 값이 마스킹되어 표시된다.
7. **Given** dry-run이나 실행이 수행되었을 때, **When** 기록을 확인하면, **Then** 그때
   적용된 파라미터 값 집합이 마스킹된 형태로 확인된다.
8. **Given** 운영자가 화면에서 파라미터 값을 바꿨을 때, **When** 저장소를 확인하면,
   **Then** 그 변경이 커밋으로 반영되어 있다.
9. **Given** 커밋을 조회할 때, **When** 커밋 주체를 확인하면, **Then** 사람의 확정
   행위인지 화면 변경에 따른 자동 반영인지가 구분되고 변경자와 변경 시각이 확인된다.
10. **Given** 비밀 정보를 담은 파라미터가 있을 때, **When** 저장소의 커밋 내용을 확인하면,
    **Then** 값이 아니라 값을 가져올 위치의 참조만 들어 있다.
11. **Given** 화면에서 바꾼 파라미터 값이 아직 커밋되지 않았을 때, **When** 그 값으로
    실행을 시도하면, **Then** 실행이 접수되지 않는다.

### User Story 7 - 형상 관리 저장소의 버전과 실행 연결 (Priority: P7)

확정된 정의와 파라미터 선언은 병원 안의 형상 관리 저장소에 커밋으로 보관된다. 정의 버전은
그 커밋이다. 화면에서 본 정의와 저장소에 있는 정의가 다를 수 없고, 어떤 버전으로 무엇이
만들어졌는지는 커밋 식별자로 가리킬 수 있다.

실행은 특정 커밋을 참조하고, 그 커밋 식별자가 산출물의 생성 조건 기록에 남는다. 기능
009가 생성 조건 기록의 항목으로 요구하는 "변환 정의 버전"이 바로 이 값이다. 스냅샷을
남기는 이유가 재현성인데, 어떤 정의로 만들어졌는지 가리킬 수 없으면 그 기록은 비어 있는
것과 같다.

어느 커밋을 쓸지는 워크스페이스마다 고정되어 있다. 새 버전이 확정되어도 자동으로 옮겨
가지 않고, 운영자가 승격해야 바뀐다. 한 워크스페이스를 위한 수정이 검증 없이 다른
워크스페이스의 실행에 들어가면 안 되기 때문이다. 기능 010이 참조 자산 바인딩에 적용한
원칙과 같다.

저장소는 병원 내부망 안에 있다. 외부 원격 저장소를 참조하지 않는다.

**Why this priority**: 파라미터화가 끝나야 무엇을 커밋할지가 정해진다. 이 스토리가 서면
정의의 이력과 산출물의 재현 조건이 하나의 식별자로 연결된다.

**Independent Test**: 정의를 확정해 커밋이 생기고, 그 커밋 식별자로 실행한 산출물의 생성
조건 기록에서 같은 식별자가 확인되며, 저장소에 없는 버전을 참조하는 실행이 거부되는 것을
확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 정의가 확정되었을 때, **When** 형상 관리 저장소를 확인하면, **Then** 그
   정의와 파라미터 선언이 커밋으로 보관되어 있다.
2. **Given** 정의 버전을 조회할 때, **When** 식별자를 확인하면, **Then** 저장소의 커밋
   식별자다.
3. **Given** 초안이나 dry-run 미통과 정의가 있을 때, **When** 저장소를 확인하면,
   **Then** 확정 정의로 올라가 있지 않다.
4. **Given** 실행이 성공했을 때, **When** 산출물의 생성 조건 기록을 확인하면, **Then**
   사용된 정의 버전이 커밋 식별자로 확인된다.
5. **Given** 저장소에 없는 정의 버전을 지정했을 때, **When** 실행을 요청하면, **Then**
   요청이 거부된다.
6. **Given** 커밋을 조회할 때, **When** 내용을 확인하면, **Then** 확정자, 확정 시각, 대상
   태스크, 사용된 모델 버전과 프롬프트 버전을 추적할 수 있다.
7. **Given** 형상 관리 저장소 설정을 확인할 때, **When** 저장소 위치를 보면, **Then**
   병원 내부망 안이며 외부 원격 저장소를 참조하지 않는다.
8. **Given** 저장소에 보관된 정의와 파라미터를 확인할 때, **When** 내용을 보면, **Then**
   원천 데이터 값이나 환자 식별정보가 포함되어 있지 않다.
9. **Given** 워크스페이스에 고정된 정의 버전이 있을 때, **When** 실행하면, **Then** 그
   고정된 커밋이 참조된다.
10. **Given** 새 정의 버전이 확정되었을 때, **When** 워크스페이스의 고정 버전을 확인하면,
    **Then** 이전 버전 그대로이고 자동으로 바뀌지 않았다.
11. **Given** 운영자가 새 버전으로 승격했을 때, **When** 이후 실행을 확인하면, **Then**
    승격된 커밋이 참조된다.
12. **Given** 승격이 일어났을 때, **When** 승격 이력을 조회하면, **Then** 승격자, 승격
    시각, 이전 버전, 새 버전이 확인된다.
13. **Given** 확정되지 않은 버전으로 승격을 시도할 때, **When** 승격을 요청하면, **Then**
    거부된다.
14. **Given** 워크스페이스의 고정 버전이 확정된 최신 버전보다 뒤에 있을 때, **When**
    목록을 조회하면, **Then** 그 차이가 확인된다.

### Edge Cases

- 소스 커넥션에 접근할 수 없으면 어떻게 되는가? 스키마 조사가 실패로 기록되고 소스
  명세가 만들어지지 않는다. 이전 조사 결과가 있으면 그것이 그대로 남는다.
- 소스에 대상 테이블이 하나도 없으면 어떻게 되는가? 빈 소스 명세가 만들어지고, 태스크를
  정의할 입력 대상이 없으므로 이후 단계로 진행하지 않는다.
- 소스 스키마 조사 도중 컬럼의 자료형을 해석할 수 없으면 어떻게 되는가? 해당 컬럼을
  임의의 자료형으로 단정하지 않고 미확인으로 기록한다. 미확인 컬럼을 입력으로 삼는
  태스크의 초안 작성은 진행하되, 그 컬럼이 미매핑으로 남는다.
- AI 에이전트가 dry-run을 통과시켰지만 운영자가 명백한 오류를 발견하면 어떻게 되는가?
  운영자가 반려한다. 자동 통과는 확정 조건 중 하나일 뿐 확정 자체가 아니다.
- 재시도 한도를 넘긴 초안은 어떻게 되는가? 폐기되지 않고 마지막 시도 상태 그대로
  운영자 검토 대상으로 넘어간다. 실패 사유 요약이 함께 전달된다.
- 확정 대기 중인 정의가 있는 워크스페이스가 삭제 표시되면 어떻게 되는가? 기능 001의
  삭제 표시 규칙을 따라 신규 확정이 차단된다.
- 같은 태스크에 초안 작성이 동시에 여러 번 요청되면 어떻게 되는가? 태스크 단위로 하나의
  초안 작성만 진행되고 나머지는 거부되거나 대기한다.
- 확정된 정의가 실행 중일 때 그 정의를 수정하면 어떻게 되는가? 실행 중인 건은 실행
  시작 시점에 확정되어 있던 버전으로 끝까지 진행하고, 수정본은 새 버전으로 별도 확정
  절차를 거친다.
- dry-run이 정해진 시간을 넘겨 끝나지 않으면 어떻게 되는가? 해당 시도를 실패로 처리하고
  재시도 횟수에 포함한다.
- dry-run 표본을 읽을 대상 테이블이 비어 있으면 어떻게 되는가? 표본 없이 수행할 수 있는
  범위까지만 검증하고, 값 수준 검증이 이루어지지 않았음을 결과에 표시한다. 빈 테이블을
  통과 근거로 삼지 않는다.
- 운영자가 편집한 정의가 dry-run에서 계속 실패하면 어떻게 되는가? 자동 수정 재시도는
  AI 초안에만 적용되고 사람이 편집한 정의에는 적용되지 않는다. 운영자가 다시 편집하거나
  AI 초안 작성부터 다시 시작한다.
- 운영자가 편집하는 도중 소스 명세가 다시 조사되면 어떻게 되는가? 편집 중인 정의는
  편집 시작 시점의 소스 명세를 기준으로 유지되고, 확정 시점에 재검토 대상 표시가 붙는다.
- AI 에이전트가 만든 정의가 실행 시 원본 데이터 값을 로그에 남기도록 작성되어 있으면
  어떻게 되는가? 로그 마스킹은 정의 내용과 무관하게 플랫폼의 로깅 필터가 강제하므로
  정의가 그것을 무력화할 수 없다.
- 형상 관리 저장소가 일시적으로 응답하지 않으면 어떻게 되는가? 확정이 완료되지 않고 정의는
  확정 대기 상태로 남는다. 커밋 없이 확정된 것으로 표시해서는 안 된다.
- 저장소에서 과거 커밋이 사라지면 그 커밋으로 만들어진 산출물은 어떻게 되는가? 산출물의
  생성 조건 기록에 남은 식별자는 유효하지만 정의 본문을 되찾을 수 없으므로 재현이 불가능해진다.
  그래서 사용된 적이 있는 커밋은 저장소에서 제거 대상이 아니다.
- 정의 본문은 그대로인데 파라미터 값만 바뀌면 새 버전인가? 그렇다. 화면에서의 값 변경도
  커밋으로 남으므로 새 커밋이 생긴다. 다만 그 커밋은 사람의 확정 행위가 아니라 자동 반영으로
  구분해 기록된다.
- 여러 워크스페이스가 같은 정의를 쓰는데 한 곳의 요구로 정의를 고치면 어떻게 되는가?
  새 버전이 생기지만 다른 워크스페이스는 영향받지 않는다. 각자 고정된 버전을 쓰고 있고,
  옮겨 가려면 운영자가 승격해야 한다.
- 화면에서 파라미터를 바꿨는데 저장소가 응답하지 않으면 어떻게 되는가? 변경이 반영되지
  않은 것으로 다뤄지고, 커밋되지 않은 값으로는 실행이 접수되지 않는다.
- 비밀 파라미터의 값이 저장소 밖 어디에 있어야 하는가? 이 명세는 값이 저장소에 들어가지
  않고 참조만 커밋된다는 것까지 정한다. 비밀 보관 위치의 구성은 배포 설계가 정하며, 헌법
  원칙 I에 따라 병원 내부망 안이어야 한다.
- 오래된 고정 버전에 머무른 워크스페이스는 어떻게 알아차리는가? 고정 버전과 확정된 최신
  버전의 차이가 목록에 표시된다. 승격 여부는 운영자의 판단이며 시스템이 강제하지 않는다.
- 파라미터로 빼야 할 값이 정의 본문에 남아 있으면 어떻게 알 수 있는가? 확정 전 검토에서
  걸러야 하며, 물리 스키마 이름과 접속 정보는 본문에 있으면 확정이 거부된다(FR-054).

## Requirements *(mandatory)*

### Functional Requirements

**프로세스와 태스크 정의**

- **FR-001**: 시스템은 워크스페이스 유형에 따라 수행할 프로세스 구성과 그 순서를 정해야
  하며, 이 구성은 기능 004가 정의한 유형별 단계 구성과 일치해야 한다.
- **FR-002**: 사용자는 각 프로세스에 대해 태스크 목록을 정의할 수 있어야 한다.
- **FR-003**: 시스템은 각 태스크에 소속 프로세스, 프로세스 안에서의 순서, 입력 대상을
  기록해야 한다.
- **FR-004**: 시스템은 유형이 정한 프로세스 구성 자체의 추가·삭제·재배치를 허용해서는
  안 된다.
- **FR-005**: 시스템은 태스크의 입력 대상이 소스 명세에 존재하지 않으면 그 태스크의
  등록을 거부해야 한다.
- **FR-006**: 시스템은 태스크가 하나도 정의되지 않은 프로세스를 미완성으로 표시해야 한다.
- **FR-007**: 시스템은 각 정의의 상태를 초안, dry-run 통과, 확정, 반려로 구분해야 한다.
- **FR-008**: 시스템은 확정 상태가 아닌 정의로 ETL이 실행되는 것을 거부해야 한다.

**소스 스키마 조사와 소스 명세**

- **FR-009**: 시스템은 워크스페이스의 소스 커넥션에서 대상 테이블의 스키마를 읽어야 한다.
- **FR-010**: 시스템은 스키마 조사에서 메타데이터만 읽어야 하며, 환자 데이터 행을
  읽어서는 안 된다.
- **FR-011**: 시스템은 각 컬럼에 대해 이름, 자료형, 널 허용 여부, 키 여부를 기록해야 한다.
- **FR-012**: 시스템은 자료형을 해석할 수 없는 컬럼을 임의의 자료형으로 단정해서는 안
  되며, 미확인으로 기록해야 한다.
- **FR-013**: 시스템은 소스 명세에 조사 시각과 소스 커넥션 식별자를 기록해야 한다.
- **FR-014**: 시스템은 접근할 수 없는 테이블을 조사 실패로 기록하고, 성공한 테이블만
  명세에 포함해야 한다.
- **FR-015**: 시스템은 재조사 시 이전 명세와 비교해 추가·삭제·변경된 테이블과 컬럼을
  확인할 수 있게 해야 한다.
- **FR-016**: 시스템은 소스 명세의 조회를 워크스페이스 롤에 따라 통제해야 한다.

**AI 에이전트의 정의 초안 작성**

- **FR-017**: 시스템은 소스 명세와 목표 스키마를 입력으로 적재 정의와 변환 정의의 초안을
  작성해야 한다.
- **FR-018**: 시스템은 목표 스키마를 워크스페이스의 대상 표준과 대상 표준 버전 설정에서
  결정해야 하며, 저작 과정에서 임의로 바꿔서는 안 된다. SDM 유형의 목표 스키마는 SDM
  표준 스키마 정의가, CDM 유형의 목표 스키마는 OMOP CDM이 정한다.
- **FR-019**: 시스템은 목표 스키마 정의에서 각 대상 컬럼의 자료형, 키 여부, 필수 여부를
  읽어 초안 작성의 입력으로 삼아야 한다.
- **FR-020**: 시스템은 목표 스키마 정의에 필수로 표시된 컬럼이 초안에서 채워지지 않은
  경우 이를 미충족으로 표시해야 하며, 임의의 값으로 채워서는 안 된다.
- **FR-021**: 시스템은 생성된 초안에 사용된 모델 버전과 프롬프트 버전을 함께 기록해야
  하며, 둘 중 하나라도 확인되지 않으면 초안을 저장해서는 안 된다.
- **FR-022**: 시스템은 AI 에이전트를 직접 호출해서는 안 되며, 정해진 경유 지점을 통해서만
  호출해야 한다.
- **FR-023**: 시스템은 목표 스키마의 어느 항목에도 대응하지 않는 소스 컬럼에 대해 임의의
  대응을 만들어서는 안 되며, 미매핑으로 표시해야 한다.
- **FR-024**: 시스템은 AI 응답을 받지 못한 경우 초안 작성을 실패로 기록해야 하며, 부분
  초안을 저장해서는 안 된다.
- **FR-025**: 시스템은 같은 태스크에 대해 동시에 여러 초안 작성이 진행되지 않게 해야 한다.

**dry-run 검증**

- **FR-026**: 시스템은 dry-run이 워크스페이스의 데이터 계층에 어떤 변경도 남기지 않게
  해야 한다.
- **FR-027**: 시스템은 dry-run을 소스의 실제 데이터를 표본으로 읽어 수행해야 한다.
- **FR-028**: 시스템은 dry-run이 읽는 표본에 크기 상한을 두어야 하며, 상한을 넘겨 읽어서는
  안 된다.
- **FR-029**: 시스템은 dry-run 표본 읽기를 소스 커넥션의 접근 통제 아래 수행해야 하며,
  저작 권한만으로 소스 데이터를 임의 조회하는 경로를 만들어서는 안 된다.
- **FR-030**: 시스템은 dry-run이 끝나면 읽은 표본을 보존해서는 안 된다.
- **FR-031**: 시스템은 dry-run 실패 시 AI 에이전트가 초안을 수정해 재시도하도록 해야 한다.
- **FR-032**: 시스템은 자동 재시도에 한도를 두어야 하며, 한도에 도달하면 자동 수정을
  중단하고 해당 초안을 운영자 검토 대상으로 넘겨야 한다.
- **FR-033**: 시스템은 dry-run 결과에 시도 횟수와 각 시도의 실패 사유 요약을 기록해야 한다.
- **FR-034**: 시스템은 dry-run 결과를 화면에 표시할 때 표본에서 온 원본 데이터 값이 그대로
  노출되지 않게 해야 한다. 실패 사유 요약도 이 제한의 적용 대상이다.
- **FR-035**: 시스템은 표본을 읽을 대상이 비어 있어 값 수준 검증이 이루어지지 않은 경우
  이를 결과에 표시해야 하며, 빈 표본을 통과 근거로 삼아서는 안 된다.
- **FR-036**: 시스템은 정해진 시간을 넘긴 dry-run 시도를 실패로 처리하고 재시도 횟수에
  포함해야 한다.
- **FR-037**: 시스템은 dry-run을 통과하지 못한 초안의 확정을 거부해야 한다.

**운영자 검토와 확정**

- **FR-038**: 시스템은 확정을 검토 권한을 가진 사람만 수행할 수 있게 해야 한다.
- **FR-039**: 시스템은 dry-run 통과를 확정으로 간주해서는 안 되며, 사람의 확정 행위를
  별도로 요구해야 한다.
- **FR-040**: 사용자는 검토 중인 정의의 내용을 직접 편집할 수 있어야 한다.
- **FR-041**: 시스템은 사람이 편집한 정의를 dry-run 미통과 상태로 되돌려야 하며, dry-run을
  다시 통과하기 전에는 확정을 거부해야 한다.
- **FR-042**: 시스템은 자동 수정 재시도를 AI가 작성한 초안에만 적용해야 하며, 사람이
  편집한 정의를 AI가 자동으로 고쳐서는 안 된다.
- **FR-043**: 시스템은 편집 이력에 편집자, 편집 시각, 편집 전후 내용을 기록해야 한다.
- **FR-044**: 시스템은 반려 시 반려 사유를 기록하고 정의를 초안 상태로 되돌려야 한다.
- **FR-045**: 시스템은 확정 이력에 검토자, 검토 시각, 확정된 정의 버전, 사용된 모델
  버전과 프롬프트 버전, 그리고 AI 초안 이후 사람 편집이 있었는지를 기록해야 한다.
- **FR-046**: 시스템은 검토 화면에서 소스 명세, 정의 초안, dry-run 결과를 함께 확인할
  수 있게 해야 한다.
- **FR-047**: 시스템은 소스 명세가 변경되었을 때 영향받는 확정 정의를 재검토 대상으로
  표시해야 한다.
- **FR-048**: 시스템은 확정된 정의의 수정을 새 버전으로 다뤄야 하며, 새 버전은 dry-run과
  확정을 다시 거쳐야 실행 대상이 되어야 한다.
- **FR-049**: 시스템은 실행 중인 건에 대해 실행 시작 시점에 확정되어 있던 정의 버전을
  끝까지 적용해야 한다.

**정의의 파라미터화**

- **FR-050**: 시스템은 정의를 정의 본문과 파라미터로 분리해 보관해야 하며, 워크스페이스마다
  정의 본문을 복제하지 않고 파라미터 값만 달리해 재사용할 수 있게 해야 한다.
- **FR-051**: 시스템은 정의마다 요구하는 파라미터의 이름, 의미, 필수 여부, 기본값을
  선언하게 해야 한다.
- **FR-052**: 시스템은 필수 파라미터에 값이 없는 정의의 확정과 실행 접수를 거부해야 하며,
  어떤 파라미터가 비었는지 안내해야 한다.
- **FR-053**: 시스템은 정의가 선언하지 않은 파라미터가 주어진 실행 요청을 거부해야 한다.
- **FR-054**: 시스템은 물리 스키마 이름, 소스 접속 정보, 대상 타깃 식별자를 정의 본문에
  고정해서는 안 되며 파라미터로만 주입되게 해야 한다.
- **FR-055**: 시스템은 파라미터 값에 포함된 비밀 정보를 형상 관리 저장소에 평문으로
  보관해서는 안 되며, 화면과 이력에서 마스킹해 표시해야 한다.
- **FR-056**: 시스템은 dry-run과 실행에 적용된 파라미터 값 집합을 기록해야 하며, 기록에도
  FR-055의 마스킹을 적용해야 한다.

**형상 관리 저장소의 버전**

- **FR-057**: 시스템은 확정된 정의와 그 파라미터 선언을 형상 관리 저장소에 커밋으로
  보관해야 한다.
- **FR-058**: 시스템은 정의 버전 식별자를 형상 관리 저장소의 커밋 식별자로 삼아야 한다.
- **FR-059**: 시스템은 커밋으로부터 확정자, 확정 시각, 대상 태스크, 사용된 모델 버전과
  프롬프트 버전을 추적할 수 있게 해야 한다.
- **FR-060**: 시스템은 확정되지 않은 초안이나 dry-run 미통과 정의를 확정 정의로 저장소에
  올려서는 안 된다.
- **FR-061**: 시스템은 형상 관리 저장소에 존재하지 않는 정의 버전을 참조하는 실행 요청을
  거부해야 한다.
- **FR-062**: 시스템은 산출물의 생성 조건 기록에 사용된 정의 버전을 커밋 식별자로
  포함해야 한다.
- **FR-063**: 시스템은 형상 관리 저장소를 병원 내부망 안에 두어야 하며, 외부 원격 저장소를
  참조해서는 안 된다.
- **FR-064**: 시스템은 저장소에 보관되는 정의와 파라미터에 원천 데이터 값이나 환자
  식별정보가 포함되지 않게 해야 한다.
- **FR-065**: 시스템은 화면에서 이루어진 파라미터 값 변경을 형상 관리 저장소에 커밋으로
  자동 반영해야 하며, 커밋되지 않은 파라미터 값이 실행에 사용되어서는 안 된다.
- **FR-066**: 시스템은 각 커밋의 주체가 사람의 확정 행위인지 화면 변경에 따른 자동 반영인지
  구분해 기록해야 하며, 변경자와 변경 시각을 함께 남겨야 한다.
- **FR-067**: 시스템은 비밀 정보를 담은 파라미터에 대해 값 대신 참조만 커밋해야 한다.
  비밀 값 자체는 저장소 밖의 비밀 보관 위치에 두고 실행 시점에 해석되어야 한다.
- **FR-068**: 시스템은 워크스페이스마다 사용할 정의 버전을 고정해 보유해야 하며, 실행은
  그 고정된 커밋을 참조해야 한다.
- **FR-069**: 시스템은 새 정의 버전이 확정되어도 워크스페이스의 고정 버전을 자동으로
  바꿔서는 안 된다.
- **FR-070**: 사용자는 워크스페이스의 고정 버전을 다른 확정 버전으로 승격할 수 있어야
  하며, 승격은 명시적인 조작이어야 한다.
- **FR-071**: 시스템은 승격 이력에 승격자, 승격 시각, 이전 버전, 새 버전을 기록해야 한다.
- **FR-072**: 시스템은 확정되지 않았거나 저장소에 없는 버전으로의 승격을 거부해야 한다.
- **FR-073**: 시스템은 워크스페이스별로 현재 고정된 버전과 확정된 최신 버전이 다를 때 그
  차이를 확인할 수 있게 해야 한다.

### Key Entities

- **소스 명세**: 특정 시점의 소스 커넥션에서 조사한 결과. 조사 시각, 소스 커넥션 식별자,
  테이블 명세 목록을 갖는다. 조사할 때마다 새로 만들어지고 이전 것과 비교 대상이 된다.
- **테이블 명세**: 소스의 테이블 하나에 대한 기록. 테이블 이름과 컬럼 명세 목록을 갖는다.
- **컬럼 명세**: 컬럼 하나에 대한 기록. 이름, 자료형, 널 허용 여부, 키 여부를 갖는다.
  자료형은 미확인 상태를 가질 수 있다.
- **프로세스 구성**: 워크스페이스 유형이 결정하는 프로세스의 종류와 순서. 저작 과정에서
  변경할 수 없다.
- **태스크**: 프로세스 안의 처리 단위. 소속 프로세스, 순서, 입력 대상을 갖는다.
- **목표 스키마 정의**: 대상 표준이 정하는 테이블·컬럼 구조. 각 컬럼의 자료형, 키 여부,
  필수 여부를 담는다. 워크스페이스의 대상 표준과 버전이 어느 정의를 쓸지 결정한다.
- **정의**: 태스크 하나를 수행하는 적재 정의와 변환 정의. 상태(초안·dry-run 통과·확정·
  반려)와 버전을 갖는다.
- **정의 버전**: 확정 단위. 수정할 때마다 새로 만들어지며 이전 버전을 대체하지 않는다.
  식별자는 형상 관리 저장소의 커밋 식별자이며, 산출물의 생성 조건 기록이 가리키는 값이다.
- **파라미터 선언**: 정의가 요구하는 파라미터의 목록. 이름, 의미, 필수 여부, 기본값을
  갖는다. 정의 본문과 함께 버전 관리된다.
- **파라미터 값 집합**: 특정 워크스페이스·실행에 적용된 파라미터의 실제 값. 비밀 정보는
  마스킹 대상이다.
- **형상 관리 저장소**: 확정된 정의와 파라미터 선언이 커밋으로 보관되는 곳. 병원 내부망
  안에 있으며 외부 원격 저장소를 참조하지 않는다. 커밋마다 주체가 사람의 확정 행위인지
  화면 변경에 따른 자동 반영인지 구분된다.
- **고정 버전**: 워크스페이스가 실행에 사용하는 정의 버전. 새 버전 확정으로 자동으로
  바뀌지 않고 승격으로만 바뀐다.
- **승격 이력**: 고정 버전이 바뀐 기록. 승격자, 승격 시각, 이전 버전, 새 버전을 갖는다.
- **비밀 파라미터 참조**: 비밀 값을 저장소 밖 보관 위치에서 가져오기 위한 지시자. 커밋에는
  이 참조만 들어가고 값은 들어가지 않는다.
- **dry-run 결과**: 시도 횟수, 각 시도의 실패 사유 요약, 최종 통과 여부, 값 수준 검증
  수행 여부.
- **편집 이력**: 사람이 정의를 고친 기록. 편집자, 편집 시각, 편집 전후 내용을 갖는다.
  정의 버전과 별개로 누적된다.
- **확정 이력**: 검토자, 검토 시각, 확정된 정의 버전, 사용된 모델 버전과 프롬프트 버전,
  AI 초안 이후 사람 편집 여부. 반려의 경우 반려 사유를 포함한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 확정되지 않은 정의로 ETL이 실행된 사례가 0건이다.
- **SC-002**: 모델 버전 또는 프롬프트 버전이 누락된 채 저장된 초안이 0건이다.
- **SC-003**: 스키마 조사 과정에서 환자 데이터 행이 읽힌 사례가 0건이다.
- **SC-004**: dry-run이 워크스페이스의 데이터 계층에 변경을 남긴 사례가 0건이다.
- **SC-005**: dry-run 결과 화면에 표본에서 온 원본 데이터 값이 노출된 사례가 0건이다.
- **SC-006**: dry-run이 정해진 표본 크기 상한을 넘겨 소스 데이터를 읽은 사례가 0건이다.
- **SC-007**: dry-run 종료 후 표본이 남아 있는 사례가 0건이다.
- **SC-008**: AI 에이전트가 정해진 경유 지점을 거치지 않고 호출된 사례가 0건이다.
- **SC-009**: 목표 스키마에 대응하지 않는 소스 컬럼이 임의의 대응으로 채워진 사례가
  0건이다.
- **SC-010**: dry-run을 통과하지 않은 초안이 확정된 사례가 0건이다.
- **SC-011**: 검토 권한이 없는 사용자가 정의를 확정한 사례가 0건이다.
- **SC-012**: 사람이 편집한 뒤 dry-run을 다시 통과하지 않고 확정된 정의가 0건이다.
- **SC-013**: 확정 이력 중 AI 초안 이후 사람 편집 여부가 기록되지 않은 사례가 0건이다.
- **SC-014**: 유형이 정한 프로세스 구성이 저작 과정에서 변경된 사례가 0건이다.
- **SC-015**: 소스 스키마가 변경된 뒤 영향받는 확정 정의가 재검토 대상으로 표시되지
  않은 사례가 0건이다.
- **SC-016**: 운영자가 태스크 하나의 정의를 검토해 확정하거나 반려하는 데 필요한 정보를
  한 화면에서 확인할 수 있고, 검토 판단까지 5분 이내가 걸린다.
- **SC-017**: 태스크 하나의 정의를 실행 가능한 상태로 만드는 데 걸리는 시간이, 운영자가
  처음부터 직접 작성하는 경우의 절반 이하다.
- **SC-018**: 감사자가 임의의 확정 정의에 대해 어떤 소스 명세와 어떤 모델·프롬프트
  버전에서 나왔는지 추적하는 데 5분 이내가 걸린다.
- **SC-019**: 운영자에게 넘어온 초안 중 재시도 한도 초과 사유가 기록되지 않은 사례가
  0건이다.
- **SC-020**: 정의 본문에 물리 스키마 이름이나 소스 접속 정보가 고정된 사례가 0건이다.
- **SC-021**: 워크스페이스가 하나 늘어날 때 정의 본문을 복제한 사례가 0건이다.
- **SC-022**: 확정된 정의 100%가 형상 관리 저장소의 커밋 식별자를 정의 버전으로 갖는다.
- **SC-023**: 실행 산출물 100%에 대해 어떤 정의 버전으로 만들어졌는지를 커밋 식별자로
  확인할 수 있다.
- **SC-024**: 형상 관리 저장소에서 평문 비밀 정보가 발견된 사례가 0건이다.
- **SC-025**: 저장소에 보관된 정의와 파라미터에서 환자 식별정보나 원천 데이터 값이 발견된
  사례가 0건이다.
- **SC-026**: 화면에서 이루어진 파라미터 값 변경 100%가 저장소 커밋으로 반영된다.
  커밋되지 않은 값으로 실행된 사례는 0건이다.
- **SC-027**: 저장소의 커밋 100%가 주체(사람의 확정 / 화면 변경 자동 반영)와 변경자,
  변경 시각을 갖는다.
- **SC-028**: 새 정의 버전 확정으로 워크스페이스의 고정 버전이 자동으로 바뀐 사례가 0건이다.
- **SC-029**: 고정 버전 변경 100%가 승격자와 승격 시각을 포함한 승격 이력을 갖는다.
- **SC-030**: 운영자가 워크스페이스의 고정 버전과 확정된 최신 버전의 차이를 1분 이내에
  확인할 수 있다.

## Assumptions

- 이 명세는 설계 시점의 저작 절차를 다룬다. 기능 004는 워크스페이스 유형별로 어떤
  단계가 어떤 순서로 있는지를 정하고, 이 명세는 그 각 단계 안에서 실제로 수행될 태스크와
  정의를 어떻게 만들어 확정하는지를 정한다. 기능 002는 확정된 정의를 실행하는 것을
  다룬다. 세 기능의 경계는 "무엇이 있는가 / 어떻게 만드는가 / 어떻게 돌리는가"다.
- 원문의 "SDM/CDM 모두 소스 커넥션으로부터 SDM으로 변환 대상이 되는 테이블 스키마를
  읽어서"는 두 유형 모두 소스 스키마를 읽는다는 뜻으로 해석했다. 목표 스키마는 유형에
  따라 다르며, 원문 후반의 "SDM/CDM 목표 스키마로 변환"이 그 점을 명시한다.
- SDM 유형의 목표 스키마는 기관이 관리하는 SDM 표준 스키마 정의 문서가 정한다. 이 문서는
  4개 구분(기본정보·진료정보·검사정보·건강정보) 아래 17개 테이블과 204개 컬럼을 정의하고,
  각 컬럼마다 자료형, 키 여부, 필수 여부(R/O)와 함께 KR CDI, KR Core, FHIR 대응을 담는다.
  버전 식별자를 가지며(예: `2026 SDM ver2.31`), 헌법 원칙 I에 따라 오프라인 반입 자산으로
  다룬다.
- 이로써 기능 001과 004의 SDM 서술 차이가 해소된다. 001의 "FHIR로 전송하기 위한
  워크스페이스"는 SDM 데이터의 용도를, 004의 "실명 기반 표준 데이터 모델로 변환"은 목표
  스키마를 가리킨다. FHIR는 목표 스키마가 아니라 SDM 각 컬럼에 대응하는 전송 표현이며,
  그 대응 관계가 SDM 스키마 정의 문서 안에 함께 들어 있다. 둘은 층위가 다를 뿐 충돌이
  아니다.
- CDM 유형의 목표 스키마는 OMOP CDM이 정한다. 기능 004 FR-009가 CDM 용어매핑의 대상
  표준을 OMOP으로 지정한 것과 일치한다.
- 정의는 본문과 파라미터로 나뉜다. 워크스페이스마다 정의를 복제하지 않기 위해서이고,
  물리 스키마 이름을 본문에서 빼는 것은 기능 009 FR-003(대상 스키마는 타깃 레지스트리
  조회로만 해석)과 같은 이유다. 본문에 스키마 이름이 박히면 레지스트리로 교체할 수 있게
  만든 의미가 사라진다.
- 정의 버전은 형상 관리 저장소의 커밋이다(FR-058). 이로써 기능 009가 생성 조건 기록의
  항목으로 요구하는 "변환 정의 버전"이 실체를 갖는다. 기능 010의 매핑 사전 버전, 용어집
  배포 버전과 함께 산출물의 재현 조건을 이룬다.
- 형상 관리 저장소는 헌법 원칙 I이 요구하는 대로 병원 내부망 안의 Gitea다(FR-063).
  적재·변환·워크플로 정의가 모두 같은 저장소의 버전 관리를 받는다.
- 파라미터 값에 비밀 정보가 섞일 수 있다는 점이 저장소 도입의 새 위험이다. 커밋은 지우기
  어려우므로 평문 보관 금지를 요구사항으로 못박았다(FR-055). 기능 001 FR-012가 화면과
  이력에 요구하던 마스킹이 저장소까지 확장된 것이다.
- 파라미터 값은 화면에서 바꿀 수 있고 그 변경이 자동으로 커밋된다(FR-065). 기능 001
  FR-009의 화면 변경 권한을 그대로 두면서 이력을 저장소 한 곳에 모으기 위한 선택이다.
  커밋 주체를 사람의 확정과 자동 반영으로 구분해 기록하므로(FR-066) 이력이 잦아져도 무엇이
  검토를 거친 변경인지 구분된다.
- 비밀 파라미터는 값이 아니라 참조만 커밋한다(FR-067). 자동 커밋을 허용하는 순간 비밀
  값이 실수로 저장소에 들어갈 경로가 생기고, 커밋은 지우기 어렵다. 값을 아예 저장소 밖에
  두는 것이 마스킹보다 확실하다.
- 워크스페이스는 정의 버전을 고정해 두고 승격으로만 옮긴다(FR-068~FR-070). 기능 010이
  참조 자산 바인딩에 적용한 원칙(FR-030, 새 버전 확정이 기존 바인딩을 자동으로 바꾸지
  않는다)과 같다. 한 워크스페이스를 위한 수정이 검증 없이 다른 워크스페이스의 실행에
  들어가는 것을 막는다.
- 승격을 강제하지는 않는다. 오래된 고정 버전에 머무르는 것은 운영자의 판단이며, 시스템은
  고정 버전과 최신 버전의 차이를 보여 주는 데까지만 관여한다(FR-073).
- 사용된 적이 있는 커밋은 저장소에서 제거하지 않는다. 제거하면 그 커밋으로 만들어진
  산출물의 생성 조건 기록이 가리킬 대상을 잃고, 재현성을 위해 버전을 남긴 의미가 사라진다.
- dry-run은 소스의 실제 데이터를 표본으로 읽는다. 이 선택은 값 수준 검증의 신뢰도를 얻는
  대신 dry-run 경로를 PHI 접촉 지점으로 만든다. 그래서 표본 크기 상한(FR-028), 소스
  커넥션 접근 통제 준수(FR-029), 표본 미보존(FR-030), 결과·실패 사유 요약의 마스킹
  (FR-034)을 함께 요구한다. 이 네 가지가 없으면 헌법 원칙 II·III을 만족하지 못한다.
- 운영자는 초안을 직접 편집할 수 있고, 편집한 정의는 dry-run을 다시 통과해야 확정된다.
  사람이 고친 내용이 검증 없이 실행 대상이 되면 dry-run 게이트가 우회되기 때문이다.
  편집 이력은 정의 버전과 별개로 누적되며, 확정 이력에 사람 편집 여부가 남는다. 편집분은
  AI 산출물이 아니므로 모델·프롬프트 버전만으로는 정의의 출처를 설명할 수 없고, 사람
  편집 여부가 함께 있어야 추적이 완결된다.
- "dlt 스크립트"와 "dbt 스크립트"는 구현 기술명이라 각각 "적재 정의", "변환 정의"로
  표현했다. 기능 004가 manifest에 "변환 정의 버전"을 기록하도록 한 것과 같은 용어다.
- AI 에이전트는 헌법 원칙 I에 따라 병원 내부망 안에서 동작한다. 저작 과정에서 외부
  네트워크로 나가는 경로는 없다.
- 헌법 원칙 IV는 "ETL은 AI 컴포넌트를 직접 호출해서는 안 된다"고 정한다. 저작은 ETL
  실행이 아니지만, 호출 경로를 이원화하면 통제 지점이 둘이 되므로 같은 경유 규칙을
  적용한다(FR-020).
- 헌법 원칙 V의 모델·프롬프트 버전 기록 의무를 저작 산출물에도 적용한다. 확정된 정의가
  어떤 모델에서 나왔는지 추적할 수 없으면 사후 검증이 불가능하기 때문이다(FR-019, FR-035).
- 스키마 조사가 메타데이터만 읽는다는 제약(FR-010)은 헌법 원칙 II에서 나온다. 저작은
  운영자 작업이고 landing·work 계층 접근과 별개 경로이므로, 조사 단계에서 환자 데이터
  행에 닿지 않아야 경계가 단순하게 유지된다.
- dry-run 결과 표시의 마스킹 요구(FR-028)는 헌법 원칙 III의 "웹에 노출하는 로그는 오류
  유형과 발생 위치만 추출한 요약본으로 제한"과 같은 규칙이다. 이 명세는 dry-run 결과를
  그 규칙의 적용 대상으로 명시하는 데 그친다.
- 자동 재시도 한도(FR-026)의 구체적인 횟수는 설정값이다. 이 명세는 한도가 존재해야 하고
  초과 시 사람에게 넘어가야 한다는 것만 정한다. 한도 없는 자동 수정은 비용과 시간이
  통제되지 않는다.
- dry-run의 시간 제한(FR-029)도 설정값이며, 이 명세는 제한이 존재하고 초과가 실패로
  처리된다는 것만 정한다.
- 목표 스키마 정의 자체(대상 표준의 테이블·컬럼 구조)는 헌법 원칙 I에 따라 오프라인
  반입 자산이다. 이 명세는 그 자산을 입력으로 쓰는 것만 다루고, 반입 절차는 범위 밖이다.
- 워크스페이스 생성·설정·소스 커넥션·롤은 기능 001이 소유한다. 대상 표준과 대상 표준
  버전은 001에서 생성 시 확정되고 변경 불가이므로, 목표 스키마도 워크스페이스 생애
  동안 고정이다. 다른 목표 스키마가 필요하면 새 워크스페이스를 만든다.
- 확정된 정의의 저장 위치와 형상 관리 방식은 이 명세의 범위 밖이다. 헌법 원칙 I에 따라
  병원 안의 형상 관리에 보관된다는 전제만 둔다.
- 검토 화면의 구성과 표시 방식(FR-036)은 어떤 정보가 함께 보여야 하는지만 정하고,
  화면 레이아웃은 범위 밖이다.
- 태스크 사이의 의존 관계는 프로세스 안의 순서로 표현한다. 프로세스를 가로지르는 임의의
  의존 그래프는 이번 범위에서 다루지 않는다. 유형이 정한 프로세스 순서가 곧 큰 단위의
  의존 관계다.
