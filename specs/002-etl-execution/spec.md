## User Scenarios & Testing *(mandatory)*

### User Story 1 - ETL 실행 요청 (Priority: P1)

운영자가 워크스페이스를 골라 ETL 실행을 요청한다. 정기 실행 주기를 기다리지 않고
지금 데이터를 가져와 변환해야 할 때 쓴다. 요청이 접수되면 실행 건이 하나 생기고,
그 실행 건은 어느 워크스페이스에 속하는지 기록된 채로 대기 상태에서 시작한다.

**Why this priority**: 실행을 걸 수 없으면 상태도 이력도 로그도 볼 대상이 없다.
이 스토리만 있어도 "필요할 때 수동으로 파이프라인을 돌린다"는 가치가 성립한다.

**Independent Test**: 운영자가 활성 워크스페이스에 실행을 요청하고, 실행 건이 생성되어
해당 워크스페이스에 귀속된 것이 확인되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 실행 권한이 있는 사용자가 활성 워크스페이스를 볼 때, **When** 실행을
   요청하면, **Then** 실행 건이 생성되고 대기 상태로 표시된다.
2. **Given** 실행 권한이 없는 사용자일 때, **When** 실행을 요청하면, **Then** 요청이
   거부된다.
3. **Given** 삭제 표시 상태인 워크스페이스일 때, **When** 실행을 요청하면, **Then**
   요청이 거부된다.
4. **Given** 실행 건이 생성되었을 때, **When** 그 실행 건을 조회하면, **Then** 소속
   워크스페이스 식별자, 요청자, 요청 시각이 확인된다.
5. **Given** 정기 실행 주기로 시작된 실행 건이 있을 때, **When** 이력을 조회하면,
   **Then** 수동 요청 건과 동일한 형식으로 표시되고 시작 경로(수동/정기)가 구분된다.

### User Story 2 - 실행 상태와 이력 조회 (Priority: P2)

사용자가 워크스페이스의 실행 이력을 열어 언제 무엇이 돌았고 어떻게 끝났는지 본다.
목록에는 실행 건마다 시작 시각, 종료 시각, 결과가 나온다. 진행 중인 건은 실행중으로만
표시되고 몇 퍼센트 진행됐는지는 보여주지 않는다. 화면에 들어가거나 새로고침할 때
현재 상태를 가져오며, 자동으로 계속 갱신하지 않는다.

**Why this priority**: 실행을 걸었으면 결과를 알아야 한다. 상태와 이력은 실패 진단의
입구이기도 하다.

**Independent Test**: 실행을 하나 걸고 이력 목록에 나타나는지, 상태가 대기→실행중→성공
또는 실패로 바뀌는지, 새로고침 시 최신 상태가 반영되는지 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 워크스페이스에 실행 이력이 있을 때, **When** 이력 목록을 조회하면,
   **Then** 각 실행 건의 시작 시각, 종료 시각, 결과가 최신순으로 표시된다.
2. **Given** 실행이 진행 중일 때, **When** 상태를 조회하면, **Then** 실행중으로만
   표시되고 진행률이나 완료 단계 수는 표시되지 않는다.
3. **Given** 화면을 열어 둔 상태에서 실행 상태가 바뀌었을 때, **When** 사용자가
   새로고침하면, **Then** 바뀐 상태가 반영된다.
4. **Given** 화면을 열어 둔 채 아무 조작도 하지 않을 때, **When** 시간이 지나면,
   **Then** 시스템이 자동으로 상태를 반복 조회하지 않는다.
5. **Given** 실행 건의 상태를 조회할 때, **When** 상태 값을 확인하면, **Then** 대기,
   실행중, 성공, 실패, 취소 다섯 가지 중 하나다.
6. **Given** 배정되지 않은 워크스페이스일 때, **When** 그 워크스페이스의 실행 이력
   조회를 시도하면, **Then** 접근이 거부된다.

### User Story 3 - 실패 원인 요약 확인 (Priority: P3)

실행이 실패했을 때 사용자가 어느 단계에서 무엇 때문에 멈췄는지 한눈에 본다. 실패
단계는 적재, 검증, 변환, AI 호출 중 하나로 표시되고, 그 옆에 한 줄짜리 오류 요약이
붙는다. 이 요약에는 원본 데이터 값이나 환자 식별정보가 들어가지 않는다.

**Why this priority**: 실패 자체는 상태로 알 수 있지만, 어느 단계인지 모르면 대응할
수 없다. 한 줄 요약만으로도 담당자를 정하고 다음 행동을 결정할 수 있다.

**Independent Test**: 적재 단계에서 실패하도록 만든 실행 건을 조회해 실패 단계가
"적재"로, 오류 요약이 한 줄로 표시되고 그 안에 원본 데이터 값이 없는 것을 확인하면
검증 완료.

**Acceptance Scenarios**:

1. **Given** 실행이 실패했을 때, **When** 실행 건 상세를 조회하면, **Then** 실패 단계가
   적재, 검증, 변환, AI 호출 중 하나로 표시된다.
2. **Given** 실행이 실패했을 때, **When** 실행 건 상세를 조회하면, **Then** 한 줄짜리
   오류 요약이 함께 표시된다.
3. **Given** 검증 단계에서 기대에 어긋난 실제 값 때문에 실패했을 때, **When** 오류
   요약을 확인하면, **Then** 어긋난 실제 값이 요약에 포함되지 않는다.
4. **Given** 적재 단계에서 특정 레코드 때문에 실패했을 때, **When** 오류 요약을
   확인하면, **Then** 해당 레코드의 원본 값이 요약에 포함되지 않는다.
5. **Given** 실행이 성공했을 때, **When** 실행 건 상세를 조회하면, **Then** 실패 단계와
   오류 요약이 표시되지 않는다.
6. **Given** AI 호출 단계에서 실패했을 때, **When** 실행 건 상세를 조회하면, **Then**
   호출에 사용된 모델 버전과 프롬프트 버전이 함께 확인된다.

### User Story 4 - 실행 취소와 깨끗한 재적재 (Priority: P4)

사용자가 잘못 건 실행이나 오래 붙잡고 있는 실행을 멈춘다. 취소된 실행이 중간까지 적재한
데이터는 그 자리에 남고, 다음 실행이 시작될 때 정리된다. 정리하고 다시 적재하는 방식은
워크스페이스 유형에 따라 다르며, ETL 두 유형에만 적용된다. 참조 자산 관리 두 유형은 환자
데이터를 적재하지 않으므로 이 분기의 대상이 아니다.

**SDM ETL**은 환자 한 사람 단위로 변환하므로 한 실행이 다루는 데이터가 적어서 처음부터
다시 하는 비용이 크지 않다. 그래서 중단 적재분을 전부 지우고 처음부터 다시 적재한다.
**OMOP CDM ETL**은 병원 EHR 전체를 다뤄 데이터가 커서 처음부터 다시 하면 앞 단계를
반복하는 데만 오랜 시간이 든다. 그래서 운영자가 어느 단계부터 다시 할지 지정할 수 있고,
지정한 단계 이후의 데이터만 지우고 그 단계부터 다시 적재한다. 지정한 단계 이전의 산출물은
그대로 쓴다.

어느 쪽이든 결과는 같다. 반쪽짜리 데이터가 남지 않는다.

**Why this priority**: 워크스페이스 안에서는 한 번에 한 건만 실행되므로, 멈추지 못하는
실행 하나가 대기열 전체를 막는다. 그리고 중단이 남긴 부분 적재를 정리하지 못하면 다음
실행의 결과를 믿을 수 없다. CDM에서 중간 단계 지정이 필요한 이유는 별개다. 규모가 큰
워크스페이스에서 매번 처음부터 다시 하면 재실행 자체가 실용적이지 않다.

**Independent Test**: SDM ETL 워크스페이스에서 실행 중인 건을 취소하고 새 실행을 걸어 취소된
적재분이 사라지고 처음부터 다시 쌓이는 것을 확인하고, OMOP CDM ETL 워크스페이스에서 취소 후
운영자가 중간 단계를 지정해 재실행했을 때 그 단계 이전 산출물은 남고 이후만 다시 적재되는
것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 실행이 진행 중이고 실행 권한이 있을 때, **When** 취소를 요청하면,
   **Then** 그 실행 건이 취소 상태로 종료된다.
2. **Given** 실행이 대기열에서 차례를 기다릴 때, **When** 취소를 요청하면, **Then**
   대기열에서 제거되고 취소 상태가 된다.
3. **Given** 실행이 이미 성공 또는 실패로 종료되었을 때, **When** 취소를 요청하면,
   **Then** 요청이 거부되고 최종 상태가 그대로 유지된다.
4. **Given** 실행이 취소된 직후일 때, **When** 데이터를 확인하면, **Then** 취소 시점까지
   적재된 데이터가 아직 남아 있다.
5. **Given** SDM ETL 워크스페이스에 취소된 실행의 적재분이 있을 때, **When** 다음 실행이
   시작되면, **Then** 그 적재분이 먼저 삭제되고 처음부터 다시 적재된다.
6. **Given** SDM ETL 워크스페이스일 때, **When** 사용자가 시작 단계를 지정해 재실행하려 하면,
   **Then** 지정이 받아들여지지 않는다.
7. **Given** 중단된 실행이 여러 건 누적된 SDM ETL 워크스페이스일 때, **When** 다음 실행이
   시작되면, **Then** 누적된 모든 중단 실행의 적재분이 삭제된다.
8. **Given** 실행이 실패로 종료되었을 때, **When** 다음 실행이 시작되면, **Then**
   취소된 경우와 동일하게 실패 실행의 적재분이 정리된다.
9. **Given** OMOP CDM ETL 워크스페이스에 중단된 실행이 있을 때, **When** 운영자가 재실행을
   준비하면, **Then** 시작 단계를 지정할 수 있다.
10. **Given** 운영자 롤이 없는 사용자일 때, **When** 시작 단계를 지정하려 하면, **Then**
    지정이 거부된다.
11. **Given** 중단된 실행에서 완료되지 않은 단계를 시작 단계로 지정할 때, **When** 재실행을
    요청하면, **Then** 요청이 거부된다.
12. **Given** CDM 재실행에 시작 단계를 지정하지 않았을 때, **When** 실행이 시작되면,
    **Then** 처음부터 다시 적재된다.
13. **Given** 운영자가 시작 단계를 지정했을 때, **When** 실행이 시작되면, **Then** 그
    단계 이후의 중단 적재분이 먼저 삭제되고 그 단계부터 다시 적재된다.
14. **Given** 운영자가 시작 단계를 지정했을 때, **When** 실행이 끝난 뒤 확인하면,
    **Then** 지정한 단계 이전 단계의 산출물이 삭제되지 않고 그대로 쓰였다.
15. **Given** 재사용된 단계 산출물이 있을 때, **When** 이후 다른 실행이 중단 실행을
    정리하면, **Then** 재사용된 산출물은 삭제 대상이 되지 않는다.
16. **Given** CDM에 중단된 실행이 여러 건 누적되었을 때, **When** 중간 단계를 지정해
    재실행하면, **Then** 가장 최근 중단 실행의 산출물이 재사용되고 그보다 앞선 중단
    실행의 적재분은 삭제된다.
17. **Given** 중간 단계부터 재실행이 완료되었을 때, **When** 그 실행 건의 기록을
    조회하면, **Then** 지정된 시작 단계, 재사용된 단계와 그 산출물이 만들어진 실행 건,
    삭제된 범위가 확인된다.
18. **Given** 중간 단계부터 재실행해 CDM 스냅샷이 만들어졌을 때, **When** manifest를
    확인하면, **Then** 각 단계가 어느 실행 건에서 어떤 버전으로 수행됐는지가 확인된다.
19. **Given** 재사용하려는 단계의 버전을 확인할 수 없을 때, **When** 중간 단계를 지정해
    재실행하려 하면, **Then** 요청이 거부된다.
20. **Given** 다음 실행이 중단 적재분을 정리했을 때, **When** 그 실행 건의 기록을
    조회하면, **Then** 삭제 대상이 있었는지와 정리 결과가 확인된다.

### User Story 5 - 운영자의 실패 로그 조회 (Priority: P5)

실패 단계와 한 줄 요약만으로 원인을 못 잡을 때, 운영자가 단계별 실행 로그를 연다.
로그는 실패한 실행 건에 대해서만, 운영자 롤을 가진 사람에게만 열린다. 운영자가 아닌
사용자에게는 로그 조회 진입점 자체가 없고, 실패 단계와 한 줄 요약이 진단 수단의
전부다. 화면에 뜨는 로그는 정형 식별자 패턴이 마스킹된 상태다.

**Why this priority**: 가장 민감한 데이터를 다루는 심층 진단 수단이라, 앞선 통제
장치가 모두 갖춰진 뒤에 마지막으로 연다. 앞의 네 스토리 없이는 도달할 경로도 없다.

**Independent Test**: 실패한 실행 건에서 운영자가 로그를 조회해 단계별 항목이 보이고
정형 식별자 패턴이 마스킹된 것을 확인하고, 같은 화면에서 비운영자에게는 진입점이
보이지 않는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 실행이 실패했고 운영자 롤이 있을 때, **When** 로그 조회를 요청하면,
   **Then** 실패한 단계의 로그가 표시된다.
2. **Given** 실행이 성공했을 때, **When** 운영자가 로그 조회를 시도하면, **Then**
   로그가 노출되지 않는다.
3. **Given** 운영자 롤이 없는 사용자가 실패한 실행 건을 볼 때, **When** 상세 화면을
   조회하면, **Then** 로그 조회 진입점이 표시되지 않는다.
4. **Given** 운영자 롤이 없는 사용자일 때, **When** 로그 조회를 직접 시도하면,
   **Then** 요청이 거부된다.
5. **Given** 로그에 주민등록번호, 환자번호, 전화번호 형태의 값이 포함되어 있을 때,
   **When** 로그를 조회하면, **Then** 해당 값들이 마스킹되어 표시된다.
6. **Given** 로그 조회가 일어났을 때, **When** 감사 이력을 확인하면, **Then** 누가
   어느 실행 건의 로그를 언제 열었는지 기록되어 있다.
7. **Given** 로그가 매우 클 때, **When** 로그를 조회하면, **Then** 정해진 상한까지만
   전달되고 잘렸다는 사실이 사용자에게 안내된다.

### Edge Cases

- 실행 요청 직후 워크스페이스가 삭제 표시되면 어떻게 되는가? 진행 중인 실행은 완료까지
  유지되고, 완료 후 새 실행 요청만 거부된다.
- 실행이 오래 걸려 상태가 실행중에 머물러 있으면 사용자는 무엇을 보는가? 진행률 없이
  실행중과 시작 이후 경과 시간만 확인할 수 있다.
- 오케스트레이션 계층에서 실행 기록을 더 이상 조회할 수 없으면 어떻게 되는가? 실행
  건은 상태 불명으로 표시되고, 마지막으로 확인된 상태와 그 시각이 함께 안내된다.
- 취소 요청과 실행 완료가 거의 동시에 일어나면 어떻게 되는가? 이미 종료된 실행은
  취소되지 않고 최종 상태가 유지되며, 취소 요청은 실패로 응답된다.
- 소스 커넥션 대상 시스템이 응답하지 않으면 어떻게 되는가? 적재 단계 실패로 기록된다.
- 실패 로그가 제어 평면이 감당할 수 없을 만큼 크면 어떻게 되는가? 로그 원본은 저장소에
  남고 화면에는 상한까지만 전달된다.
- 워크스페이스가 정리(cleanup)된 뒤 실행 이력을 조회하면 어떻게 되는가? 실행 이력과
  결과는 남아 있고, 산출물과 로그 원본은 조회되지 않는다.
- 같은 실행 건에 대해 여러 사용자가 동시에 로그를 조회하면 어떻게 되는가? 각 조회가
  개별 감사 기록으로 남는다.
- 앞선 실행이 오래 끝나지 않는 동안 정기 주기가 반복 도래하면 대기열이 무한히 쌓이는가?
  대기열에 정기 주기 건이 이미 있으면 추가 정기 건은 적재하지 않고 건너뛴다.
- 대기 중인 실행이 있는 상태에서 워크스페이스가 삭제 표시되면 어떻게 되는가? 대기 건은
  취소 처리되고, 진행 중인 건만 완료까지 유지된다.
- 중단된 실행의 적재분을 정리하는 도중에 그 실행마저 중단되면 어떻게 되는가? 정리되지
  않은 중단 실행 목록에 남아, 그다음 실행이 두 건의 적재분을 함께 삭제한다.
- CDM에서 중간 단계부터 재실행하는 도중에 다시 취소되면 어떻게 되는가? 그 재개 실행이
  새로운 중단 실행이 되고, 그 실행에서 완료된 단계까지를 기준으로 다시 시작 단계를 지정할
  수 있다. 재사용해서 이어받은 앞 단계 산출물은 이미 재개 실행 건에 귀속되어 있으므로
  그대로 남는다.
- 재사용하려던 앞 단계 산출물이 이미 정리되어 없으면 어떻게 되는가? 그 단계를 시작 단계로
  지정할 수 없다. 완료된 단계의 산출물이 남아 있는 지점까지만 지정할 수 있고, 남은 것이
  없으면 처음부터 다시 적재한다.
- 중단 이후 원천 데이터가 바뀌었는데 중간 단계부터 재실행하면 어떻게 되는가? 시스템은
  재사용하는 산출물이 원천의 현재 상태를 반영하는지 판단하지 않는다. 중간 재개를 지정한다는
  것은 그 산출물을 그대로 쓰겠다는 운영자의 판단이며, 시스템은 그 산출물이 언제 만들어졌는지를
  기록해 판단 근거를 남긴다.
- 중간 단계부터 재실행한 CDM 스냅샷은 여러 실행 건의 산출물이 섞인 것인데 원본 자산으로
  다뤄도 되는가? 그렇다. 단계마다 어느 실행 건에서 어떤 버전으로 만들어졌는지가 manifest에
  기록되므로 생성 조건이 완전히 남는다.
- SDM ETL 워크스페이스에서 시작 단계를 지정하려 하면 어떻게 되는가? 지정이 받아들여지지 않고
  처음부터 다시 적재된다.
- 워크스페이스가 정리(cleanup)될 때까지 다음 실행이 한 번도 없었다면 중단 실행의
  적재분은 어떻게 되는가? 워크스페이스 정리 과정에서 데이터 계층과 함께 제거된다.
- 실행 중인 건을 여러 사용자가 동시에 취소 요청하면 어떻게 되는가? 첫 요청만 반영되고
  이후 요청은 이미 종료된 실행에 대한 요청으로 거부된다.

## Requirements *(mandatory)*

### Functional Requirements

**트리거**

- **FR-001**: 사용자는 워크스페이스 단위로 ETL flow 실행을 요청할 수 있어야 한다.
- **FR-002**: 시스템은 해당 워크스페이스에 실행 권한을 가진 사용자의 요청만 받아들여야
  한다.
- **FR-003**: 시스템은 삭제 표시 상태인 워크스페이스에 대한 신규 실행 요청을 거부해야
  한다.
- **FR-004**: 시스템은 모든 실행 건에 소속 워크스페이스 식별자를 예외 없이 부여해야
  하며, 워크스페이스 식별자가 없는 실행 건이 존재해서는 안 된다.
- **FR-005**: 시스템은 각 실행 건에 대해 요청자, 요청 시각, 시작 경로(수동 요청 또는
  정기 주기)를 기록해야 한다.
- **FR-006**: 시스템은 같은 워크스페이스에 진행 중인 실행이 있을 때 새 실행 요청을
  대기열에 적재해야 하며, 앞선 실행이 종료된 뒤 순차적으로 실행해야 한다. 한 워크스페이스
  안에서 두 건 이상이 동시에 실행되어서는 안 된다.
- **FR-049**: 시스템은 SDM ETL 워크스페이스의 두 실행 단위 — 환자 단위 변환 파이프라인
  (기능 004·012)과 집합 단위 확정 실행(기능 012) — 에 FR-006의 순차 실행 규칙을 함께
  적용해야 한다. 한쪽이 도는 동안 다른 쪽은 대기열에서 기다린다.
- **FR-050**: 시스템은 확정 실행이 사람 검수 대기로 길게 멈출 수 있음을 고려해, 대기 중인
  환자 단위 변환 요청에 대기 사유를 표시해야 한다.
- **FR-028**: 시스템은 대기열에 있는 실행 건을 대기 상태로 표시하고, 대기 순번을 함께
  제공해야 한다.
- **FR-029**: 시스템은 정기 실행 주기가 도래한 경우에도 진행 중인 실행이 있으면 대기열에
  적재해야 한다. 다만 같은 워크스페이스의 대기열에 이미 정기 주기 건이 있으면 추가
  정기 건을 적재하지 않고 건너뛰어야 하며, 건너뛴 사실을 기록해야 한다.
- **FR-030**: 시스템은 워크스페이스가 삭제 표시되면 그 워크스페이스의 대기 중인 실행
  건을 취소 처리해야 한다.

**상태 조회**

- **FR-007**: 시스템은 실행 건의 상태를 대기, 실행중, 성공, 실패, 취소 다섯 가지 중
  하나로 표시해야 한다.
- **FR-008**: 시스템은 진행률, 완료 단계 수, 처리 건수 등 진행 정도를 나타내는 값을
  표시해서는 안 된다.
- **FR-009**: 시스템은 화면 진입과 사용자의 새로고침 시점에 상태를 조회해야 하며,
  주기적 자동 폴링을 수행해서는 안 된다.
- **FR-010**: 시스템은 오케스트레이션 계층에서 실행 기록을 조회할 수 없는 경우 해당
  실행 건을 상태 불명으로 표시하고 마지막 확인 상태와 시각을 함께 제공해야 한다.

**실패 상세**

- **FR-011**: 시스템은 실패한 실행 건에 대해 실패 단계를 적재, 검증, 변환, AI 호출 중
  하나로 표시해야 한다.
- **FR-012**: 시스템은 실패한 실행 건에 대해 한 줄 분량의 오류 요약을 제공해야 한다.
- **FR-013**: 시스템은 오류 요약에 원본 데이터 값, 실패 레코드 내용, 검증에서 어긋난
  실제 값, 환자 식별정보가 포함되지 않도록 해야 한다. 요약은 오류 유형과 발생 위치만을
  담아야 한다.
- **FR-014**: 시스템은 AI 호출 단계와 관련된 실행 기록에 대해 사용된 모델 버전과
  프롬프트 버전을 함께 조회할 수 있게 해야 한다.

**로그 조회**

- **FR-015**: 시스템은 실행 단계별 로그를 조회할 수 있게 해야 한다.
- **FR-016**: 시스템은 실행 로그를 실패한 실행 건에 대해서만, 운영자 롤 보유자에게만
  노출해야 한다. 성공한 실행 건의 로그와, 운영자 롤이 없는 사용자에 대한 로그는 어떤
  형태로도 노출해서는 안 된다. 운영자 롤이 없는 사용자에게는 로그 조회 진입점 자체를
  제공하지 않아야 한다.
- **FR-017**: 시스템은 화면에 노출하는 로그에서 주민등록번호, 환자번호, 전화번호를
  포함한 정형 식별자 패턴을 마스킹해야 한다.
- **FR-018**: 시스템은 로그 조회에 대해 조회자, 대상 실행 건, 조회 시각을 감사 이력으로
  기록해야 한다.
- **FR-019**: 시스템은 화면에 전달하는 로그 분량에 상한을 두어야 하며, 상한을 넘어
  잘린 경우 그 사실을 사용자에게 알려야 한다. 대용량 로그 원본이 제어 평면을 통과해서는
  안 된다.

**이력**

- **FR-020**: 사용자는 워크스페이스별 실행 건 목록을 조회할 수 있어야 한다.
- **FR-021**: 시스템은 각 실행 건에 대해 시작 시각, 종료 시각, 최종 결과를 제공해야
  한다.
- **FR-022**: 시스템은 실행 건 목록을 최신순으로 정렬해 제공해야 하며, 상태별 필터링을
  지원해야 한다.
- **FR-023**: 시스템은 배정되지 않은 워크스페이스의 실행 이력에 대한 접근을 거부해야
  한다.
- **FR-024**: 시스템은 실행 건 식별자로 해당 실행이 만든 산출물의 저장 위치를 추적할 수
  있게 해야 한다.
- **FR-025**: 시스템은 워크스페이스가 정리된 뒤에도 실행 이력과 결과를 보존해야 한다.

**취소**

- **FR-026**: 사용자는 대기 중이거나 실행 중인 실행 건을 취소할 수 있어야 한다. 취소는
  해당 워크스페이스에 실행 권한을 가진 사용자만 요청할 수 있다.
- **FR-031**: 시스템은 이미 종료된(성공, 실패, 취소) 실행 건에 대한 취소 요청을 거부하고
  최종 상태를 유지해야 한다.
- **FR-032**: 시스템은 취소 시점에 이미 적재된 데이터를 즉시 삭제해서는 안 된다. 중단된
  실행이 남긴 데이터는 그 자리에 둔 채 실행 건만 취소 상태로 종료한다.
- **FR-034**: 시스템은 적재된 데이터가 어느 실행 건의 어느 단계에서 비롯되었는지 식별할
  수 있어야 한다. 중단 적재분의 삭제 범위와 재사용 범위는 이 귀속 정보로 결정된다.
- **FR-035**: 시스템은 중단 실행 적재분의 삭제와 재적재 결과를 해당 실행 건의 기록에
  남겨야 하며, 삭제 대상이 있었는지 여부를 확인할 수 있어야 한다.

**재실행 — SDM ETL 워크스페이스**

- **FR-033**: 시스템은 SDM ETL 워크스페이스에서 중단된 실행(취소 또는 실패로 종료된 실행)
  이후 시작되는 다음 실행이, 아직 정리되지 않은 모든 중단 실행의 적재분을 먼저 삭제한 뒤
  처음부터 다시 적재하도록 해야 한다.
- **FR-036**: 시스템은 SDM ETL 워크스페이스에서 시작 단계를 지정한 재실행을 제공해서는 안 된다.

**재실행 — OMOP CDM ETL 워크스페이스**

- **FR-037**: 시스템은 OMOP CDM ETL 워크스페이스에서 중단된 실행 이후 재실행할 때 시작 단계를
  지정할 수 있게 해야 한다.
- **FR-038**: 시스템은 시작 단계를 지정할 수 있는 사람을 운영자 롤 보유자로 한정해야 한다.
- **FR-039**: 시스템은 지정할 수 있는 시작 단계를 중단된 실행에서 완료된 단계의 바로 다음
  단계까지로 한정해야 하며, 완료되지 않은 단계를 시작 단계로 지정한 요청을 거부해야 한다.
- **FR-040**: 시스템은 시작 단계가 지정되지 않은 OMOP CDM ETL 재실행을 처음부터 다시 적재하는
  것으로 처리해야 한다.
- **FR-041**: 시스템은 지정된 시작 단계 이후의 중단 적재분을 먼저 삭제한 뒤 그 단계부터
  다시 적재해야 한다.
- **FR-042**: 시스템은 지정된 시작 단계 이전 단계의 산출물을 삭제하지 않고 그대로 재사용해야
  한다.
- **FR-043**: 시스템은 재사용된 단계 산출물의 귀속을 재개 실행 건으로 이관해야 하며,
  이관된 산출물이 이후 중단 실행 정리의 삭제 대상이 되어서는 안 된다.
- **FR-044**: 시스템은 중단된 실행이 여러 건 누적된 경우 가장 최근 중단 실행의 산출물을
  재사용 대상으로 삼고, 그보다 앞선 중단 실행의 적재분은 삭제해야 한다.
- **FR-045**: 시스템은 재개 실행 건의 기록에 지정된 시작 단계, 재사용된 단계와 그 산출물이
  만들어진 실행 건, 삭제된 범위를 남겨야 한다.
- **FR-046**: 시스템은 OMOP CDM 스냅샷의 manifest에 각 단계가 어느 실행 건에서 어떤 버전으로
  수행됐는지를 기록해야 한다.
- **FR-047**: 시스템은 재사용하려는 단계의 버전을 확인할 수 없으면 시작 단계를 지정한
  재실행을 거부해야 한다.
- **FR-048**: 시스템은 재사용되는 단계 산출물이 만들어진 시각을 재개 실행 건의 기록에
  남겨야 한다. 시스템은 그 산출물이 원천의 현재 상태를 반영하는지 판단하지 않는다.

**가명처리 단계의 실패 표시**

- **FR-051**: 시스템은 기능 012의 가명처리 단계 실패를 이 스펙의 실패 단계 4종
  (적재·검증·변환·AI 호출)에 매핑해 표시해야 한다. 정형 컬럼 처리 실패는 `변환`,
  LLM 비식별화 실패는 `AI 호출`이다. 가명처리를 별도 실패 단계로 추가해서는 안 된다.
- **FR-052**: 시스템은 확정 게이트(자유서식 검수, 재식별 위험 점검)의 결과를 이 스펙의
  실행 상태·실패 상세로 표시하지 않아야 한다. 그 결과는 기능 012의 확정 기록이 담는다.

**전 기능 공통**

- **FR-027**: 시스템은 실행 요청과 취소에 대해 실행자와 시각을 감사 이력으로 기록해야
  한다.

### Key Entities

- **실행 건(flow run)**: ETL flow 한 번의 실행. 고유 식별자, 소속 워크스페이스 식별자,
  상태, 시작 경로(수동/정기), 요청자, 요청 시각, 시작 시각, 종료 시각을 갖는다.
- **실행 상태**: 대기, 실행중, 성공, 실패, 취소 중 하나. 진행 정도를 나타내는 값은
  포함하지 않는다. 오케스트레이션 계층 조회 실패 시 상태 불명이 별도로 표시된다.
- **대기열**: 워크스페이스별로 하나. 진행 중인 실행이 있을 때 들어온 요청이 순서대로
  쌓이고 앞선 실행 종료 후 하나씩 실행된다. 각 대기 건은 대기 순번을 갖는다.
- **중단 실행**: 취소 또는 실패로 종료되어 적재분이 아직 정리되지 않은 실행 건. 같은
  워크스페이스의 다음 실행이 시작될 때 정리 대상이 된다.
- **적재 귀속 정보**: 적재된 데이터가 어느 실행 건의 어느 단계에서 비롯되었는지를 나타내는
  정보. 중단 실행 적재분의 삭제 범위와 중간 재개 시 재사용 범위를 결정하는 근거다. 재사용된
  산출물의 귀속은 재개 실행 건으로 이관된다.
- **시작 단계 지정**: CDM 재실행에서 운영자가 고르는 재적재 시작 지점. 중단된 실행에서
  완료된 단계의 바로 다음 단계까지 고를 수 있다. 지정하지 않으면 처음부터다.
- **실행 단계**: 적재, 검증, 변환, AI 호출. 실패한 실행 건은 이 중 하나를 실패 단계로
  갖는다.
- **오류 요약**: 실패한 실행 건에 붙는 한 줄 설명. 오류 유형과 발생 위치만 담고 원본
  데이터 값을 담지 않는다.
- **실행 로그**: 단계별로 남는 실행 기록. 화면 노출본은 마스킹·요약·분량 상한이 적용된
  형태이며, 원본은 저장소에 남는다.
- **산출물 위치**: 실행 건이 만든 데이터의 저장 경로. 워크스페이스, 계층, 실행 일자,
  실행 건 식별자로 결정된다.
- **감사 이력**: 실행 요청, 취소, 로그 조회에 대한 기록. 실행자, 대상, 시각을 포함한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 워크스페이스를 열어 ETL 실행을 요청하기까지 30초 이내가 걸린다.
- **SC-002**: 워크스페이스 식별자가 없는 실행 건이 생성된 사례가 0건이다.
- **SC-003**: 사용자가 실행 이력 화면에 진입한 시점 기준으로 최신 상태가 표시되며,
  화면 진입 후 자동 반복 조회가 발생한 사례가 0건이다.
- **SC-004**: 실패한 실행 건에 대해 사용자가 실패 단계와 오류 요약을 확인하기까지
  화면 이동 2회 이내가 걸린다.
- **SC-005**: 화면에 노출된 오류 요약과 로그에서 환자 식별정보나 원본 데이터 값이
  발견된 사례가 0건이다.
- **SC-006**: 로그 조회의 100%가 조회자와 시각과 함께 감사 이력에 남는다.
- **SC-007**: 성공한 실행 건의 로그가 의도치 않게 노출된 사례가 0건이다.
- **SC-008**: 실행 이력 목록이 100건 기준으로 사용자가 기다린다고 느끼지 않는 시간
  안에 표시된다.
- **SC-009**: 실행 건 식별자만으로 해당 실행의 산출물 위치를 찾는 데 1분 이내가 걸린다.
- **SC-010**: 실패한 실행 건의 90% 이상에서 운영자가 로그 원본을 열지 않고 실패 단계와
  오류 요약만으로 다음 조치를 결정할 수 있다.
- **SC-011**: 한 워크스페이스에서 두 건 이상의 실행이 동시에 진행된 사례가 0건이다.
- **SC-012**: 앞선 실행이 종료된 뒤 대기열의 다음 건이 시작되기까지 1분을 넘지 않는다.
- **SC-013**: 중단된 실행이 남긴 적재분이 다음 실행 완료 후에도 남아 있는 사례가 0건이다.
- **SC-016**: SDM ETL 워크스페이스에서 시작 단계를 지정한 재실행이 수행된 사례가 0건이다.
- **SC-017**: CDM 중간 재개에서 지정한 시작 단계 이전 단계의 산출물이 삭제된 사례가 0건이다.
- **SC-018**: CDM 중간 재개 후 지정한 시작 단계 이후의 중단 적재분이 남아 있는 사례가
  0건이다.
- **SC-019**: 재사용된 단계 산출물이 이후의 중단 실행 정리에서 삭제된 사례가 0건이다.
- **SC-020**: 중간 재개로 만들어진 CDM 스냅샷 중 manifest에 단계별 출처 실행 건이나 버전이
  누락된 사례가 0건이다.
- **SC-021**: 운영자 롤이 없는 사용자가 시작 단계 지정에 성공한 사례가 0건이다.
- **SC-022**: 중단된 실행에서 완료되지 않은 단계가 시작 단계로 받아들여진 사례가 0건이다.
- **SC-023**: 중간 단계부터 재실행한 OMOP CDM ETL 실행이 같은 지점까지 처음부터 다시 수행하는
  경우보다 짧은 시간에 완료된다.
- **SC-024**: SDM ETL 워크스페이스에서 환자 단위 변환과 집합 확정 실행이 동시에 수행된
  사례가 0건이다.
- **SC-025**: 대기 중인 실행 100%가 대기 사유를 함께 표시한다.
- **SC-026**: 가명처리 단계 실패가 실패 단계 4종(적재·검증·변환·AI 호출) 밖의 값으로
  표시된 사례가 0건이다.
- **SC-027**: 확정 게이트 결과가 실행 상태나 실패 상세로 표시된 사례가 0건이다.
- **SC-014**: 운영자 롤이 없는 사용자에게 실행 로그가 노출된 사례가 0건이다.
- **SC-015**: 사용자가 진행 중인 실행을 취소 요청한 뒤 취소 상태로 반영되기까지
  1분을 넘지 않는다.

## Assumptions

- 워크스페이스마다 실행 대상 ETL flow는 하나다. 여러 종류의 flow 선택은 이번 범위 밖이다.
- 실행을 요청할 수 있는 사람은 해당 워크스페이스에 실행 권한을 가진 롤 보유자로
  한정한다. 롤과 사용자 계정은 통합 인증·권한 서비스가 소유하며 워크스페이스 배정은
  기능 001에서 관리한다.
- 실패한 실행의 자동 재시도는 이번 범위 밖이다. 재실행이 필요하면 사용자가 새 실행을
  요청한다.
- 재실행 방식은 워크스페이스 유형에 따라 다르다. SDM ETL은 중단 적재분을 전부 지우고
  처음부터 다시 적재한다. OMOP CDM ETL은 운영자가 시작 단계를 지정할 수 있고, 지정한 단계
  이후만 지우고 그 단계부터 다시 적재한다. 이전 버전의 이 명세는 부분 재개를 전면 금지했으나 CDM에 한해
  허용하는 것으로 바꿨다.
- 유형에 따라 나눈 이유는 데이터 규모다. ~~SDM은 요청 단위로 확정된 코호트만 다뤄~~
  **정정(2026-09-01, 기능 004 후속 지시 5)**: SDM ETL은 **환자 한 사람 단위**의 변환
  요청만 받으므로 한 실행이 다루는 데이터가 적어 처음부터 다시 하는 비용이 크지 않고,
  매번 같은 방식으로 처리하는 편이 규칙이 단순하다. OMOP CDM ETL은 병원 EHR 전체를
  다루므로 앞 단계를 반복하는 데만 오랜 시간이 들어 재실행 자체가 실용적이지 않게 된다.
- OMOP CDM ETL의 중간 재개에서 시스템은 재사용하는 산출물이 원천의 현재 상태를 반영하는지 판단하지
  않는다. 중간 재개를 지정한다는 것은 그 산출물을 그대로 쓰겠다는 운영자의 판단이며,
  시스템은 산출물이 만들어진 시각을 기록해 판단의 근거를 남긴다(FR-048). 이것이 시작 단계
  지정을 운영자 롤로 한정한 이유이기도 하다.
- 중간 재개로 만들어진 OMOP CDM 스냅샷은 여러 실행 건의 산출물이 섞인 것이다. 기능 004는 CDM
  스냅샷을 재생성할 수 없는 원본 자산으로 다루고 manifest에 생성 조건을 기록하도록 한다.
  섞인 스냅샷도 단계마다 출처 실행 건과 버전이 기록되면 생성 조건이 완전히 남으므로 같은
  기준을 만족한다(FR-046). 재사용 단계의 버전을 확인할 수 없으면 중간 재개를 거부해
  기록되지 않는 조건이 생기지 않게 한다(FR-047).
- 재사용된 산출물의 귀속을 재개 실행 건으로 옮기는 것(FR-043)은 이후의 중단 실행 정리가
  사용 중인 데이터를 지우는 것을 막기 위해서다. 귀속을 옮기지 않으면 원래 실행 건이 계속
  미정리 중단 실행으로 남아 다음 정리에서 삭제 대상이 된다.
- 취소와 실패를 모두 "중단된 실행"으로 보고 동일하게 처리한다. 둘 다 완료되지 못한
  실행이 부분 적재를 남긴다는 점에서 같은 문제이고, 실패 건만 정리하지 않으면 고아
  데이터가 남기 때문이다.
- 중단 실행 적재분의 삭제는 다음 실행이 시작될 때 수행한다. 취소 시점에 즉시 되돌리지
  않으므로, 중단 직후 다음 실행 전까지는 부분 적재 데이터가 존재하는 구간이 있다.
- 운영자 롤이 없는 사용자의 진단 수단은 실패 단계와 한 줄 오류 요약이 전부다. 로그는
  요약본 형태로도 제공하지 않는다.
- 대기열은 워크스페이스별로 하나이며 우선순위 개념이 없다. 수동 요청과 정기 주기 건이
  같은 대기열에 도착 순서대로 쌓인다.
- 실행 실패에 대한 알림(메일, 메신저 등) 발송은 이번 범위 밖이다. 사용자는 화면 조회로
  결과를 확인한다.
- 실행 상태와 로그는 상태 전이 시점에만 갱신되므로, 화면 진입과 새로고침 시 조회만으로
  충분하다. 실시간 스트리밍이나 주기적 폴링은 필요하지 않다.
- 진행률을 표시하지 않는 것은 의도된 결정이다. 단계별 완료 비율을 산출하려면
  오케스트레이션 계층에 추가 조회 부하가 걸리고, 사용자의 의사결정에는 상태만으로
  충분하다.
- ETL flow는 AI 컴포넌트를 직접 호출하지 않고 Backend API를 경유한다. 따라서 "AI 호출"
  실패 단계는 Backend API 호출 실패를 뜻하며, 모델 서빙 계층의 내부 오류는 그 API가
  변환한 형태로 전달된다.
- 실행 로그 원본은 저장소에 보관되고 제어 평면은 참조와 요약만 다룬다. 화면은 원본
  전체를 내려받지 않는다.
- 실행 이력은 워크스페이스가 정리된 뒤에도 보존된다(기능 001의 정리 대상이 아니다).
  다만 산출물과 로그 원본은 정리 대상이므로 조회되지 않는다.
- 이 기능은 실행의 트리거·관측만 다룬다. flow 내부의 적재·검증·변환 로직 설계와
  실행 주기 설정은 각각 별도 기능이다.
