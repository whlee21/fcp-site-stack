## Clarifications

### Session 2026-09-01

- Q: 파이프라인 정의 확정의 주체는? → A: 워크스페이스 스코프의 `파이프라인 확정자` 롤이다.
  전역 플랫폼 운영자가 아니다. 확정 권한이 워크스페이스별로 나뉘어 최소권한에 부합하고,
  운영자가 모든 워크스페이스의 병목이 되지 않는다. 기능 011 FR-038을 개정해야 한다.
- Q: 자유서식 검수 권한은 어떻게 구성하나요? → A: **제한 롤만 요구한다.** 별도의 검수자
  롤을 두지 않는다. 원문 대조가 실명 계층에서 이루어지므로 제한 롤이 실질적 게이트이고,
  그 위에 롤을 하나 더 얹어도 통제는 늘지 않는다. 기능 008 FR-023의 "검수 권한" 개념은
  제한 롤로 흡수된다.
- Q: 직무 분리(SoD)를 어디까지 강제하나요? → A: 참조 자산 매핑에만 강제한다(현행 기능 010
  유지). 파이프라인 확정과 가명처리 검수에는 강제하지 않되, 확정 기록에 저작자와 확정자를
  남겨 사후 확인이 가능하게 한다. 넓게 강제하면 소규모 기관에서 최소 인원을 채우지 못해
  운영이 막힌다.

## 이 기능이 푸는 문제

롤이 기능마다 따로 생겨났다. 기능 001은 `플랫폼 운영자`와 `제한 롤`을, 005는 `검토
권한자`를, 008은 `검수 권한`을, 009는 `개설자`와 `참여자`를, 010은 매핑의 `작성자`와
`승인자`를, 012는 `제한 롤 보유자`인 검수자를 각자 이름 붙여 썼다. 어느 것이 같은 롤이고
어느 것이 다른 롤인지 정한 곳이 없다.

그 결과 **같은 행위에 서로 다른 주체가 지정된 곳이 있다.** 파이프라인 정의 확정을 기능
005는 "검토 권한을 가진 사람"(FR-038)이, 기능 011은 "플랫폼 운영자 롤 보유자"(FR-038)가
한다고 규정한다. 둘 중 하나는 틀렸거나, 둘은 다른 행위인데 이름이 같다.

이 기능은 흩어진 롤 이름을 **하나의 카탈로그로 모으고**, 각 롤이 무엇을 할 수 있고 무엇을
할 수 없는지를 한 곳에서 정한다. 초안이므로 롤의 존재와 경계를 정하는 데 집중하고, 세부
권한 항목의 전수 열거는 각 기능 스펙에 맡긴다.

## 소유 경계

세 계층이 각각 다른 것을 소유한다. 이 구분이 흐려지면 같은 정보가 두 곳에 저장된다.

| 소유 | 대상 |
| --- | --- |
| **통합 인증·권한 서비스** (기능 001 FR-021) | 사용자 계정, 롤 객체, 사용자-롤 소속 |
| **이 기능** | 롤 카탈로그 — 어떤 롤이 존재하고 각각 무엇을 할 수 있는가(권한 의미) |
| **기능 001** | 사용자·워크스페이스·롤 셋 사이의 배정 연결 |
| **기능 009** | 프로젝트 스코프의 멤버십 |

이 기능은 계정을 만들지도, 롤 객체를 저장하지도, 배정을 수행하지도 않는다. **무엇이 무엇을
할 수 있는지의 정의**만 소유한다.

## 롤 카탈로그 초안

### 스코프

롤은 두 층이다.

- **전역 롤**: 플랫폼 전체에 적용된다. 특정 워크스페이스에 매이지 않는다.
- **워크스페이스 스코프 롤**: 배정된 워크스페이스 안에서만 유효하다. 한 워크스페이스의
  롤이 다른 워크스페이스로 전이되지 않는다(기능 001 Assumptions).
- **프로젝트 스코프 롤**: 기능 009가 소유한다. 이 카탈로그는 존재만 기록한다.

### 전역 롤

| 롤 | 할 수 있는 것 | 할 수 없는 것 |
| --- | --- | --- |
| **플랫폼 운영자** | 워크스페이스 생성·설정·상태 전환·삭제, 유형과 계층 정책 적용, 타깃 폐기 승인, 워크스페이스 병합·이행, 재식별 위험 기준값 변경(심의 근거 첨부) | 제한 계층의 데이터 자체를 조회하는 것. 운영 권한과 데이터 접근은 분리된다 |
| **감사자** | 감사 이력, 설정 변경 이력, 확정 기록, 롤 배정 현황 조회 | 어떤 데이터 계층에도 접근. 설정을 바꾸는 것 |

### 워크스페이스 스코프 롤

| 롤 | 할 수 있는 것 | 할 수 없는 것 |
| --- | --- | --- |
| **제한 롤** | 배정된 워크스페이스의 제한 계층 데이터 조회, 자유서식 비식별화 결과 검수(개별 확인·일괄 승인) | 다른 워크스페이스의 계층 접근 |
| **파이프라인 저작자** | 스크립트 초안 작성·편집, dry-run·시뮬레이션 실행 요청 | 자기가 만든 정의를 확정하는 것 |
| **파이프라인 확정자** | 저작 결과 검토, 확정·반려 | 확정 대상 정의를 직접 저작하는 것 |
| **참조 자산 작성자** | 용어집 배포본 반입 등록, 매핑 항목 작성 | 자기가 작성한 매핑을 승인하는 것 |
| **참조 자산 승인자** | 배포본 확정, 매핑 사전 검토·승인 | 자기가 승인할 매핑을 작성하는 것 |
| **실행 요청자** | 잡 실행 요청, 실행 상태·이력 조회 | 파이프라인 정의 변경 |
| **조회자** | 워크스페이스 메타데이터, 품질 리포트 요약, 타깃 구성 조회 | 데이터 계층 접근, 실행 요청 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 롤 카탈로그 조회와 권한 확인 (Priority: P1)

운영자가 롤 카탈로그를 열어 어떤 롤이 있고 각각 무엇을 할 수 있는지 한 화면에서 본다.
롤마다 스코프(전역·워크스페이스·프로젝트), 허용 행위, 금지 행위, 그렇게 정한 근거가 함께
나온다.

카탈로그는 시스템이 실제 권한 판정에 쓰는 근거와 같은 것이어야 한다. 화면에 적힌 것과
실제 판정이 다르면 카탈로그는 문서가 아니라 오해의 원인이 된다.

**Why this priority**: 카탈로그가 없으면 나머지 모든 스토리에 대상이 없다. 이 스토리만
있어도 "지금 이 플랫폼에 어떤 롤이 있는가"에 답할 수 있게 된다.

**Independent Test**: 카탈로그를 조회해 위 표의 롤이 모두 나오고, 각 롤의 스코프와 허용·금지
행위가 확인되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 롤 카탈로그, **When** 운영자가 조회하면, **Then** 각 롤의 스코프, 허용 행위,
   금지 행위, 정의 근거가 확인된다.
2. **Given** 임의의 롤, **When** 스코프를 확인하면, **Then** 전역·워크스페이스·프로젝트 중
   하나로 명시되어 있다.
3. **Given** 카탈로그에 없는 롤, **When** 배정을 시도하면, **Then** 거부된다.
4. **Given** 카탈로그의 허용 행위 목록, **When** 실제 권한 판정과 비교하면, **Then**
   일치한다.
5. **Given** 부여 대상이 없는 롤(연구자), **When** 카탈로그에서 확인하면, **Then** 부여
   불가 상태와 그 사유가 함께 표시된다.

### User Story 2 - 운영 권한과 데이터 접근의 분리 (Priority: P1)

플랫폼 운영자는 워크스페이스를 만들고 설정하고 삭제할 수 있지만, 그 워크스페이스의 제한
계층 데이터를 조회할 수는 없다. 데이터를 보려면 제한 롤을 따로 받아야 한다.

두 권한을 한 롤에 묶으면 운영 업무를 하는 모든 사람이 PHI에 접근할 수 있게 된다. 운영은
자주 필요하고 데이터 접근은 드물게 필요하므로, 묶으면 넓은 쪽이 상시 열린다.

**Why this priority**: 헌법 II의 계층 제한이 롤 설계로 무너지는 가장 흔한 경로가 "운영자는
다 볼 수 있다"는 편의다. 이 분리가 없으면 US1의 카탈로그는 형식이 된다.

**Independent Test**: 플랫폼 운영자 롤만 가진 사용자가 워크스페이스 설정은 바꾸고 제한 계층
조회는 차단되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 플랫폼 운영자 롤만 가진 사용자, **When** 워크스페이스 설정을 변경하면,
   **Then** 허용된다.
2. **Given** 플랫폼 운영자 롤만 가진 사용자, **When** 제한 계층 데이터 조회를 시도하면,
   **Then** 차단된다.
3. **Given** 플랫폼 운영자 롤과 제한 롤을 함께 가진 사용자, **When** 제한 계층을 조회하면,
   **Then** 허용되고 그 조회가 감사 이력에 남는다.
4. **Given** 감사자 롤을 가진 사용자, **When** 어떤 데이터 계층에든 접근을 시도하면,
   **Then** 차단된다.
5. **Given** 감사자 롤을 가진 사용자, **When** 설정 변경을 시도하면, **Then** 차단된다.

### User Story 3 - 저작과 확정의 분리 (Priority: P2)

정의를 만드는 롤과 확정하는 롤을 나눈다. 파이프라인 스크립트는 `파이프라인 저작자`가 만들고
`파이프라인 확정자`가 확정하며, 참조 자산은 `참조 자산 작성자`가 만들고 `참조 자산 승인자`가
승인한다.

**롤을 나누는 것과 자기 승인을 막는 것은 다른 문제다.** 롤은 어디서나 나뉘지만, 같은 사람이
자기가 만든 것을 확정하지 못하도록 **시스템이 강제하는 범위는 참조 자산 매핑으로 한정한다**
(기능 010의 현행 규칙). 파이프라인 확정에는 강제하지 않는다 — 사람이 적은 기관에서 저작자와
확정자를 항상 다른 사람으로 채우지 못하면 운영이 멈추기 때문이다.

강제하지 않는 대신 기록을 남긴다. 모든 확정 기록에 저작자와 확정자가 각각 남으므로, 같은
사람이었다는 사실은 사후에 확인할 수 있다.

**Why this priority**: 롤 분리 없이는 권한을 나눌 수단이 없다. 다만 US1의 카탈로그가 먼저
있어야 어떤 롤 사이에 분리를 걸지 말할 수 있다.

**Independent Test**: 참조 자산 매핑에서 자기 승인이 거부되고, 파이프라인 확정에서는
허용되되 저작자와 확정자가 기록에 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 참조 자산 작성자가 작성한 매핑 항목, **When** 같은 사람이 승인을 시도하면,
   **Then** 거부된다.
2. **Given** 파이프라인 저작자가 만든 초안, **When** 확정자 롤도 가진 같은 사람이 확정하면,
   **Then** 허용된다.
3. **Given** 2번의 확정 기록, **When** 조회하면, **Then** 저작자와 확정자가 같은 사람임이
   확인된다.
4. **Given** 저작자와 확정자가 다른 사람일 때, **When** 확정하면, **Then** 허용되고 두
   사람이 확정 기록에 남는다.
5. **Given** 한 사용자가 저작 롤과 확정 롤을 함께 보유할 때, **When** 롤 배정을 확인하면,
   **Then** 보유 자체는 허용된다.

### User Story 4 - 워크스페이스 스코프 격리 (Priority: P2)

한 워크스페이스에서 받은 롤이 다른 워크스페이스로 전이되지 않는다. A 워크스페이스의 제한
롤 보유자는 B 워크스페이스에서는 아무 권한도 없다.

전역 롤은 예외다. 플랫폼 운영자와 감사자는 워크스페이스 배정 없이도 각자의 행위를 할 수
있다. 다만 그 행위 범위는 운영과 조회로 한정되며 데이터 접근을 포함하지 않는다(US2).

**Why this priority**: 스코프 전이는 조용히 일어나고 발견하기 어렵다. 다만 카탈로그와
운영·데이터 분리가 먼저 있어야 검증할 대상이 생긴다.

**Independent Test**: A 워크스페이스에만 배정된 사용자가 B 워크스페이스의 자원에 접근해
차단되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** A 워크스페이스에만 배정된 사용자, **When** B 워크스페이스 자원에 접근하면,
   **Then** 차단된다.
2. **Given** A 워크스페이스의 제한 롤 보유자, **When** B 워크스페이스의 제한 계층에
   접근하면, **Then** 차단된다.
3. **Given** 전역 롤 보유자, **When** 워크스페이스 배정 없이 운영 행위를 하면, **Then**
   허용된다.
4. **Given** 사용자가 통합 인증·권한 서비스에서 비활성화되었을 때, **When** 그 사용자의
   접근을 확인하면, **Then** 모든 스코프에서 차단된다.

### User Story 5 - 롤 배정 현황 조회와 감사 (Priority: P3)

운영자가 "누가 어디에 어떤 롤로 배정되어 있는지"를 조회한다. 반대로 롤 하나를 골라 그
롤을 가진 사용자 목록을 본다.

롤 배정과 해제는 실행자, 시각, 대상, 이전 상태, 새 상태가 감사 이력에 남는다. 특히 제한
롤의 부여와 회수는 PHI 접근 경계의 변경이므로 반드시 남아야 한다.

**Why this priority**: 조회와 감사는 롤 체계가 실제로 쓰이기 시작한 뒤에 필요해진다.

**Independent Test**: 사용자 한 명의 전체 배정 현황과 롤 하나의 보유자 목록이 각각 조회되고,
배정 변경이 감사 이력에 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 임의의 사용자, **When** 배정 현황을 조회하면, **Then** 어느 워크스페이스에
   어떤 롤로 배정되어 있는지 확인된다.
2. **Given** 임의의 롤, **When** 보유자를 조회하면, **Then** 그 롤을 가진 사용자 목록이
   확인된다.
3. **Given** 제한 롤 부여, **When** 감사 이력을 확인하면, **Then** 실행자, 시각, 대상
   사용자, 대상 워크스페이스가 남아 있다.
4. **Given** 제한 롤 회수, **When** 감사 이력을 확인하면, **Then** 동일하게 남아 있다.
5. **Given** 감사자 롤을 가진 사용자, **When** 배정 현황을 조회하면, **Then** 허용된다.

---

### Edge Cases

- 한 사용자가 저작자와 확정자 롤을 모두 갖는 것은 허용되는가? → 롤 보유는 허용되나, 자기가
  만든 개별 정의에 대한 확정만 거부된다. 소규모 기관에서 사람이 부족한 상황을 막지 않으면서
  자기 승인만 차단한다.
- 카탈로그에 있으나 아직 아무도 갖지 않은 롤은? → 정상 상태다. 연구자 롤이 그 예다.
- 롤 카탈로그가 바뀌면 이미 배정된 사용자는? → 배정은 유지되고, 그 롤의 허용 행위 변경이
  다음 권한 판정부터 적용된다. 카탈로그 변경은 감사 이력에 남는다.
- 통합 인증·권한 서비스에는 있는데 카탈로그에 없는 롤이 배정 대상으로 들어오면? →
  거부한다(기능 001 FR-032와 같은 취지).
- 프로젝트 개설자가 워크스페이스에서 배정 해제되면? → 기능 009가 정한 대로 운영자가 다른
  멤버에게 이관한다. 이 카탈로그는 그 규칙을 재정의하지 않는다.
- 전역 롤 보유자가 0명이 되면? → 워크스페이스 생성·설정이 불가능해진다. 최소 1명 유지를
  요구한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 카탈로그

- **FR-001**: 시스템은 플랫폼에서 사용되는 모든 롤을 하나의 카탈로그로 보유해야 한다.
- **FR-002**: 시스템은 롤마다 스코프(전역, 워크스페이스, 프로젝트), 허용 행위, 금지 행위,
  정의 근거를 기록해야 한다.
- **FR-003**: 시스템은 카탈로그에 없는 롤의 배정을 거부해야 한다.
- **FR-004**: 시스템은 권한 판정의 근거를 카탈로그와 일치시켜야 한다. 카탈로그에 없는
  허용을 판정에서 부여해서는 안 된다.
- **FR-005**: 시스템은 부여 대상이 없는 롤을 카탈로그에 표시하고 그 사유를 함께 제시해야
  한다.
- **FR-006**: 시스템은 카탈로그 변경을 감사 이력에 남겨야 한다.

#### 소유 경계

- **FR-007**: 시스템은 사용자 계정과 롤 객체의 저장을 통합 인증·권한 서비스에 맡겨야 하며,
  이 기능에서 중복 저장해서는 안 된다.
- **FR-008**: 시스템은 사용자·워크스페이스·롤의 배정 연결을 기능 001의 모델로 다뤄야 한다.
- **FR-009**: ~~시스템은 프로젝트 스코프 롤의 멤버십을 기능 009의 모델로 다뤄야 한다.~~
  **범위 밖(2026-09-01, 헌법 v4.2.1)** — 프로젝트·추출물 모델이 연구자 대상 기능 배제에
  포함되었다. 프로젝트 스코프 롤은 부여하지 않는다.

#### 전역 롤

- **FR-010**: 시스템은 플랫폼 운영자 롤에 워크스페이스 생성·설정·상태 전환·삭제, 타깃 폐기
  승인, 워크스페이스 병합·이행 권한을 부여해야 한다.
- **FR-011**: 시스템은 플랫폼 운영자 롤에 제한 계층 데이터 조회 권한을 부여해서는 안 된다.
  데이터 접근은 제한 롤을 통해서만 이루어져야 한다.
- **FR-012**: 시스템은 감사자 롤에 감사 이력, 설정 변경 이력, 확정 기록, 롤 배정 현황의
  조회 권한만 부여해야 한다.
- **FR-013**: 시스템은 감사자 롤에 데이터 계층 접근과 설정 변경 권한을 부여해서는 안 된다.
- **FR-014**: 시스템은 전역 롤 보유자가 최소 1명 유지되도록 해야 하며, 마지막 보유자의
  회수를 거부해야 한다.

#### 워크스페이스 스코프 롤

- **FR-015**: 시스템은 워크스페이스 스코프 롤의 효력을 배정된 워크스페이스로 한정해야 하며,
  다른 워크스페이스로 전이시켜서는 안 된다.
- **FR-016**: 시스템은 제한 롤에 배정된 워크스페이스의 제한 계층 데이터 조회 권한을 부여해야
  한다.
- **FR-017**: 시스템은 파이프라인 저작자 롤에 스크립트 초안 작성·편집과 dry-run·시뮬레이션
  실행 요청 권한을 부여해야 한다.
- **FR-018**: 시스템은 파이프라인 확정자 롤을 **워크스페이스 스코프**로 두고, 검토와
  확정·반려 권한을 부여해야 한다. 확정 권한을 전역 플랫폼 운영자 롤로 한정해서는 안 된다.
  기능 005 FR-038의 "검토 권한을 가진 사람"이 이 롤이며, 기능 011 FR-038("확정 권한을
  플랫폼 운영자 롤 보유자로 한정")은 이에 맞춰 개정되어야 한다.
- **FR-019**: 시스템은 참조 자산 작성자 롤에 용어집 배포본 반입 등록과 매핑 항목 작성
  권한을 부여해야 한다.
- **FR-020**: 시스템은 참조 자산 승인자 롤에 배포본 확정과 매핑 사전 검토·승인 권한을
  부여해야 한다.
- **FR-021**: 시스템은 자유서식 비식별화 결과의 검수와 개별 확인·일괄 승인을 **제한 롤
  보유자**가 수행할 수 있게 해야 하며, 별도의 검수자 롤을 두어서는 안 된다. 기능 008
  FR-023의 "검수 권한"은 제한 롤로 흡수된다.
- **FR-022**: 시스템은 검수 과정의 실명 계층 원문 조회를 허용하되, 조회자·시각·대상 환자를
  감사 이력에 남겨야 한다(기능 012 FR-057).
- **FR-023**: 시스템은 실행 요청자 롤에 잡 실행 요청과 실행 상태·이력 조회 권한을 부여해야
  한다.
- **FR-024**: 시스템은 조회자 롤에 워크스페이스 메타데이터, 품질 리포트 요약, 타깃 구성의
  조회 권한만 부여해야 하며, 데이터 계층 접근과 실행 요청 권한을 부여해서는 안 된다.

#### 직무 분리

- **FR-025**: 시스템은 저작자와 확정자를 별개 롤로 두어야 한다.
- **FR-026**: 시스템은 한 사용자가 저작 롤과 확정 롤을 함께 보유하는 것을 허용해야 한다.
  롤 보유 자체를 막지 않는다.
- **FR-027**: 시스템은 자기 승인 거부를 **참조 자산 매핑에 한정해** 강제해야 한다(기능
  010의 현행 규칙). 파이프라인 확정과 가명처리 검수에는 강제해서는 안 된다.
- **FR-028**: 시스템은 확정 기록에 저작자와 확정자를 각각 남겨야 한다. 자기 승인을
  강제로 막지 않는 영역에서는 이 기록이 유일한 사후 확인 수단이므로, 두 사람이 같아도
  그 사실이 드러나야 한다.

#### 연구자 롤

- **FR-029**: 시스템은 연구자 롤을 카탈로그에 정의하되, 부여 대상 워크스페이스가 없는 동안
  실제 배정을 거부해야 한다. 프로젝트 개설자·참여자 롤도 같게 다뤄야 한다(헌법 v4.2.1로
  범위 밖).
- **FR-030**: 시스템은 연구자 롤에 데이터 워크스페이스(SDM ETL, OMOP CDM ETL)의 어떤
  계층에 대한 접근 권한도 부여해서는 안 된다.

#### 조회와 감사

- **FR-031**: 시스템은 사용자 한 명의 전체 배정 현황을 조회할 수 있게 해야 한다.
- **FR-032**: 시스템은 롤 하나의 보유자 목록을 조회할 수 있게 해야 한다.
- **FR-033**: 시스템은 롤 배정과 회수를 실행자, 시각, 대상 사용자, 대상 워크스페이스와
  함께 감사 이력에 남겨야 한다.
- **FR-034**: 시스템은 제한 롤의 부여와 회수를 다른 롤과 구분해 식별할 수 있게 기록해야
  한다. PHI 접근 경계의 변경이기 때문이다.
- **FR-035**: 시스템은 제한 계층 데이터 조회를 감사 이력에 남겨야 한다.
- **FR-036**: 시스템은 롤 배정 현황 조회를 플랫폼 운영자와 감사자에게 허용해야 한다.
- **FR-037**: 시스템은 롤 카탈로그와 배정 현황 화면에 환자 식별정보나 원천 데이터 값을
  노출해서는 안 된다.
- **FR-038**: 시스템은 플랫폼 운영자만 재식별 위험 기준값을 변경할 수 있게 해야 하며,
  변경 시 심의 근거 첨부를 필수로 요구해야 한다(기능 008 FR-031·FR-032). 별도의 기준값
  관리 롤은 두지 않는다 — 심의라는 실질적 게이트가 이미 조직 절차로 존재하므로, 롤을
  하나 더 만들면 통제는 늘지 않고 관리 대상만 는다.

### Key Entities *(include if feature involves data)*

- **롤**: 권한의 단위. 이름, 스코프, 허용 행위 목록, 금지 행위 목록, 정의 근거, 부여 가능
  여부를 갖는다. 롤 객체 자체의 저장은 통합 인증·권한 서비스가 소유하고, 이 기능은 그
  의미를 소유한다.
- **롤 스코프**: 전역, 워크스페이스, 프로젝트 중 하나. 롤의 효력 범위를 결정한다.
- **롤 카탈로그**: 롤 전체의 목록과 각각의 정의. 권한 판정의 근거이며 변경 이력을 갖는다.
- **허용 행위 / 금지 행위**: 롤이 할 수 있는 것과 명시적으로 할 수 없는 것. 금지를 함께
  적는 이유는 "적혀 있지 않으니 되는 줄 알았다"를 막기 위함이다.
- **직무 분리 규칙**: 같은 사람이 저작과 확정을 함께 수행하는 것을 막는 규칙. 롤 보유가
  아니라 개별 산출물 단위로 적용된다.
- **롤 배정**: 기존 개념(기능 001). 사용자·워크스페이스·롤의 연결.
- **부여 가능 여부**: 롤이 지금 실제로 배정될 수 있는 상태인지. 연구자 롤처럼 대상
  워크스페이스가 없으면 부여 불가다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 임의의 롤 하나를 골라 그것이 무엇을 할 수 있고 무엇을 할 수 없는지
  확인하는 데 1분 이내가 걸린다.
- **SC-002**: 카탈로그에 정의되지 않은 롤이 배정된 사례가 0건이다.
- **SC-003**: 카탈로그에 없는 허용이 권한 판정에서 부여된 사례가 0건이다.
- **SC-004**: 플랫폼 운영자 롤만 가진 사용자가 제한 계층 데이터를 조회한 사례가 0건이다.
- **SC-005**: 감사자 롤 보유자가 데이터 계층에 접근하거나 설정을 변경한 사례가 0건이다.
- **SC-006**: 전역 롤 보유자가 0명이 된 사례가 0건이다.
- **SC-007**: 워크스페이스 스코프 롤이 배정되지 않은 워크스페이스에서 효력을 발휘한 사례가
  0건이다.
- **SC-008**: 참조 자산 매핑에서 작성자와 승인자가 같은 사람인 사례가 0건이다.
- **SC-017**: 파이프라인 확정 기록에서 저작자와 확정자가 같은 사람인 건을 식별할 수 있다.
- **SC-018**: 별도의 가명처리 검수자 롤이 카탈로그에 존재한 사례가 0건이다.
- **SC-009**: 확정 기록 100%에 저작자와 확정자가 각각 남아 있다.
- **SC-010**: 연구자 롤이 실제로 배정된 사례가 0건이다(분석 워크스페이스 구현 전까지).
- **SC-019**: 프로젝트 개설자 또는 프로젝트 참여자 롤이 배정된 사례가 0건이다(범위 배제
  해제 전까지).
- **SC-011**: 롤 배정·회수 100%가 실행자, 시각, 대상과 함께 감사 이력에 남는다.
- **SC-012**: 제한 롤의 부여·회수를 다른 롤 변경과 구분해 조회할 수 있다.
- **SC-013**: 운영자가 특정 사용자의 전체 배정 현황을 확인하는 데 1분 이내가 걸린다.
- **SC-014**: 운영자가 특정 롤의 보유자 전체를 확인하는 데 1분 이내가 걸린다.
- **SC-015**: 롤 카탈로그와 배정 현황 화면에서 환자 식별정보나 원천 데이터 값이 발견된
  사례가 0건이다.
- **SC-016**: 통합 인증·권한 서비스에서 비활성화된 사용자의 접근이 모든 스코프에서
  차단되기까지 5분을 넘지 않는다.

## Assumptions

- **이 스펙은 초안이다.** 사용자가 "초안"으로 요청했으므로 롤의 존재와 경계를 정하는 데
  집중하고, 각 롤의 세부 권한 항목을 전수 열거하지 않았다. 세부 권한은 각 기능 스펙이
  이미 규정하고 있으며, 이 카탈로그는 그것들이 어느 롤에 속하는지를 정한다.
- **운영 권한과 데이터 접근은 분리한다.** 헌법 II의 계층 제한을 롤 설계에서 무너뜨리는 가장
  흔한 경로가 "운영자는 다 볼 수 있다"는 편의다. 기능 001이 플랫폼 운영자에게 워크스페이스
  관리 권한을 주면서 제한 계층 접근을 별도의 제한 롤로 둔 것과 같은 취지다.
- **감사자 롤은 이 스펙이 새로 제안한다.** 헌법 준수 게이트가 감사 이력 보존을 요구하지만
  조회 전용 주체가 어느 기능에도 없다. 운영자에게 감사 조회를 맡기면 감사 대상과 감사
  주체가 같아진다. 필요 없다고 판단되면 덜어낼 수 있다.
- **직무 분리 강제는 참조 자산 매핑에만 적용한다.** 롤은 어디서나 저작자와 확정자로
  나뉘지만, 시스템이 자기 승인을 막는 것은 매핑뿐이다(기능 010의 현행 규칙). 파이프라인
  확정까지 강제하면 사람이 적은 기관에서 최소 인원을 채우지 못해 운영이 멈춘다. 강제하지
  않는 영역에서는 확정 기록의 저작자·확정자 기록이 사후 확인 수단이 된다.
- **가명처리 검수에 별도 롤을 두지 않는다.** 검수의 실질적 게이트는 실명 계층 원문 대조
  권한, 즉 제한 롤이다. 그 위에 검수자 롤을 얹어도 통제는 늘지 않고 배정 대상만 는다.
  다만 기능 008 FR-023이 말하는 "검수 권한"이 제한 롤로 흡수된다는 점은 008에 명시되어야
  한다.
- **연구자 롤은 정의하되 부여하지 않는다.** 헌법 v4.0.0과 `TODO(RESEARCH_ANALYSIS_WORKSPACE)`의
  귀결이다. 롤을 아예 빼면 분석 워크스페이스 스펙을 쓸 때 다시 만들어야 하고, 부여 가능
  상태로 두면 잘못 배정될 수 있다.
- **기관 심의는 시스템 롤이 아니다.** 조직 절차이며 시스템은 그 결과(기준값과 심의 근거)를
  기록한다. 값을 입력하는 주체는 플랫폼 운영자로 두고 심의 근거 첨부를 필수로 했다(FR-038).
  별도의 기준값 관리 롤을 두지 않은 것은, 실질적 게이트가 심의이지 롤이 아니기 때문이다.
- **롤 이름은 한국어를 정본으로 한다.** 기존 스펙이 모두 한국어 롤 이름을 쓰고 있다.
- 사용자 계정 생성·삭제와 롤 객체 정의는 통합 인증·권한 서비스가 소유하며 이 기능의 범위
  밖이다(기능 001 FR-021).

## Dependencies

- **기능 001 (워크스페이스 관리)**: 사용자·워크스페이스·롤 배정 연결과 통합 인증·권한 서비스
  경계를 제공한다. 이 스펙은 그 위에 롤의 의미를 얹는다.
- **기능 005 (ETL 파이프라인 저작)**: 저작·확정 권한의 실제 행위를 규정한다. FR-038의
  "검토 권한자"가 이 카탈로그의 어느 롤인지 확정해야 한다.
- **기능 008 (가명 연구용 SDM)**: 재식별 위험 기준값 심의를 규정한다. FR-023의 "검수
  권한을 가진 사람"이 제한 롤로 흡수되어 **개정 완료**(2026-09-01).
- **기능 009 (타깃·프로젝트·잡)**: 프로젝트 스코프 롤(개설자·참여자)을 소유하나, 헌법
  v4.2.1로 그 부분이 **범위 밖**이 되었다. 타깃·잡 모델은 범위 안이며 실행 요청자 롤이
  거기 걸린다.
- **기능 010 (워크스페이스 유형 세분화)**: 참조 자산의 작성자·승인자 분리 원칙을 제공한다.
- **기능 011 (워크스페이스 유형 간소화)**: FR-038이 이 스펙 FR-018에 맞춰 **개정 완료**
  (2026-09-01) — 확정 주체는 워크스페이스 스코프 파이프라인 확정자 롤이다.
- **기능 012 (환자 단위 가명처리 실행)**: 검수자에게 제한 롤을 요구한다(FR-056).
- **헌법 v4.0.0**: 원칙 II(계층 제한, 연구자 접근 분리), 원칙 V(추적성), 준수 게이트의
  롤 명시 요구가 이 기능의 제약이다.

## Out of Scope

- 사용자 계정의 생성·삭제·비활성화 (통합 인증·권한 서비스 소유)
- 롤 객체의 저장 구조와 인증 흐름
- 각 기능이 규정한 세부 권한 항목의 재정의
- 연구자용 분석 워크스페이스의 롤 구성 (`TODO(RESEARCH_ANALYSIS_WORKSPACE)` 확정 후 별도 정의)
- 조직 차원의 적정성 심의 절차 자체
