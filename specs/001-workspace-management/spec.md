## User Scenarios & Testing *(mandatory)*

### User Story 1 - 워크스페이스 생성 (Priority: P1)

플랫폼 운영자가 새로운 데이터 작업 단위를 만든다. 워크스페이스 유형(SDM/CDM)을
고르고, 데이터를 가져올 원천 시스템 연결 정보를 지정하고, 산출물이 따를 대상 표준 버전을
확정한다. 생성이 끝나면 그 워크스페이스는 고유하고 변경 불가능한 식별자를 갖고, 이후
모든 데이터 계층·실행 이력·권한이 이 식별자 위에 쌓인다.

**Why this priority**: 워크스페이스는 이 플랫폼의 모든 작업이 귀속되는 최상위 단위다.
생성 없이는 다른 어떤 기능도 대상이 존재하지 않는다. 이 스토리만 구현해도 "격리된
작업 공간을 만든다"는 가치가 독립적으로 성립한다.

**Independent Test**: 운영자가 유형·소스 커넥션·대상 표준 버전을 입력해 워크스페이스를
생성하고, 생성된 워크스페이스가 목록에 조회되며 그 식별자가 변경 시도에 거부되는 것을
확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 운영자 권한 사용자가 생성 화면에 있을 때, **When** 유형을 CDM으로 고르고
   유효한 소스 커넥션과 대상 표준 버전을 입력해 생성하면, **Then** 워크스페이스가
   생성되고 소문자 슬러그 형식의 식별자가 부여된다.
2. **Given** 이미 존재하는 워크스페이스 식별자와 동일한 값을 입력했을 때,
   **When** 생성을 시도하면, **Then** 생성이 거부되고 중복 사유가 안내된다.
3. **Given** 소프트 삭제되어 보존 기간이 남아 있는 워크스페이스의 식별자를 입력했을 때,
   **When** 생성을 시도하면, **Then** 생성이 거부된다.
4. **Given** 생성된 워크스페이스가 있을 때, **When** 식별자 변경을 시도하면,
   **Then** 시도가 거부된다.
5. **Given** 소스 커넥션 정보가 병원 내부망 밖 주소를 가리킬 때, **When** 생성을
   시도하면, **Then** 생성이 거부되고 외부 연결 불가 사유가 안내된다.
6. **Given** 유형을 SDM으로 선택했을 때, **When** 생성이 완료되면, **Then** 해당
   워크스페이스의 모든 데이터 계층이 실명 기반 제한 대상으로 표시된다.

### User Story 2 - 사용자·롤 배정 (Priority: P2)

운영자가 워크스페이스에 접근할 사용자와 그 롤을 배정한다. 배정되지 않은 사용자는 그
워크스페이스의 어떤 데이터도 볼 수 없다. **제한 계층**은 별도의 제한 롤을 가진 사용자만
접근할 수 있으며, 어느 계층이 제한 계층인지는 **워크스페이스 유형이 결정한다**(헌법
v4.1.1 명명 규칙 > 계층 용어). 환자 데이터를 다루는 워크스페이스(SDM ETL, OMOP CDM ETL)는
전 계층이 제한 계층이고, 참조 자산 관리 워크스페이스는 제한 계층을 두지 않는다.

**Why this priority**: 워크스페이스가 존재하는 순간 PHI 노출 위험이 생긴다. 접근 통제는
데이터가 흐르기 전에 자리 잡아야 한다. 생성 다음으로 급하다.

**Independent Test**: 운영자가 사용자 A에게 일반 롤을, 사용자 B에게 제한 롤을 배정한 뒤,
A가 제한 계층 조회에 실패하고 B는 성공하는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 워크스페이스가 존재할 때, **When** 운영자가 사용자에게 롤을 배정하면,
   **Then** 해당 사용자가 그 워크스페이스의 배정 목록에 나타난다.
2. **Given** 제한 롤이 없는 사용자가 있을 때, **When** CDM 워크스페이스의 landing, work,
   **mart** 중 어느 계층이든 데이터 조회를 시도하면, **Then** 접근이 거부된다.
3. **Given** 제한 롤이 없는 사용자가 있을 때, **When** SDM 워크스페이스의 어느 계층이든
   조회를 시도하면, **Then** 접근이 거부된다.
4. **Given** 사용자에게 배정된 롤이 있을 때, **When** 운영자가 배정을 해제하면,
   **Then** 그 사용자의 접근이 즉시 차단된다.
5. **Given** 권한 배정·해제가 일어났을 때, **When** 감사 이력을 조회하면, **Then**
   누가 누구에게 어떤 롤을 언제 배정·해제했는지 확인할 수 있다.
6. **Given** 통합 인증·권한 서비스에 없는 사용자나 롤을 지정했을 때, **When** 배정을
   시도하면, **Then** 배정이 거부된다.
7. **Given** 배정된 사용자가 통합 인증·권한 서비스에서 비활성화되었을 때, **When** 그
   사용자가 워크스페이스 접근을 시도하면, **Then** 접근이 거부된다.

### User Story 3 - 워크스페이스 설정 변경 (Priority: P3)

운영자가 운영 중인 워크스페이스의 소스 커넥션, 실행 주기, 워크스페이스별 파라미터를
변경한다. 원천 시스템 접속 정보가 바뀌거나, 적재 주기를 조정하거나, 변환 동작을 바꾸는
파라미터를 조정할 때 사용한다.

**Why this priority**: 생성과 권한이 있으면 워크스페이스는 이미 동작한다. 설정 변경은
운영 지속성을 위해 필요하지만, 초기 가치 전달 이후에 와도 된다.

**Independent Test**: 운영자가 실행 주기를 변경하고 저장한 뒤, 변경된 주기가 조회되고
변경 이력에 이전 값과 새 값이 남는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 워크스페이스가 존재할 때, **When** 운영자가 실행 주기를 변경하면,
   **Then** 이후 실행이 새 주기를 따른다.
2. **Given** 소스 커넥션을 변경할 때, **When** 저장 전에 연결 확인을 요청하면,
   **Then** 연결 성공 여부가 저장 전에 안내된다.
3. **Given** 연결 확인에 실패한 소스 커넥션일 때, **When** 저장을 시도하면,
   **Then** 저장이 거부된다.
4. **Given** 설정이 변경되었을 때, **When** 변경 이력을 조회하면, **Then** 변경자,
   변경 시각, 이전 값, 새 값이 확인된다.
5. **Given** 워크스페이스가 존재할 때, **When** 대상 표준 버전 변경을 시도하면,
   **Then** 변경이 거부된다.
6. **Given** 소스 커넥션에 비밀 정보(계정, 암호)가 포함될 때, **When** 설정 화면이나
   이력을 조회하면, **Then** 비밀 정보는 마스킹되어 표시된다.

### User Story 4 - 소프트 삭제와 보존 후 정리 (Priority: P4)

운영자가 더 이상 쓰지 않는 워크스페이스를 삭제한다. 삭제는 즉시 데이터를 없애지 않는다.
워크스페이스는 삭제 표시 상태로 전환되어 신규 실행이 중단되고 일반 접근이 막히지만,
데이터 스키마는 보존 기간 동안 그대로 남는다. 보존 기간이 지나면 정리 대상이 되어
스키마와 저장소 산출물이 제거된다.

**Why this priority**: 삭제는 파괴적이고 되돌릴 수 없는 방향의 동작이라 가장 마지막에
신중히 구현한다. 앞의 세 스토리 없이는 삭제할 대상 자체가 없다.

**Independent Test**: 운영자가 워크스페이스를 삭제하고, 즉시 조회 시 삭제 표시 상태로
보이며 스키마가 여전히 존재하고 신규 실행이 생기지 않는 것을 확인한 뒤, 보존 기간
경과를 모사해 정리가 수행되는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 운영 중인 워크스페이스가 있을 때, **When** 운영자가 삭제하면, **Then**
   워크스페이스가 삭제 표시 상태로 바뀌고 예정된 신규 실행이 더 이상 생성되지 않는다.
2. **Given** 워크스페이스가 삭제 표시 상태일 때, **When** 즉시 데이터 계층을 확인하면,
   **Then** 스키마와 데이터가 그대로 존재한다.
3. **Given** 워크스페이스가 삭제 표시 상태이고 보존 기간이 남아 있을 때, **When**
   운영자가 복구를 요청하면, **Then** 워크스페이스가 삭제 전 상태로 되돌아간다.
4. **Given** 보존 기간이 경과했을 때, **When** 정리가 수행되면, **Then** 해당
   워크스페이스의 데이터 계층과 저장소 산출물이 제거되고 정리 결과가 기록된다.
5. **Given** 삭제 또는 정리가 수행되었을 때, **When** 감사 이력을 조회하면, **Then**
   실행자, 시각, 대상 워크스페이스, 보존 만료 예정일이 확인된다.
6. **Given** 정리가 완료된 워크스페이스가 있을 때, **When** 목록을 조회하면, **Then**
   실행 이력과 감사 기록은 남아 있고 데이터 계층만 사라진 것이 확인된다.

### Edge Cases

- 삭제 표시 상태에서 이미 진행 중이던 실행이 있으면 어떻게 되는가? 진행 중 실행은
  완료까지 두고, 완료 후 신규 실행만 막는다.
- 보존 기간 경과 시점에 복구 요청과 정리 작업이 동시에 들어오면 어떻게 되는가?
  복구가 우선하며, 복구 성공 시 정리는 취소된다.
- 정리 작업이 중간에 실패하면 어떻게 되는가? 워크스페이스는 정리 실패 상태로 남고
  운영자에게 알림이 가며, 부분 삭제 상태가 기록된다.
- 소스 커넥션 대상 시스템이 응답하지 않을 때 워크스페이스 생성은 가능한가?
  연결 확인 실패 시 생성이 거부된다.
- 사용자가 여러 워크스페이스에 서로 다른 롤로 배정된 경우 권한은 어떻게 결정되는가?
  워크스페이스마다 독립적으로 결정되며 다른 워크스페이스의 롤이 전이되지 않는다.
- 마지막 운영자 권한 배정을 해제하려 하면 어떻게 되는가? 워크스페이스에 운영자 롤이
  최소 1명 남아야 하므로 해제가 거부된다.
- 통합 인증·권한 서비스가 일시적으로 응답하지 않으면 어떻게 되는가? 새 배정은 거부되고,
  기존 접근 판정은 안전한 쪽(거부)으로 처리된다.
- 배정된 사용자가 통합 인증·권한 서비스에서 삭제되면 배정 기록은 어떻게 되는가? 배정은
  무효로 표시되고 감사 이력에는 남는다.
- 보존 기간 시스템 설정이 변경되면 이미 삭제 표시된 워크스페이스는 어떻게 되는가?
  삭제 시점에 확정된 만료 예정일이 그대로 유지되며 앞당겨지거나 늦춰지지 않는다.
- 보존 만료 예정일이 이미 지난 상태로 시스템이 오래 중단되었다가 재개되면 어떻게
  되는가? 재개 후 만료된 워크스페이스들이 순차적으로 정리 대상이 된다.
- 삭제 표시 상태인 워크스페이스의 권한 배정을 변경할 수 있는가? 복구를 위한 운영자
  롤 조정만 허용하고 데이터 접근 롤 신규 배정은 거부된다.

## Requirements *(mandatory)*

### Functional Requirements

**생성**

**설정**

- **FR-009**: 사용자는 워크스페이스의 소스 커넥션, 실행 주기, 워크스페이스별 파라미터를
  변경할 수 있어야 한다.
- **FR-010**: 시스템은 소스 커넥션 변경 저장 전에 연결 확인을 수행해야 하며, 확인에
  실패하면 저장을 거부해야 한다.
- **FR-011**: 시스템은 모든 설정 변경에 대해 변경자, 변경 시각, 이전 값, 새 값을
  기록해야 한다.
- **FR-012**: 시스템은 소스 커넥션의 비밀 정보를 화면과 변경 이력에서 마스킹해
  표시해야 한다.
- **FR-013**: 시스템은 유형, 대상 표준 버전, 워크스페이스 식별자의 변경 요청을
  거부해야 한다.

**권한**

- **FR-014**: 사용자는 워크스페이스별로 사용자에게 롤을 배정하고 해제할 수 있어야 한다.
- **FR-015**: 시스템은 워크스페이스에 배정되지 않은 사용자의 해당 워크스페이스 데이터
  접근을 거부해야 한다.
- **FR-016**: 시스템은 제한 롤이 없는 사용자의 **제한 계층** 접근을 거부해야 한다. 어느
  계층이 제한 계층인지는 워크스페이스 유형이 결정하며, 환자 데이터를 다루는 워크스페이스는
  전 계층이 제한 계층이다(헌법 v4.1.1).
- **FR-017**: ~~시스템은 SDM 워크스페이스에 대해 제한 롤이 없는 사용자의 mart 계층을
  포함한 전 계층 접근을 거부해야 한다.~~ **FR-016에 흡수됨(2026-09-01, 헌법 v4.0.0·v4.1.1)**
  — 전 계층 제한이 SDM만의 예외가 아니라 환자 데이터 워크스페이스 전체의 규칙이 되었다.
- **FR-018**: 시스템은 롤 배정 해제 시 그 사용자의 접근을 즉시 차단해야 한다.
- **FR-019**: 시스템은 워크스페이스마다 운영자 롤 보유자가 최소 1명 유지되도록
  마지막 운영자 롤 해제를 거부해야 한다.
- **FR-020**: 시스템은 모든 권한 배정·해제에 대해 실행자, 대상 사용자, 롤, 시각을
  감사 이력으로 기록해야 한다.
- **FR-021**: 시스템은 배정 대상 사용자 계정과 롤 정의를 플랫폼에 포함된 통합 인증·권한
  서비스에서 가져와야 한다. 이 기능은 사용자 계정이나 롤 자체를 생성·수정·삭제하지 않고,
  기존 사용자와 롤을 워크스페이스에 배정하는 것만 관리해야 한다.
- **FR-032**: 시스템은 통합 인증·권한 서비스에 존재하지 않는 사용자 또는 롤에 대한 배정
  요청을 거부해야 한다.
- **FR-033**: 시스템은 통합 인증·권한 서비스에서 사용자가 비활성화되거나 롤이 회수되면,
  그 사용자의 해당 워크스페이스 접근을 차단해야 한다.

**삭제**

- **FR-022**: 시스템은 워크스페이스 삭제 시 소프트 삭제만 수행해야 하며, 데이터 계층
  스키마를 즉시 삭제해서는 안 된다.
- **FR-023**: 시스템은 삭제 표시된 워크스페이스에 대해 신규 실행 생성을 중단해야 하며,
  이미 진행 중인 실행은 완료까지 유지해야 한다.
- **FR-024**: 시스템은 삭제 표시된 워크스페이스에 대한 일반 사용자의 데이터 접근을
  차단해야 한다.
- **FR-025**: 사용자는 보존 기간이 남아 있는 삭제 표시 워크스페이스를 삭제 전 상태로
  복구할 수 있어야 한다.
- **FR-026**: 시스템은 보존 기간 경과 후 해당 워크스페이스의 데이터 계층과 저장소
  산출물을 정리해야 하며, 정리 결과를 기록해야 한다.
- **FR-027**: 시스템은 정리 완료 후에도 워크스페이스의 실행 이력과 감사 기록을
  보존해야 한다.
- **FR-028**: 시스템은 정리 실패 시 워크스페이스를 정리 실패 상태로 유지하고 운영자에게
  알려야 하며, 어느 범위까지 제거되었는지 기록해야 한다.
- **FR-029**: 시스템은 소프트 삭제 후 보존 기간이 경과하면 정리를 수행해야 한다. 보존
  기간은 운영자 실수를 되돌리기 위한 복구 유예 기간이며, 워크스페이스 유형과 무관하게
  동일한 값을 적용해야 한다. 기관이 시스템 설정으로 값을 지정할 수 있어야 하고 기본값은
  30일이다.
- **FR-034**: 시스템은 삭제 시점의 보존 기간 값으로 보존 만료 예정일을 확정하고 해당
  워크스페이스에 고정해야 한다. 이후 시스템 설정의 보존 기간이 변경되어도 이미 삭제
  표시된 워크스페이스의 만료 예정일은 바뀌지 않아야 한다.
- **FR-035**: 시스템은 보존 기간 시스템 설정의 변경에 대해 변경자, 변경 시각, 이전 값,
  새 값을 기록해야 한다.

**전 기능 공통**

- **FR-030**: 시스템은 워크스페이스 생성, 설정 변경, 권한 변경, 삭제, 복구, 정리
  각각에 대해 실행자와 시각을 포함한 감사 이력을 남겨야 한다.
- **FR-031**: 시스템은 워크스페이스 관련 오류 메시지와 화면 노출 로그에 원천 데이터
  값이나 환자 식별정보가 포함되지 않도록 해야 한다.

### Key Entities

- **워크스페이스**: 데이터 작업의 최상위 격리 단위. 변경 불가한 소문자 슬러그 식별자,
  유형, 대상 표준 버전, 상태(활성/삭제 표시/정리 실패/정리 완료), 생성 시각, 삭제
  시각, 보존 만료 예정일을 갖는다.
- **워크스페이스 유형**: SDM 또는 CDM. 유형은 데이터 계층의 PHI 제한 범위를 결정한다.
  - **SDM**: 실명 기반. 개인의 임상의료 정보를 FHIR로 전송하기 위한 워크스페이스.
    mart 계층까지 실명이 유지되므로 전 계층이 제한 대상이다.
  - **CDM**: 가명 기반. 연구용 임상의료 데이터 워크스페이스. landing·work는 가명화 이전
    원천 값을 포함할 수 있어 제한 대상이다. ~~mart는 가명 기반이지만~~ **개정(2026-09-01,
    헌법 v4.0.0): mart도 제한 대상이다.** 가명 기반이라는 이유로 계층이 제한에서 빠지지
    않으며, 연구자 접근은 연구자용 분석 워크스페이스를 통해서만 이루어진다.
- **소스 커넥션**: 워크스페이스가 데이터를 가져올 원천 시스템 접속 정보. 비밀 정보를
  포함하며 마스킹 대상이다. 연결 확인 상태와 최종 확인 시각을 갖는다.
- **대상 표준 버전**: 워크스페이스 산출물이 따를 표준의 버전. 생성 시 확정되며 불변이다.
- **실행 주기**: 워크스페이스의 정기 실행 일정.
- **워크스페이스 파라미터**: 워크스페이스별로 다른 변환·적재 동작을 결정하는 설정 값 집합.
- **데이터 계층**: 워크스페이스에 속한 landing, work, mart 계층. 각 계층은 접근 제한
  수준을 갖는다.
- **롤 배정**: 사용자와 워크스페이스와 롤의 연결. 제한 롤 여부를 포함한다. 사용자와
  롤 자체는 통합 인증·권한 서비스가 소유하며, 이 기능은 셋 사이의 연결만 소유한다.
- **감사 이력**: 워크스페이스에 가해진 모든 변경의 기록. 실행자, 시각, 동작, 이전 값,
  새 값을 포함하며 워크스페이스 정리 후에도 보존된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 필요한 정보를 손에 쥔 상태에서 워크스페이스 하나를 생성 완료하는
  데 5분 이내가 걸린다.
- **SC-002**: 배정되지 않은 사용자 또는 제한 롤이 없는 사용자의 제한 계층 접근 시도가
  100% 차단된다. 허용된 접근이 잘못 차단되는 경우는 0건이다.
- **SC-003**: 워크스페이스 식별자가 생성 후 변경된 사례가 0건이다.
- **SC-004**: 삭제 요청 후 데이터 계층 스키마가 보존 기간 종료 전에 제거된 사례가 0건이다.
- **SC-005**: 보존 기간이 만료된 워크스페이스의 정리가 만료일로부터 24시간 이내에
  시작된다.
- **SC-006**: 보존 기간 내 복구 요청의 100%가 삭제 전 설정·권한·데이터를 그대로 되돌린다.
- **SC-007**: 생성·설정·권한·삭제·복구·정리 동작의 100%에 대해 실행자와 시각을 감사
  이력에서 조회할 수 있다.
- **SC-008**: 워크스페이스 관리 화면에 노출된 텍스트에서 환자 식별정보나 원천 데이터
  값이 발견된 사례가 0건이다.
- **SC-009**: 잘못된 소스 커넥션 정보로 워크스페이스가 생성되어 첫 실행에서 실패하는
  비율이 5% 미만이다.
- **SC-010**: 운영자가 특정 사용자가 어떤 워크스페이스에 어떤 롤로 배정되어 있는지
  확인하는 데 1분 이내가 걸린다.
- **SC-011**: 통합 인증·권한 서비스에서 사용자가 비활성화된 뒤 그 사용자의 워크스페이스
  접근이 차단되기까지 5분을 넘지 않는다.

## Assumptions

- 워크스페이스를 생성·설정·삭제할 수 있는 사람은 플랫폼 운영자 롤 보유자로 한정한다.
  일반 사용자는 배정된 워크스페이스의 조회만 가능하다.
- 대상 표준 버전은 생성 시 확정되고 이후 변경할 수 없다. 입력 요구사항 표에서 "설정"
  항목에 대상 표준 버전이 없고 "생성"에만 있는 것을 근거로 한 판단이다. 다른 표준
  버전이 필요하면 새 워크스페이스를 만든다.
- 워크스페이스 유형 역시 생성 시 확정되고 변경할 수 없다. 유형이 데이터 계층의 PHI
  제한 범위를 결정하므로 사후 변경은 접근 통제 경계를 깨뜨린다.
- 소스 커넥션의 원천 시스템은 모두 병원 내부망 안에 있다. 외부 인터넷 소스는 존재하지
  않는다.
- 롤은 워크스페이스 스코프로 배정된다. 한 워크스페이스의 롤이 다른 워크스페이스로
  전이되지 않는다.
- 사용자 계정과 롤 정의는 플랫폼에 포함된 통합 인증·권한 서비스(Keycloak)가 소유한다.
  이 서비스는 병원 내부망에 함께 배포되며 외부 인증 사업자에 의존하지 않는다. 사용자
  계정 생성·삭제와 롤 정의는 이 기능의 범위 밖이다.
- ADMET 유형은 이번 범위에서 제외한다. 향후 추가될 수 있으므로 유형은 확장 가능한
  선택지로 다루되, 지금은 SDM과 CDM만 구현·검증 대상이다.
- 소프트 삭제된 워크스페이스는 보존 기간 동안 신규 실행이 중단되고 일반 접근이
  차단되지만, 운영자는 복구를 위해 메타데이터를 조회할 수 있다.
- 보존 기간은 복구 유예 기간이지 법정 보유 의무 기간이 아니다. 워크스페이스의 데이터
  계층은 병원 원천 시스템에서 재생성할 수 있는 파생물이며, 원본 임상 기록의 법정 보존
  의무는 원천 시스템이 진다는 전제 위에 있다. 원천에서 재생성할 수 없는 산출물을 보유한
  워크스페이스가 생기면 FR-029를 재검토해야 한다.
- 정리(cleanup)는 데이터 계층 스키마와 저장소 산출물을 대상으로 하며, 실행 이력과
  감사 기록은 정리 대상이 아니다.
- 보존 기간 만료 시 정리는 자동으로 수행된다. 운영자의 별도 승인 단계는 두지 않는다.
- SDM은 실명 기반으로 개인의 임상의료 정보를 FHIR로 전송하기 위한 워크스페이스이고,
  CDM은 가명 기반 연구용 임상의료 데이터 워크스페이스다. 이 정의가 FR-007과 FR-017의
  SDM 전 계층 제한 근거다.
- 헌법 v2.0.0 원칙 II는 가명화된 연구용 SDM을 포함해 예외 없는 원외 반출 금지를
  정한다. 이전에 기록해 둔 "연구용 SDM만 반출 대상" 문구는 개정으로 사라졌고, 반출
  대상을 판정하는 문제 자체가 없어졌다. 이 기능에서 후속 확인 대상이던 항목은 종결한다.
- 다만 "연구용"이라는 말의 지시 대상은 기능별로 다르다. 이 기능에서 연구용은 CDM
  워크스페이스의 성격을 가리키고, 기능 004에서 연구용은 SDM 7단계 가명처리 산출물을
  가리킨다. 둘은 배타적이지 않다 — CDM은 상시 유지되는 가명 기반 연구용 데이터 자산이고,
  SDM 제공 데이터셋은 요청 단위로 만들어지는 산출물이다. FR-007·FR-017의 SDM 전 계층
  제한 근거는 SDM이 mart 계층까지 실명 기반이라는 점이며, 이 근거는 헌법 v2.0.0에서도
  그대로 유지된다.
- 이 기능은 워크스페이스 자체의 생명주기만 다룬다. 워크스페이스 안에서 실행되는
  데이터 파이프라인의 설계·실행 로직과, SDM 연구용 데이터를 병원 내부에서 연구자에게
  제공하는 통제 절차는 별도 기능(기능 004)이다.
- 다기관 간 워크스페이스 동기화·공유는 범위 밖이다.
