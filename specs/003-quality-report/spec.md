## User Scenarios & Testing *(mandatory)*

### User Story 1 - 한 회차의 검증 결과 통합 조회 (Priority: P1)

사용자가 방금 끝난 실행 회차를 열어 데이터가 쓸 만한지 판단한다. 적재 직후 수행된
검증과 변환 이후 수행된 검증이 한 화면에 나란히 나오고, 각 지점에서 몇 개 규칙이
통과했고 몇 개가 실패했는지 보인다. 두 검증이 서로 다른 도구에서 나왔다는 사실은
화면에 드러나지 않는다. 사용자는 형식이 다른 결과를 각각 읽는 대신 하나의 표를 본다.

**Why this priority**: 실행이 성공했다는 것과 데이터가 쓸 만하다는 것은 다른 이야기다.
통합된 한 화면이 없으면 사용자는 판단 자체를 시작할 수 없다. 이 스토리만 있어도
"이번 회차 데이터를 믿어도 되는가"에 답할 수 있다.

**Independent Test**: 적재 검증과 변환 검증이 모두 수행된 실행 회차를 열어 두 결과가
동일한 형식의 한 화면에 표시되고, 각 지점의 통과·실패 규칙 수가 확인되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 적재 검증과 변환 검증이 모두 수행된 실행 회차가 있을 때, **When** 품질
   리포트를 조회하면, **Then** 두 검증 결과가 하나의 화면에 동일한 형식으로 표시된다.
2. **Given** 실행 회차의 품질 리포트를 볼 때, **When** 단계별 요약을 확인하면,
   **Then** 각 검증 지점의 통과 규칙 수와 미통과 규칙 수, 그리고 미통과의 심각도별
   내역이 표시된다.
3. **Given** 변환 검증이 수행되기 전에 실행이 중단되었을 때, **When** 품질 리포트를
   조회하면, **Then** 적재 검증 결과만 표시되고 변환 검증은 미수행으로 구분된다.
4. **Given** 품질 리포트를 조회할 때, **When** 소속 정보를 확인하면, **Then** 해당
   워크스페이스 식별자와 실행 회차 식별자가 함께 확인된다.
5. **Given** 배정되지 않은 워크스페이스일 때, **When** 그 워크스페이스의 품질 리포트
   조회를 시도하면, **Then** 접근이 거부된다.
6. **Given** 실행 회차의 상태가 기능 002에서 갱신되었을 때, **When** 품질 리포트를
   조회하면, **Then** 복제본이 아닌 현재 상태가 반영되어 표시된다.

### User Story 2 - 규칙별 통과·실패 확인 (Priority: P2)

사용자가 실패한 검증을 눌러 어느 테이블의 어떤 규칙이 몇 건 어긋났는지 본다. 목록에는
대상 테이블, 규칙명, 통과 여부, 실패 건수가 나온다. 실패한 규칙이 위로 올라오고,
통과한 규칙은 접어 둘 수 있다.

**Why this priority**: 요약만으로는 무엇을 고쳐야 할지 모른다. 테이블과 규칙명이 있어야
담당자를 정하고 원인을 찾아갈 수 있다. 실패 건수는 문제의 크기를 알려준다.

**Independent Test**: 일부 규칙이 실패한 회차에서 규칙 목록을 열어 대상 테이블, 규칙명,
실패 건수가 표시되고 실패 규칙이 먼저 보이는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 검증 결과가 있는 실행 회차일 때, **When** 규칙 목록을 조회하면, **Then**
   각 항목에 대상 테이블, 규칙명, 통과 여부, 심각도, 실패 건수가 표시된다.
2. **Given** 통과와 미통과가 섞인 규칙 목록일 때, **When** 목록을 조회하면, **Then**
   미통과 규칙이 먼저 표시되고, 미통과 안에서는 시스템이 제공한 심각도 순서를 따른다.
3. **Given** 규칙 목록이 길 때, **When** 통과 항목만 감추는 필터를 적용하면, **Then**
   실패한 규칙만 남는다.
4. **Given** 통과한 규칙일 때, **When** 항목을 확인하면, **Then** 실패 건수가 0으로
   표시된다.
5. **Given** 규칙이 어긋난 실제 데이터 값이 존재하고 대상 계층 접근 권한이 있을 때,
   **When** 규칙 상세를 조회하면, **Then** 마스킹된 샘플 값이 표시되고 원본 값은
   표시되지 않는다.
6. **Given** 대상 테이블이 속한 계층에 접근 권한이 없는 사용자일 때, **When** 규칙
   상세를 조회하면, **Then** 실패 건수까지만 표시되고 샘플 값은 표시되지 않는다.
7. **Given** 어긋난 값이 매우 많을 때, **When** 규칙 상세를 조회하면, **Then** 정해진
   상한까지의 샘플만 표시된다.
8. **Given** 검증 도구가 심각도 값을 부여했을 때, **When** 규칙 항목을 조회하면,
   **Then** 도구가 준 값이 변형 없이 그대로 표시된다.
9. **Given** 하나의 규칙이 여러 테이블에 적용될 때, **When** 목록을 조회하면,
   **Then** 테이블별로 개별 항목으로 표시된다.

### User Story 3 - 회차별 품질 추이 조회 (Priority: P3)

사용자가 같은 워크스페이스의 여러 실행 회차를 나란히 놓고 품질이 나아지는지 나빠지는지
본다. 회차별로 실패 규칙 수와 실패 건수가 어떻게 변했는지 보이고, 특정 규칙 하나를
골라 그 규칙만의 추이도 볼 수 있다.

**Why this priority**: 한 회차만 보면 이번 실패가 일시적인지 계속되던 문제인지 알 수
없다. 추이는 원인 추적과 개선 여부 판단에 필요하지만, 단건 조회가 먼저 있어야 의미가
생긴다.

**Independent Test**: 여러 회차가 쌓인 워크스페이스에서 추이를 열어 회차별 실패 규칙
수의 변화가 표시되고, 특정 규칙을 선택하면 그 규칙의 회차별 결과가 나오면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 여러 실행 회차가 있는 워크스페이스일 때, **When** 추이를 조회하면,
   **Then** 회차별 미통과 규칙 수와 실패 건수가 시간순으로 표시된다.
2. **Given** 추이를 볼 때, **When** 특정 규칙을 선택하면, **Then** 그 규칙의 회차별
   통과 여부와 실패 건수가 표시된다.
3. **Given** 어떤 회차에서 규칙이 추가되거나 제거되었을 때, **When** 그 규칙의 추이를
   조회하면, **Then** 해당 규칙이 존재하지 않았던 회차가 미적용으로 구분된다.
4. **Given** 추이에서 특정 회차를 선택할 때, **When** 상세로 이동하면, **Then** 그
   회차의 품질 리포트가 열린다.
5. **Given** 검증이 수행되지 않은 회차가 섞여 있을 때, **When** 추이를 조회하면,
   **Then** 그 회차는 실패 0건이 아니라 미수행으로 구분된다.

### Edge Cases

- 검증 도구가 결과를 남기지 못한 채 실행이 끝나면 어떻게 되는가? 해당 검증 지점은
  미수행으로 표시되며, 통과로 간주되지 않는다.
- 규칙명이 회차 사이에 바뀌면 추이는 어떻게 되는가? 규칙 식별 기준이 달라지므로 이전
  이름의 규칙은 종료된 것으로, 새 이름은 신규로 다뤄진다.
- 실패 건수가 대상 테이블 전체 행 수만큼 큰 경우 어떻게 표시하는가? 건수를 그대로
  표시하되 전체 대비 비율을 함께 제공한다.
- 한 회차에서 같은 테이블·같은 규칙이 여러 번 평가되면 어떻게 되는가? 평가 시점별로
  구분해 저장하고 화면에는 마지막 결과를 대표로 표시한다.
- 검증 결과가 매우 많을 때(규칙 수천 개) 화면은 어떻게 되는가? 실패 항목을 우선 제공하고
  전체 목록은 나눠서 조회한다.
- 워크스페이스가 정리(cleanup)된 뒤 품질 리포트를 조회하면 어떻게 되는가? 정규화된
  검증 결과와 추이는 남아 있고, 원본 검증 산출물은 조회되지 않는다.
- 실행이 취소되어 다음 실행이 적재분을 지우고 다시 적재한 경우 추이는 어떻게 되는가?
  중단된 회차의 검증 결과도 회차 이력에 남되 중단으로 구분되어 추이 판단에서 제외된다.
- 검증 결과가 도착하기 전에 사용자가 품질 리포트를 열면 어떻게 되는가? 집계 대기 중으로
  표시되고, 화면 진입·새로고침 시점에 다시 조회된다.
- 검증 도구가 심각도 값을 주지 않으면 어떻게 되는가? 심각도 없음으로 저장되고, 표시
  순서에서는 미통과 항목의 기본 순위를 따른다.
- 검증 도구가 이전에 없던 새로운 심각도 값을 주기 시작하면 어떻게 되는가? 값은 그대로
  저장되고, 표시 순서가 정의되지 않은 값은 순서 정의가 추가될 때까지 기본 순위로 표시된다.
- 실패 건수가 1건인데 샘플이 노출되면 개인이 특정되지 않는가? 샘플은 마스킹된 형태로만
  저장·표시되고, 대상 계층 접근 권한이 있는 사용자에게만 노출된다.
- 실행 이력 저장소에서 해당 실행 회차를 찾을 수 없으면 어떻게 되는가? 검증 결과는 그대로
  표시되고 실행 회차 정보만 확인 불가로 표시된다.

## Requirements *(mandatory)*

### Functional Requirements

**정규화 저장**

- **FR-001**: 시스템은 적재 검증 결과와 변환 검증 결과를 하나의 공통 구조로 정규화해
  저장해야 한다. 이 품질검증 결과 저장소는 실행 이력·상태 저장소와 물리적으로 분리되어야
  한다.
- **FR-002**: 시스템은 조회 측이 출처별 원본 형식을 해석하지 않고도 모든 검증 결과를
  동일한 형태로 읽을 수 있게 제공해야 한다.
- **FR-003**: 시스템은 정규화된 각 항목에 대해 적재 검증과 변환 검증 중 어느 쪽에서
  비롯되었는지를 보존해야 한다. 다만 이 구분이 조회 측의 해석 분기를 요구해서는 안 된다.
- **FR-004**: 시스템은 정규화된 모든 검증 결과 항목을 실행 회차 식별자와 워크스페이스
  식별자에 귀속시켜야 한다.
- **FR-005**: 시스템은 검증 결과의 정규화 저장을 해당 검증 지점이 끝난 시점에 수행해야
  하며, 아직 도착하지 않은 결과는 집계 대기 중으로 구분해야 한다.
- **FR-006**: 시스템은 새로운 검증 출처가 추가되어도 조회 측의 표시 형식이 바뀌지 않도록
  공통 구조를 유지해야 한다.

**단계별 통합 표시**

- **FR-007**: 시스템은 한 실행 회차의 적재 검증 결과와 변환 검증 결과를 하나의 화면에
  동일한 형식으로 표시해야 한다.
- **FR-008**: 시스템은 각 검증 지점에 대해 통과 규칙 수와 미통과 규칙 수를 제공해야
  하며, 미통과 규칙 수의 심각도별 내역을 함께 제공해야 한다.
- **FR-009**: 시스템은 수행되지 않은 검증 지점을 미수행으로 구분해야 하며, 통과로
  간주해서는 안 된다.

**규칙별 통과·실패**

- **FR-010**: 시스템은 각 검증 결과 항목에 대해 대상 테이블, 규칙명, 통과 여부, 실패
  건수를 제공해야 한다.
- **FR-011**: 시스템은 규칙 목록에서 미통과 규칙을 통과 규칙보다 먼저 표시해야 하며,
  통과 항목을 감추는 필터와 심각도별 필터를 제공해야 한다.
- **FR-012**: 시스템은 규칙이 어긋난 실제 데이터 값을 원본 그대로 저장하거나 화면에
  노출해서는 안 된다.
- **FR-013**: 시스템은 화면에 노출하는 모든 품질 리포트 항목에서 주민등록번호, 환자번호,
  전화번호를 포함한 정형 식별자 패턴을 마스킹해야 한다.
- **FR-014**: 시스템은 실패 건수와 함께 규칙에 어긋난 값의 마스킹된 샘플을 제공해야
  한다.
- **FR-031**: 시스템은 샘플 값을 마스킹한 뒤에만 저장해야 한다. 마스킹되지 않은 원본
  값이 저장소에 남아서는 안 된다.
- **FR-032**: 시스템은 마스킹된 샘플에서 원본 값을 복원할 수 없게 해야 한다. 샘플은
  값의 형태를 파악할 수 있는 수준까지만 남긴다.
- **FR-033**: 시스템은 하나의 규칙 결과에 저장·표시하는 샘플 개수에 상한을 두어야 한다.
- **FR-034**: 시스템은 대상 테이블이 속한 데이터 계층에 접근 권한이 있는 사용자에게만
  마스킹된 샘플을 노출해야 한다. 권한이 없는 사용자에게는 실패 건수까지만 제공한다.
- **FR-015**: 시스템은 검증 도구가 각 결과에 부여한 심각도 값을 변형하거나 재정의하지
  않고 그대로 저장하고 표시해야 한다.
- **FR-028**: 시스템은 심각도 값을 출처 구분과 무관하게 하나의 공통 항목으로 제공해야
  하며, 조회 측이 출처별로 심각도를 다르게 해석하지 않아도 되게 해야 한다.
- **FR-029**: 시스템은 심각도 값별 표시 순서를 함께 제공해야 한다. 정렬과 우선순위
  판단에 필요한 순서는 시스템이 정의하고, 조회 측이 심각도 값을 해석해 순서를 만들어서는
  안 된다.
- **FR-030**: 시스템은 통과하지 못한 규칙 전체를 미통과로 집계해야 하며, 그 내역을
  심각도별로 함께 제공해야 한다. 미통과 집계는 특정 심각도 값의 정의에 의존해서는 안 된다.

**이력과 추이**

- **FR-016**: 사용자는 워크스페이스의 실행 회차별 품질 결과 추이를 조회할 수 있어야 한다.
- **FR-017**: 시스템은 추이에서 회차별 미통과 규칙 수와 실패 건수를 시간순으로 제공해야
  한다.
- **FR-018**: 사용자는 특정 규칙을 선택해 그 규칙의 회차별 결과 추이를 조회할 수 있어야
  한다.
- **FR-019**: 시스템은 규칙이 존재하지 않았거나 검증이 수행되지 않은 회차를 미적용 또는
  미수행으로 구분해야 하며, 실패 0건과 같게 다뤄서는 안 된다.
- **FR-020**: 사용자는 추이에서 특정 회차를 선택해 그 회차의 품질 리포트로 이동할 수
  있어야 한다.
- **FR-021**: 시스템은 중단된 실행 회차의 검증 결과를 이력에 남기되 중단으로 구분해야
  하며, 추이 판단에서 제외해야 한다.
- **FR-022**: 시스템은 워크스페이스가 정리된 뒤에도 정규화된 검증 결과와 추이를 보존해야
  한다.

**기존 기능과의 경계**

- **FR-023**: 시스템은 실행 이력·상태 저장소와 품질검증 결과 저장소를 분리해 유지해야
  한다. 실행 이력과 상태는 기능 002가 소유하고, 품질검증 결과는 이 기능이 소유한다.
- **FR-026**: 시스템은 품질검증 결과 저장소에 실행 상태를 복제 보관해서는 안 되며,
  실행 회차 식별자로 참조해야 한다.
- **FR-027**: 시스템은 품질 리포트 화면을 구성할 때 두 저장소를 함께 읽어 실행 회차
  정보와 검증 결과를 결합해 제공해야 한다. 이 결합은 조회 측이 아니라 시스템이 수행해야
  한다.

**권한과 감사**

- **FR-024**: 시스템은 해당 워크스페이스에 배정된 사용자만 품질 리포트를 조회할 수 있게
  해야 한다.
- **FR-025**: 시스템은 품질 리포트 조회에 대해 조회자, 대상 실행 회차, 조회 시각을
  감사 이력으로 기록해야 한다.

### Key Entities

- **검증 결과 항목**: 품질검증 결과 저장소의 최소 단위. 실행 회차 식별자, 워크스페이스
  식별자, 검증 지점(적재 검증 또는 변환 검증), 대상 테이블, 규칙명, 통과 여부, 심각도,
  실패 건수, 마스킹된 샘플, 평가 시각을 갖는다. 실행 상태는 포함하지 않고 실행 회차
  식별자로 참조한다.
- **심각도**: 검증 도구가 결과에 부여한 값. 시스템은 이 값을 변형하지 않고 보존하며,
  표시 순서만 별도로 정의해 함께 제공한다.
- **마스킹된 샘플**: 규칙에 어긋난 값을 원본 복원이 불가능한 형태로 가공한 표본. 규칙
  결과당 개수 상한이 있고, 대상 계층 접근 권한이 있는 사용자에게만 노출된다.
- **검증 지점**: 적재 직후와 변환 직후 두 지점. 각 지점은 수행됨 또는 미수행 상태를
  갖는다.
- **규칙**: 검증 대상 조건. 규칙명과 적용 대상 테이블로 식별된다. 회차 사이에 추가·제거될
  수 있다.
- **실행 회차**: 기능 002의 실행 건에 대응하는 단위. 품질 결과는 항상 하나의 실행 회차에
  귀속된다.
- **추이 계열**: 하나의 워크스페이스 또는 하나의 규칙에 대해 회차 순서대로 늘어놓은
  결과의 나열. 미수행·미적용·중단 회차가 구분되어 포함된다.
- **감사 이력**: 품질 리포트 조회 기록. 조회자, 대상, 시각을 포함한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 실행 회차 하나의 적재 검증과 변환 검증 결과를 확인하는 데 화면
  이동 1회 이내가 걸린다.
- **SC-002**: 조회 측이 검증 출처별로 서로 다른 형식을 해석해야 하는 지점이 0곳이다.
- **SC-003**: 실패한 규칙에 대해 사용자가 대상 테이블과 규칙명을 확인하는 데 30초
  이내가 걸린다.
- **SC-004**: 품질 리포트 화면과 저장된 검증 결과에서 원본 데이터 값이나 환자 식별정보가
  발견된 사례가 0건이다.
- **SC-005**: 검증이 수행되지 않은 지점이 통과로 표시된 사례가 0건이다.
- **SC-006**: 규칙 1,000개 규모의 회차에서 사용자가 기다린다고 느끼지 않는 시간 안에
  실패 규칙 목록이 표시된다.
- **SC-007**: 사용자가 특정 규칙의 최근 10회차 추이를 확인하는 데 1분 이내가 걸린다.
- **SC-008**: 검증 결과 항목의 100%가 워크스페이스 식별자와 실행 회차 식별자에 귀속된다.
- **SC-009**: 품질 리포트 조회의 100%가 조회자와 시각과 함께 감사 이력에 남는다.
- **SC-010**: 새로운 검증 출처가 추가될 때 조회 측 표시 형식의 변경이 0건이다.
- **SC-011**: 저장된 샘플에서 원본 값을 복원할 수 있었던 사례가 0건이다.
- **SC-012**: 대상 계층 접근 권한이 없는 사용자에게 샘플 값이 노출된 사례가 0건이다.
- **SC-013**: 검증 도구가 부여한 심각도 값이 저장·표시 과정에서 변형된 사례가 0건이다.
- **SC-014**: 품질검증 결과 저장소에 실행 상태가 복제 보관된 사례가 0건이다.
- **SC-015**: 실패한 규칙의 80% 이상에서 사용자가 원본 데이터를 직접 조회하지 않고
  마스킹된 샘플만으로 원인의 방향을 잡을 수 있다.

## Assumptions

- 이 기능은 검증 결과를 보여주는 데 한정한다. 검증 규칙을 정의·수정·삭제하는 기능과,
  검증 실패 시 파이프라인을 중단할지 결정하는 정책은 이번 범위 밖이다.
- 원문은 "세 출처(Prefect 상태 / GX 결과 / dbt 결과)를 단일 테이블로 정규화"라고 했으나,
  실행 이력·상태 저장소와 품질검증 결과 저장소를 분리하기로 결정했다. 따라서 품질검증
  결과 저장소가 정규화하는 대상은 적재 검증과 변환 검증 두 출처이며, 실행 상태는 기능
  002가 소유하고 실행 회차 식별자로 참조한다. "조회 측이 출처별 형식을 해석하지 않는다"는
  원문의 취지는 두 검증 출처에 대해 그대로 유지된다.
- 검증은 적재 직후와 변환 직후 두 지점에서만 수행된다. 기능 002의 실패 단계 중 "AI
  호출"에 대응하는 검증 결과는 이 리포트에 포함되지 않는다.
- 기능 011의 **시뮬레이션 결과**와 기능 012의 **확정 게이트 결과**는 이 리포트의 대상이
  아니다(2026-09-01 확정). 이 스펙은 실행 회차별 적재·변환 검증을 다루는데, 시뮬레이션은
  워크스페이스 생성 시 저작 단계의 산출물이고 확정 게이트는 실행이 아니라 산출물 확정의
  판정이다. 셋을 한 리포트에 섞으면 "이 회차의 품질"이라는 축이 무너진다.
- 기능 012의 가명처리 단계에서 나오는 검증 결과는 이 리포트에 포함된다. 그 단계가 기능
  002의 실패 단계 `변환`·`AI 호출`에 매핑되므로(002 FR-051) 기존 두 검증 지점 안에서
  다뤄진다.
- 기능 002는 실패 단계를 적재·검증·변환·AI 호출 네 가지로 표시하는데, 그중 "검증"은
  적재 검증과 변환 검증을 함께 가리킨다. 이 기능은 그 안을 두 지점으로 나눠 보여준다.
  002의 단계 구분을 바꾸지는 않는다.
- 품질 리포트는 규칙명, 테이블명, 건수 같은 집계 정보를 다루므로 워크스페이스에 배정된
  사용자면 조회할 수 있다. 기능 002의 실행 로그와 달리 운영자 전용이 아니다.
- 실패 건수는 집계값이므로 그 자체로 환자 식별정보가 아니다. 다만 실패 건수가 1이고
  대상이 좁은 경우 개인을 특정할 여지가 있어, 화면 노출은 마스킹 규칙의 적용을 받는다.
- 마스킹된 샘플 값은 실패 건수와 달리 원본에서 파생된 값이므로, 대상 테이블이 속한
  데이터 계층의 접근 권한을 가진 사용자에게만 노출한다. ~~헌법 원칙 II가 landing·work
  계층과 SDM 전 계층을 제한 롤로 묶고 있으므로~~ **정정(2026-09-01, 헌법 v4.2.1)**:
  헌법 원칙 II는 환자 데이터를 다루는 워크스페이스의 **전 계층**을 계열 불문하고 제한
  대상으로 묶는다. 그 계층에서 나온 샘플도 같은 경계를 따라야 한다는 판단은 그대로이며,
  적용 범위만 넓어졌다. 건수까지는 권한과 무관하게 볼 수 있다.
- 심각도 값의 어휘는 검증 도구가 정한다. 시스템은 값을 재정의하거나 공통 등급으로
  변환하지 않는다. 다만 정렬과 우선순위 판단에 필요한 표시 순서는 시스템이 값별로
  정의해 함께 제공한다. 조회 측이 심각도 값을 해석해 순서를 만들지 않게 하려는 것이며,
  값 자체를 바꾸는 것은 아니다.
- "미통과"는 통과하지 못한 모든 규칙을 뜻하며 심각도와 무관하게 집계된다. 심각도별
  내역은 그 안의 분해로 제공된다. 이렇게 하면 집계의 정의가 도구별 심각도 어휘에
  의존하지 않는다.
- 추이 조회의 기본 범위는 최근 회차부터 거슬러 올라가며, 사용자가 조회 구간을 조정할
  수 있다. 전체 이력을 한 번에 그리지 않는다.
- 검증 결과의 정규화 저장은 실행이 끝나기를 기다리지 않고 각 검증 지점이 끝날 때마다
  수행된다. 따라서 실행 중인 회차도 부분적인 품질 리포트를 가질 수 있다.
- 화면은 상태 전이 시점에만 갱신되는 데이터를 다루므로 주기적 자동 폴링을 하지 않는다.
  기능 002와 동일하게 화면 진입과 새로고침 시점에 조회한다.
- 품질 리포트는 워크스페이스 정리 후에도 보존된다. 기능 001의 정리 대상은 데이터 계층과
  저장소 산출물이며, 집계된 검증 결과는 실행 이력과 함께 남는다.
