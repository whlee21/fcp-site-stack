# Phase 0 — Research

**Feature**: Backend REST API 레이어 | **Date**: 2026-09-01

기술 선택과 통합 방식을 확정한다. 각 항목은 결정 · 근거 · 검토한 대안 순으로 적는다.
헌법이 강제하는 항목은 "선택"이 아니라 제약이므로 그렇게 표시했다.

---

## R1. 웹 프레임워크와 ASGI 서버

**Decision**: FastAPI + **uvicorn**

**Rationale**: 이 서비스의 산출물 중 하나가 **OpenAPI 계약**이다. `contracts/`가 계약 테스트의
기준이 되므로, 스키마를 코드에서 자동 생성하는 프레임워크가 계약과 구현의 드리프트를 구조적으로
막는다. Pydantic 모델이 요청·응답 검증과 스키마 생성을 겸하므로 두 벌을 유지할 필요가 없다.
비동기 I/O가 기본이라 Prefect·Keycloak·Gitea 세 곳을 동시에 호출하는 구간에서 유리하다.

**uvicorn**을 ASGI 서버로 둔다. 단일 컨테이너 이미지 전제이므로 프로세스 관리자를 따로 두지
않고 uvicorn을 PID 1로 실행한다. 워커 수는 설정으로 노출하되 기본 1로 둔다 — 규모 가정이
미확정(R8)인 상태에서 다중 워커를 기본값으로 두면 상태 공유 문제를 근거 없이 떠안게 된다.
대기열 순번(002 FR-028)은 애플리케이션 메모리가 아니라 PostgreSQL이 정본이므로 워커를 늘려도
정합성이 깨지지 않는다.

**Alternatives considered**:
- **Litestar** — 성능·DI가 낫다는 평이 있으나 생태계가 작고, 폐쇄망에서 문제 발생 시 참조할
  자료가 적다. 원내 환경에서는 "막혔을 때 찾을 수 있는가"가 성능보다 중요하다.
- **Django REST Framework** — 관리자 화면과 ORM이 딸려오지만 UI가 범위 밖이라 이점이 없고,
  동기 기본이라 외부 의존 4종 호출에 불리하다.
- **Flask** — 스키마 자동 생성이 없어 계약을 손으로 유지해야 한다. 드리프트가 생긴다.

## R2. 데이터 접근과 마이그레이션

**Decision**: SQLAlchemy 2.x(async) + Alembic. 드라이버는 `psycopg` 3.

**Rationale**: 제어 평면 스키마는 관계가 얽혀 있다(워크스페이스–계층군–타깃–잡–롤 배정).
원시 SQL로 두면 상태 전이 규칙이 쿼리에 흩어진다. 마이그레이션은 필수다 — 워크스페이스 식별자
불변성과 감사 이력 보존이 헌법 요구사항이라 스키마 변경 이력 자체가 감사 대상이 된다.

**제약**: `adapters/db/`는 **제어 평면 스키마에만** 연결한다. 워크스페이스 데이터 계층
(`{ws}_landing`·`_work`·`_mart`·`_pseudo`)에 대한 엔진·세션을 만들지 않는다(헌법 IV).
이는 설정으로 강제한다 — DSN을 하나만 주입하고 동적 스키마 접속 경로를 두지 않는다.

**Alternatives considered**:
- **asyncpg 직접 사용** — 빠르지만 상태 전이 규칙을 SQL에 흩는다.
- **Tortoise / SQLModel** — SQLModel은 FastAPI와 결이 맞으나 복잡한 관계에서 SQLAlchemy로
  내려가게 되어 결국 두 층을 알아야 한다.

## R3. Keycloak 연동 (인증·롤)

**Decision**: JWKS를 기동 시 1회 받아 캐시하고 **토큰을 로컬에서 검증**한다. 요청마다
introspection을 호출하지 않는다. 롤 배정 조회는 Admin API를 쓰되 캐시하고 TTL을 둔다.

**Rationale**: 요청마다 Keycloak을 호출하면 인증 서버가 API의 단일 실패점이 된다. 기능 001
FR-032가 "통합 인증·권한 서비스에 존재하지 않는 사용자·롤 배정 거부"를 요구하는데, 이는
**배정 시점** 검증이지 요청 시점이 아니다.

**중요한 경계**: 기능 001 SC-011이 *"사용자가 비활성화된 뒤 접근이 차단되기까지 5분을 넘지
않는다"* 를 요구한다. 로컬 검증만 하면 토큰 만료까지 차단이 지연된다. 따라서 **캐시 TTL과
토큰 수명의 합이 5분을 넘지 않아야 한다**. 이것이 이 항목의 실질적 설계 제약이다.

**Alternatives considered**:
- **매 요청 introspection** — 즉시 차단되나 Keycloak 장애가 전면 장애가 된다.
- **토큰만 신뢰, 조회 없음** — SC-011을 만족할 수 없다.

## R4. Prefect 연동 (잡 실행)

**Decision**: API는 Prefect deployment run을 **트리거하고 상태를 조회**할 뿐이다. flow 정의를
API가 소유하지 않고, 실행 로그 원문을 API가 저장하지 않는다.

**Rationale**: 헌법 IV가 제어 평면과 데이터 평면을 나눈다. Prefect는 오케스트레이션 계층이고
API는 그 위의 제어 평면이다. API가 로그 원문을 보관하기 시작하면 PHI 경유지가 된다(헌법 III).

**설계 결정 셋**:
1. 모든 flow run에 `workspace_id` 태그를 **API가 붙인다**(헌법 V, 예외 없음). 클라이언트가
   태그를 지정하는 경로를 두지 않는다 — 지정 가능하면 빠뜨릴 수 있다.
2. 잡 상태는 Prefect가 정본이고 API는 **캐시 없이 조회 시점에 위임**한다. 002 FR이 요구하는
   대기열·순번은 API가 제어 평면 DB에서 관리한다(Prefect의 동시성 제한만으로는 002 FR-006의
   워크스페이스 단위 순차 실행을 표현할 수 없다).
3. 로그는 **실패 건에 한해, 운영자 롤에게만, 요약본으로** 노출한다(002 FR, 헌법 III).
   API는 Prefect에서 받은 로그를 마스킹 필터를 통과시킨 뒤 반환하고 저장하지 않는다.

**Alternatives considered**:
- **API가 자체 스케줄러를 갖는다** — Prefect와 이중 관리가 되고 헌법 IV의 "Prefect는 ETL만
  오케스트레이션" 규정과 충돌한다.
- **로그를 API DB에 적재** — 조회는 빨라지나 PHI 보관처가 하나 늘고 마스킹 실패 시 영구 잔존한다.

## R5. Gitea 연동 (형상 관리)

**Decision**: API가 Gitea HTTP API로 커밋을 만들고 커밋 해시를 제어 평면 DB에 기록한다.
정의 원문은 Gitea가 정본이고 API는 **참조만** 보관한다.

**Rationale**: 기능 005가 "화면에서 변경하면 시스템이 자동으로 커밋한다. 커밋 주체가 사람인지
시스템인지 구분해 기록한다"를 요구한다. 따라서 API는 커밋 주체를 구분해 커밋해야 한다.
정의 원문을 DB에 복제하면 두 정본이 생겨 어느 쪽이 맞는지 판단해야 하는 상황이 온다.

**설계 결정**: 워크스페이스는 특정 커밋을 **고정**하고 운영자가 명시적으로 승격할 때만 바뀐다
(005 clarification). API는 `pinned_commit`을 제어 평면에 두고 실행 시 그 값을 Prefect에 넘긴다.

**Alternatives considered**:
- **git CLI를 컨테이너에서 직접 실행** — 작업 디렉터리 상태 관리가 필요해지고 단일 이미지
  전제와 어긋난다.
- **정의 원문을 DB에 이중 보관** — 위 참조.

## R6. 마스킹 (헌법 III)

**Decision**: 정형 식별자(주민등록번호·환자번호·전화번호) 마스킹을 **로거 기본 필터**로 둔다.
응답 직렬화 단계나 미들웨어가 아니다.

**Rationale**: 헌법 III이 *"마스킹을 사후 처리가 아닌 로깅 필터 기본값으로 두어야 누락이
생기지 않는다"* 고 근거까지 적어 규정한다. 미들웨어에 두면 미들웨어를 거치지 않는 경로
(기동 로그, 백그라운드 태스크, 예외 핸들러)가 새어 나간다.

**검증**: 마스킹은 단위 테스트가 아니라 **통합 테스트에서 로그 출력을 캡처해** 확인한다.
필터가 등록되지 않은 로거가 하나라도 있으면 실패해야 한다.

## R7. 오프라인 배포 (헌법 I)

**Decision**: 컨테이너 이미지를 원외에서 빌드해 **이미지 아카이브로 반입**한다. Python 휠은
빌드 시점에 전부 이미지에 포함하고 런타임에 인덱스를 조회하지 않는다.

**Rationale**: 헌법 I이 *"빌드·배포·런타임 어느 단계에서도 외부 레지스트리·저장소·CDN을 직접
조회해서는 안 된다(MUST NOT)"* 고 규정한다. 원내 빌드는 불가능하므로 반입 경계는 이미지다.

**반입 기록**: 헌법 준수 게이트가 "자산명, 버전, 출처, 반입일" 기록을 요구한다. 이미지 태그와
다이제스트, 포함된 의존성 목록(lock 파일)을 반입 기록에 남긴다.

**Python 3.13 선택 (2026-09-01 변경)**: 초안은 3.14였으나 3.13으로 낮춘다. C 확장 의존
(`psycopg`, `pydantic-core` 등)의 휠 가용성이 3.13에서 확실히 넓고, 폐쇄망에서는 런타임에
소스 빌드로 대체할 수 없어 휠 부재가 곧 반입 실패다. 3.14의 신기능 중 이 서비스가 필요로
하는 것이 없으므로 최신성을 얻는 대신 반입 위험을 지는 거래가 성립하지 않는다.

**여전히 유효한 검증**: 버전과 무관하게 **이미지 빌드 단계에서 전 의존의 휠 존재를 확인**해야
한다. 빌드 로그에 소스 빌드가 나타나면 그 시점에 잡아야 하고, 반입 후에 알면 되돌리는 비용이
크다(quickstart §3).

## R8. 성능·규모 — 미해결

**Decision**: 성능 목표를 이 계획에서 **확정하지 않는다.** 아래를 작업 가정으로만 둔다.

| 항목 | 가정 | 근거 |
| --- | --- | --- |
| 동시 사용자 | 수십 명 | 단일 병원, 운영자 소수 + 배정 사용자 |
| 워크스페이스 수 | 수십 개 | 유형 4종 × 용도 |
| 잡 동시 실행 | 워크스페이스당 1건 | 002 FR-006이 순차 실행을 강제 |

**Rationale**: 명세의 SC는 전부 **사람 조작 시간**(분 단위)과 **위반 건수 0**으로 되어 있고
API 지연·처리량 기준이 없다. 근거 없는 숫자를 성공 기준으로 승격하면 그것이 나중에 아키텍처
결정을 정당화하는 데 쓰인다.

**미해결**: `TODO(PSEUDONYMIZATION_SCALE)`(기능 008·012)이 풀리지 않아 잡 하나의 처리량과
소요 시간을 알 수 없다. 이 값은 002의 실행 모델 확장 필요 여부를 결정하므로 **plan이 아니라
스펙에서 확정되어야 한다.**

## R9. PostgreSQL 18 활용

**Decision**: 식별자에 `uuidv7()`를 쓴다. 감사 이력 테이블은 append-only로 두고 애플리케이션
레벨에서 UPDATE·DELETE 경로를 제공하지 않는다.

**Rationale**: PostgreSQL 18이 `uuidv7()`를 내장한다. 시간 정렬이 되는 UUID라 감사 이력과 잡
이력처럼 시간순 조회가 지배적인 테이블에서 인덱스 지역성이 좋다. UUIDv4는 이 특성이 없다.

**주의**: 워크스페이스 식별자는 UUID가 아니다. 헌법 명명 규칙이 **소문자 슬러그**로 못박고
있고 경로·태그·권한이 그 위에 쌓인다. UUID는 내부 PK로만 쓰고 슬러그를 자연키로 유지한다.
