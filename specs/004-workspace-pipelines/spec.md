# Feature Specification: 워크스페이스별 파이프라인 명세

**Feature Branch**: `004-workspace-pipelines`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "12. 워크스페이스별 명세 — 세 워크스페이스는 서로 독립이며 데이터 의존성이 없다. SDM/CDM은 같은 병원 EHR을 각자 추출한다. 12.1 SDM: 요청 단위 작업, 9단계(요청 접수 → 동의 대조 → EHR 추출·검증 → 비정형구조화 → 용어매핑 → SDM 변환·검증 → 가명처리 → 재식별 위험 점검 → 반출 승인·패키지), 게이트 5개. 12.2 CDM: EHR을 OMOP CDM으로 변환, 재현 불가능하므로 스냅샷이 원본 자산이며 manifest 동반. 12.3 ADMET: 실험 데이터 표준화, AI 미사용." (후속 지시: ADMET 워크스페이스는 이번 범위에서 제외한다.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - CDM 파이프라인과 스냅샷 (Priority: P1)

데이터 관리자가 병원 EHR을 OMOP CDM으로 변환한다. 적재와 적재 검증을 거친 뒤 용어매핑이
수행되고, 변환과 CDM 전용 품질 검증이 이어진다. 용어매핑에 AI가 개입하므로 같은 입력에
같은 결과가 나온다는 보장이 없다. 그래서 완성된 CDM은 다시 만들어 낼 수 있는 산출물이
아니라, 그 자체가 보존해야 할 원본 자산이다. 스냅샷과 함께 어떤 vocabulary 버전과 어떤
변환 정의와 어떤 모델로 만들어졌는지가 기록된다.

**Why this priority**: 두 워크스페이스 중 단계가 적고 게이트가 없는 쪽이다. 워크스페이스
프로비저닝, 실행 트리거, 품질 리포트로 이어지는 전체 경로와 AI 컴포넌트 연동, 재현
불가능성 대응을 여기서 먼저 검증할 수 있다. 여기서 골격이 확인되면 SDM은 그 위에 통제
게이트를 얹는 문제가 된다.

**Independent Test**: EHR 소스를 가진 CDM 워크스페이스를 실행해 용어매핑을 포함한 전체
경로가 수행되고, 산출된 스냅샷과 함께 vocabulary 버전·변환 정의 버전·모델 버전이 기록된
manifest가 남으면 검증 완료.

**Acceptance Scenarios**:

1. **Given** EHR 소스가 설정된 CDM 워크스페이스일 때, **When** 실행하면, **Then**
   적재, 적재 검증, 용어매핑, 변환, CDM 품질 검증이 순서대로 수행된다.
2. **Given** 용어매핑 단계일 때, **When** 매핑을 요청하면, **Then** 대상 표준이 OMOP으로
   지정되어 호출된다.
3. **Given** 용어매핑이 수행될 때, **When** 실행 기록을 확인하면, **Then** AI 컴포넌트가
   직접 호출되지 않고 정해진 경유 지점을 통해 호출된 것이 확인된다.
4. **Given** CDM 실행이 성공했을 때, **When** 산출물을 확인하면, **Then** 스냅샷이
   생성되고 vocabulary 버전, 변환 정의 버전, 모델 버전, 프롬프트 버전이 담긴 manifest가
   함께 보관된다.
5. **Given** 같은 소스로 CDM을 두 번 실행했을 때, **When** 두 결과를 비교하면,
   **Then** 결과가 다를 수 있으며 시스템은 이를 오류로 다루지 않는다.
6. **Given** 과거 CDM 스냅샷이 있을 때, **When** 그 스냅샷을 조회하면, **Then** 함께
   보관된 manifest로 생성 조건을 확인할 수 있다.
7. **Given** 적재 검증이 실패했을 때, **When** 실행 상태를 확인하면, **Then** 이후
   단계가 수행되지 않고 실패로 종료된다.

### User Story 2 - SDM 요청 접수와 동의 대조 (Priority: P2)

연구 담당자가 외부에서 받은 환자 목록과 요청 항목 범위를 SDM 워크스페이스에 접수한다.
시스템은 그 목록을 동의 상태와 대조해 미동의자와 동의를 철회한 사람을 제외하고 코호트를
확정한다. 요청 인원과 확정 인원, 제외 사유별 인원이 시스템 기록으로 남는다.

**Why this priority**: 동의 대조는 이후 모든 단계의 법적 근거다. 이 단계 없이 EHR을
추출하면 근거 없는 처리가 된다. 그리고 이 스토리만으로도 "요청 100명 중 82명이 처리
대상"이라는 사실을 시스템이 증명할 수 있게 된다.

**Independent Test**: 환자 목록을 접수해 동의 대조를 실행하고, 확정된 코호트 인원과
제외된 인원이 사유별로 기록되며 그 수치를 나중에 다시 조회할 수 있으면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 환자 목록과 요청 항목 범위가 접수되었을 때, **When** 요청을 조회하면,
   **Then** 요청 식별자, 접수자, 접수 시각, 요청 인원이 확인된다.
2. **Given** 요청된 환자 목록에 미동의자가 포함되어 있을 때, **When** 동의 대조를
   수행하면, **Then** 그 환자가 코호트에서 제외된다.
3. **Given** 동의를 철회한 환자가 목록에 포함되어 있을 때, **When** 동의 대조를
   수행하면, **Then** 그 환자가 코호트에서 제외된다.
4. **Given** 동의 대조가 끝났을 때, **When** 결과를 조회하면, **Then** 요청 인원,
   확정 코호트 인원, 제외 인원이 사유별로 표시된다.
5. **Given** 동의 대조 결과가 기록되었을 때, **When** 나중에 그 요청을 다시 조회하면,
   **Then** 당시의 대조 결과 수치가 그대로 보존되어 있다.
6. **Given** 확정된 코호트가 있을 때, **When** 다음 단계가 시작되면, **Then** 처리
   대상이 그 코호트로만 한정된다.
7. **Given** 동의 대조 결과 코호트가 0명일 때, **When** 실행이 진행되면, **Then**
   이후 단계로 넘어가지 않고 종료된다.
8. **Given** 동의 정보를 조회할 수 없을 때, **When** 동의 대조를 수행하면, **Then**
   코호트가 확정되지 않고 실행이 실패로 종료된다.

### User Story 3 - SDM 실명 표준 데이터 생성 (Priority: P3)

확정된 코호트에 한정해 EHR을 추출하고 검증한 뒤, 기록지 같은 비정형 자료를 구조화
필드로 만들고, 용어를 표준 체계로 매핑한 다음, 실명 기반 표준 데이터 모델로 변환하고
검증한다. 이 산출물은 전 계층이 환자 식별정보 영역이므로 제한 롤만 접근한다.

**Why this priority**: 반출할 대상이 만들어지는 단계다. 코호트가 확정되어 있어야 시작할
수 있고, 이게 있어야 가명처리와 반출이 의미를 갖는다.

**Independent Test**: 확정된 코호트를 입력으로 EHR 추출·검증, 비정형구조화, 용어매핑,
변환·검증이 순서대로 수행되어 실명 기반 표준 데이터가 생성되고, 제한 롤이 없는 사용자가
그 데이터의 어느 계층에도 접근하지 못하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 확정된 코호트가 있을 때, **When** EHR 추출이 수행되면, **Then** 코호트에
   속한 환자의 데이터만 추출된다.
2. **Given** EHR 추출이 끝났을 때, **When** 적재 검증을 수행하면, **Then** 검증 결과가
   품질 리포트에 기록되고 실패 시 다음 단계로 넘어가지 않는다.
3. **Given** 비정형 기록지가 포함되어 있을 때, **When** 비정형구조화가 수행되면,
   **Then** 구조화된 필드가 생성되고 사용된 모델 버전과 프롬프트 버전이 기록된다.
4. **Given** 용어매핑이 수행될 때, **When** 결과를 확인하면, **Then** 대상 표준
   체계로 매핑된 값과 함께 사용된 vocabulary 버전, 모델 버전, 프롬프트 버전이 기록된다.
5. **Given** 매핑되지 않은 값이 있을 때, **When** 결과를 확인하면, **Then** 임의의
   값으로 채워지지 않고 미매핑으로 남는다.
6. **Given** 변환이 끝났을 때, **When** 변환 검증을 수행하면, **Then** 검증 결과가
   품질 리포트에 기록되고 실패 시 다음 단계로 넘어가지 않는다.
7. **Given** 실명 기반 표준 데이터가 생성되었을 때, **When** 제한 롤이 없는 사용자가
   어느 계층이든 접근을 시도하면, **Then** 접근이 거부된다.
8. **Given** 비정형구조화나 용어매핑에서 AI가 사용될 때, **When** 실행 기록을 확인하면,
   **Then** AI 컴포넌트가 직접 호출되지 않고 정해진 경유 지점을 통해 호출된 것이
   확인된다.

### User Story 4 - 가명처리와 재식별 위험 자동 게이트 (Priority: P4)

실명 기반 표준 데이터를 가명처리해 연구용 데이터를 만든다. 그다음 시스템이 자동으로
재식별 위험을 점검한다. 코호트가 너무 작거나, 희귀한 진단코드 조합이 있거나, 극단적인
연령값이 남아 있으면 게이트가 걸린다. 게이트에 걸리면 사람이 승인 화면에 도달하지
못한다.

**Why this priority**: 반출은 되돌릴 수 없다. 나간 데이터는 회수할 수 없으므로 위험
점검은 반출 경로가 열리기 전에 자리 잡아야 한다. 나중에 붙이면 이미 나간 데이터에
소급 적용할 수 없다.

**Independent Test**: 실명 데이터를 가명처리해 연구용 데이터를 만들고, 최소 코호트
크기에 미달하는 사례에서 자동 게이트가 걸려 승인 단계로 진행되지 않는 것을 확인하면
검증 완료.

**Acceptance Scenarios**:

1. **Given** 실명 기반 표준 데이터가 있을 때, **When** 가명처리를 수행하면, **Then**
   연구용 데이터가 생성되고 실명 식별자가 남지 않는다.
2. **Given** 연구용 데이터가 생성되었을 때, **When** 재식별 위험 점검이 수행되면,
   **Then** 사람의 개입 없이 자동으로 판정이 이루어진다.
3. **Given** 코호트 크기가 정해진 최소값에 미달할 때, **When** 위험 점검을 수행하면,
   **Then** 게이트가 걸리고 반출 승인 단계로 진행되지 않는다.
4. **Given** 희귀한 값 조합이 포함되어 있을 때, **When** 위험 점검을 수행하면,
   **Then** 게이트가 걸린다.
5. **Given** 극단적인 연령값이 남아 있을 때, **When** 위험 점검을 수행하면, **Then**
   게이트가 걸린다.
6. **Given** 위험 점검이 게이트를 걸었을 때, **When** 사용자가 반출 승인을 시도하면,
   **Then** 승인 자체가 불가능하다.
7. **Given** 위험 점검이 수행되었을 때, **When** 결과를 조회하면, **Then** 어떤 기준에
   걸렸는지 또는 모든 기준을 통과했는지가 확인된다.
8. **Given** 위험 점검 결과가 기록되었을 때, **When** 감사 이력을 조회하면, **Then**
   점검 시각과 적용된 기준값이 확인된다.

### User Story 5 - 반출 승인과 패키지 (Priority: P5)

자동 게이트를 통과한 연구용 데이터에 대해 승인 권한을 가진 사람이 반출을 승인한다.
승인되면 반출 패키지가 만들어지고, 그 시점의 데이터 스냅샷 버전과 감사 기록이 함께
남는다.

**Why this priority**: 앞선 모든 통제가 갖춰진 뒤 마지막에 열리는 문이다. 병원 밖으로
데이터가 나가는 유일한 경로이므로 가장 마지막에 신중히 붙인다.

**Independent Test**: 자동 게이트를 통과한 요청에 대해 승인자가 승인하고, 반출 패키지가
생성되며 사용된 스냅샷 버전과 승인자·승인 시각이 이력에 남으면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 자동 게이트를 통과한 요청일 때, **When** 승인 권한자가 승인하면, **Then**
   반출 패키지가 생성된다.
2. **Given** 승인 권한이 없는 사용자일 때, **When** 승인을 시도하면, **Then** 요청이
   거부된다.
3. **Given** 반출 패키지가 생성되었을 때, **When** 내용을 확인하면, **Then** 가명처리된
   연구용 데이터만 포함되어 있고 실명 기반 데이터는 포함되지 않는다.
4. **Given** 반출 패키지가 생성되었을 때, **When** 반출 이력을 조회하면, **Then** 사용된
   데이터 스냅샷 버전이 기록되어 있다.
5. **Given** 반출이 이루어졌을 때, **When** 감사 이력을 조회하면, **Then** 요청 식별자,
   승인자, 승인 시각, 반출 대상 범위가 확인된다.
6. **Given** 이미 반출된 요청일 때, **When** 되돌리기를 시도하면, **Then** 되돌릴 수
   없음이 안내된다.
7. **Given** 반출 이후 어떤 환자가 동의를 철회했을 때, **When** 이후 요청에서 그
   환자를 조회하면, **Then** 새 요청의 코호트에서 제외된다.

### Edge Cases

- SDM 요청 중간에 어떤 환자가 동의를 철회하면 진행 중인 요청은 어떻게 되는가? 진행 중인
  요청의 코호트는 동의 대조 시점에 확정된 것을 유지하고, 철회는 이후 요청부터 반영된다.
- 동의 정보를 조회할 수 없으면 어떻게 되는가? 동의 대조 단계가 실패하고 코호트가
  확정되지 않으므로 이후 단계로 진행하지 않는다. 동의 여부를 알 수 없는 환자를 동의한
  것으로 간주해서는 안 된다.
- 비정형구조화나 용어매핑에서 AI 응답을 받지 못하면 어떻게 되는가? 해당 단계가 실패로
  기록되고 실행이 종료된다. 매핑되지 않은 값을 임의로 채우지 않는다.
- CDM 스냅샷의 manifest에 기록할 모델 버전을 알 수 없으면 어떻게 되는가? 스냅샷을
  유효한 자산으로 확정하지 않는다.
- 같은 SDM 워크스페이스에 여러 반출 요청이 동시에 들어오면 어떻게 되는가? 워크스페이스
  단위 순차 실행 규칙에 따라 대기열에 쌓여 차례로 처리된다.
- 재식별 위험 기준값이 요청 처리 도중에 변경되면 어떻게 되는가? 진행 중인 요청은 점검
  시점의 기준값을 적용하고, 적용된 기준값을 결과에 함께 기록한다.
- 가명처리 이후 실명 데이터는 어떻게 되는가? 실명 데이터는 워크스페이스 안에 남고 제한
  롤 접근 대상으로 유지된다. 반출 대상이 되는 것은 가명처리된 연구용 데이터뿐이다.
- SDM과 CDM이 같은 EHR을 동시에 추출하면 서로 영향을 주는가? 두 워크스페이스는 독립이며
  중간 산출물을 공유하지 않는다. 각자 추출한다.
- 반출 패키지 생성 도중 실패하면 어떻게 되는가? 승인은 유효하되 패키지는 미생성으로
  남고, 부분 생성된 패키지는 반출 대상이 되지 않는다.
- SDM 요청이 취소되면 그때까지 만들어진 실명 데이터는 어떻게 되는가? 기능 002의 중단
  실행 처리 규칙에 따라 다음 실행이 시작될 때 삭제되고 처음부터 다시 적재된다.
- 재식별 위험 점검을 통과했으나 승인 없이 오래 방치된 요청은 어떻게 되는가? 승인 전
  상태로 남으며, 승인 시점에 점검 결과가 여전히 유효한지 다시 확인한다.

## Requirements *(mandatory)*

### Functional Requirements

**워크스페이스 공통**

- **FR-001**: 시스템은 SDM과 CDM 워크스페이스를 서로 독립적으로 운영해야 하며, 한
  워크스페이스의 산출물을 다른 워크스페이스가 입력으로 사용해서는 안 된다.
- **FR-002**: 시스템은 SDM과 CDM이 같은 병원 EHR을 각자 독립적으로 추출하도록 해야 하며,
  두 워크스페이스가 중간 산출물을 공유해서는 안 된다.
- **FR-003**: 시스템은 파이프라인이 AI 컴포넌트를 직접 호출하지 않고 정해진 경유 지점을
  통해서만 호출하도록 해야 한다.
- **FR-004**: 시스템은 AI 컴포넌트를 사용한 모든 결과에 대해 모델 버전과 프롬프트 버전을
  함께 기록해야 한다.
- **FR-005**: 시스템은 워크스페이스 유형에 따라 수행할 단계 구성이 달라지도록 해야 하며,
  각 유형의 단계 구성은 워크스페이스 생성 시 확정되어야 한다.
- **FR-006**: 시스템은 게이트가 걸린 단계에서 이후 단계로 진행하지 않아야 한다.
- **FR-007**: 시스템은 ADMET 유형의 파이프라인을 제공하지 않는다. 이번 범위의 파이프라인은
  SDM과 CDM 두 가지다.

**CDM 워크스페이스**

- **FR-008**: 시스템은 CDM 워크스페이스에서 적재, 적재 검증, 용어매핑, 변환, CDM 품질
  검증 다섯 단계를 순서대로 수행해야 한다.
- **FR-009**: 시스템은 CDM의 용어매핑을 요청할 때 대상 표준을 OMOP으로 지정해야 한다.
- **FR-010**: 시스템은 CDM 산출물을 스냅샷으로 보관해야 하며, 이 스냅샷을 다시 생성
  가능한 파생물이 아니라 보존 대상 원본 자산으로 다뤄야 한다.
- **FR-011**: 시스템은 각 CDM 스냅샷과 함께 vocabulary 버전, 변환 정의 버전, 모델 버전,
  프롬프트 버전을 담은 manifest를 보관해야 한다.
- **FR-012**: 시스템은 manifest에 기록할 정보가 하나라도 확인되지 않으면 해당 스냅샷을
  유효한 자산으로 확정해서는 안 된다.
- **FR-013**: 시스템은 같은 입력으로 CDM을 반복 실행했을 때 결과가 달라지는 것을 오류로
  다뤄서는 안 된다.
- **FR-014**: 사용자는 과거 CDM 스냅샷과 그 manifest를 조회할 수 있어야 한다.

**SDM 워크스페이스 — 요청과 동의**

- **FR-015**: 시스템은 SDM 워크스페이스의 작업을 요청 단위로 시작해야 한다. 정기 실행
  주기로 SDM 파이프라인을 시작해서는 안 된다.
- **FR-016**: 시스템은 요청 접수 시 환자 목록과 요청 항목 범위를 입력받고, 요청 식별자,
  접수자, 접수 시각, 요청 인원을 기록해야 한다.
- **FR-017**: 시스템은 동의 대조를 파이프라인 내부의 명시적 단계로 수행해야 하며,
  파이프라인 밖의 사전 절차로 대체해서는 안 된다.
- **FR-018**: 시스템은 동의 대조에서 미동의자와 동의를 철회한 사람을 코호트에서 제외해야
  한다.
- **FR-019**: 시스템은 동의 대조 결과로 요청 인원, 확정 코호트 인원, 제외 인원을 사유별로
  기록해야 하며, 이 수치는 나중에 다시 조회할 수 있어야 한다.
- **FR-020**: 시스템은 동의 여부를 확인할 수 없는 환자를 동의한 것으로 간주해서는 안
  되며, 동의 정보를 조회할 수 없으면 코호트를 확정하지 않아야 한다.
- **FR-021**: 시스템은 확정된 코호트가 0명인 경우 이후 단계로 진행하지 않아야 한다.
- **FR-022**: 시스템은 동의를 철회한 환자를 이후 요청의 코호트에서 제외해야 한다. 이미
  확정된 진행 중인 요청의 코호트는 대조 시점 상태를 유지한다.
- **FR-023**: 시스템은 [NEEDS CLARIFICATION: 동의 상태 정보의 출처 — 병원 내 별도 동의
  관리 시스템에서 조회하는지, EHR 안의 동의 항목을 읽는지, 요청과 함께 외부에서 전달받는지에
  따라 동의 대조 단계의 구현 범위와 신뢰 근거가 달라짐].

**SDM 워크스페이스 — 실명 표준 데이터 생성**

- **FR-024**: 시스템은 EHR 추출을 확정된 코호트에 속한 환자로 한정해야 한다.
- **FR-025**: 시스템은 EHR 추출 이후 적재 검증을 수행하고, 검증 실패 시 이후 단계로
  진행하지 않아야 한다.
- **FR-026**: 시스템은 비정형 기록을 구조화 필드로 변환하는 단계를 수행해야 한다.
- **FR-027**: 시스템은 용어를 SNOMED CT, LOINC, RxNorm, ATC를 포함한 대상 표준 체계로
  매핑해야 하며, 사용된 vocabulary 버전을 기록해야 한다.
- **FR-028**: 시스템은 매핑되지 않은 값을 임의로 채워서는 안 되며, 미매핑 상태로 남겨야
  한다.
- **FR-029**: 시스템은 변환 이후 변환 검증을 수행하고, 검증 실패 시 이후 단계로 진행하지
  않아야 한다.
- **FR-030**: 시스템은 실명 기반 표준 데이터의 전 계층을 제한 롤 접근 대상으로 다뤄야
  한다.

**SDM 워크스페이스 — 가명처리와 재식별 위험 게이트**

- **FR-031**: 시스템은 실명 기반 표준 데이터를 가명처리해 연구용 데이터를 생성해야 하며,
  연구용 데이터에 실명 식별자가 남아서는 안 된다.
- **FR-032**: 시스템은 재식별 위험 점검을 사람의 개입 없이 자동으로 수행해야 한다.
- **FR-033**: 시스템은 재식별 위험 점검에서 최소 코호트 크기, 희귀 값 조합, 극단 연령값을
  포함한 기준을 평가해야 한다.
- **FR-034**: 시스템은 재식별 위험 점검에 걸린 요청에 대해 반출 승인 자체가 불가능하게
  해야 한다. 사람의 판단으로 게이트를 넘길 수 없어야 한다.
- **FR-035**: 시스템은 재식별 위험 점검 결과에 어떤 기준에 걸렸는지 또는 전부 통과했는지와,
  점검 시각과 적용된 기준값을 함께 기록해야 한다.
- **FR-036**: 시스템은 진행 중인 요청에 대해 점검 시점의 기준값을 적용해야 하며, 이후
  기준값이 바뀌어도 소급 적용하지 않아야 한다.
- **FR-037**: 시스템은 [NEEDS CLARIFICATION: 재식별 위험 기준값(최소 코호트 크기, 희귀
  값 조합의 판정 방식, 극단 연령의 경계)을 누가 어떤 절차로 정하고 변경하는지 — 기관·IRB
  정책 사항이라 임의 기본값을 둘 수 없고, 변경 권한과 변경 이력 관리 범위가 달라짐].

**SDM 워크스페이스 — 반출 승인과 패키지**

- **FR-038**: 시스템은 반출 승인을 승인 권한을 가진 사람만 수행할 수 있게 해야 한다.
- **FR-039**: 시스템은 승인 이후에만 반출 패키지를 생성해야 한다.
- **FR-040**: 시스템은 반출 대상을 가명처리된 연구용 데이터로 한정해야 하며, 실명 기반
  데이터가 반출 패키지에 포함되어서는 안 된다.
- **FR-041**: 시스템은 반출 이력에 사용된 데이터 스냅샷 버전을 기록해야 한다.
- **FR-042**: 시스템은 반출 이력에 요청 식별자, 승인자, 승인 시각, 반출 대상 범위를
  기록해야 한다.
- **FR-043**: 시스템은 이미 반출된 요청에 대한 되돌리기를 제공해서는 안 되며, 되돌릴 수
  없음을 사용자에게 알려야 한다.
- **FR-044**: 시스템은 승인 시점에 재식별 위험 점검 결과가 여전히 유효한지 확인해야 한다.

### Key Entities

- **워크스페이스 유형별 단계 구성**: 유형마다 다른 처리 단계의 순서와 게이트 위치.
  CDM은 5단계이고 게이트가 검증 지점에만 있으며, SDM은 9단계에 게이트가 다섯 곳 있다.
- **반출 요청**: SDM 워크스페이스 작업의 시작 단위. 요청 식별자, 접수자, 접수 시각,
  환자 목록, 요청 항목 범위, 상태를 갖는다.
- **동의 대조 결과**: 요청 인원, 확정 코호트 인원, 제외 인원과 사유별 내역. 확정 이후
  변하지 않는다.
- **코호트**: 동의 대조를 통과해 처리 대상으로 확정된 환자 집합. 이후 모든 단계의 처리
  범위를 한정한다.
- **게이트**: 다음 단계로 넘어가기 위한 통과 조건. 검증 게이트, 자동 판정 게이트, 사람
  승인 게이트로 나뉜다.
- **재식별 위험 점검 결과**: 자동 판정의 결과. 통과 여부, 걸린 기준, 적용된 기준값,
  점검 시각을 갖는다.
- **반출 패키지**: 승인 이후 생성되는 반출 대상 산출물. 가명처리된 연구용 데이터로만
  구성된다.
- **반출 이력**: 요청 식별자, 승인자, 승인 시각, 반출 대상 범위, 사용된 스냅샷 버전.
- **CDM 스냅샷**: 재생성할 수 없는 보존 대상 원본 자산.
- **manifest**: 스냅샷의 생성 조건 기록. vocabulary 버전, 변환 정의 버전, 모델 버전,
  프롬프트 버전을 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: SDM과 CDM 워크스페이스 사이에 중간 산출물이 공유된 사례가 0건이다.
- **SC-002**: AI 컴포넌트를 사용한 결과 중 모델 버전 또는 프롬프트 버전이 누락된 사례가
  0건이다.
- **SC-003**: CDM 스냅샷 중 manifest가 누락된 사례가 0건이다.
- **SC-004**: 동의 대조를 거치지 않고 EHR이 추출된 사례가 0건이다.
- **SC-005**: 확정된 코호트 밖의 환자 데이터가 추출된 사례가 0건이다.
- **SC-006**: 담당자가 특정 요청에 대해 요청 인원과 확정 코호트 인원, 제외 사유별 인원을
  확인하는 데 1분 이내가 걸린다.
- **SC-007**: 제한 롤이 없는 사용자가 실명 기반 표준 데이터의 어느 계층에든 접근에
  성공한 사례가 0건이다.
- **SC-008**: 재식별 위험 점검을 통과하지 않은 요청이 반출된 사례가 0건이다.
- **SC-009**: 사람의 판단으로 자동 게이트가 우회된 사례가 0건이다.
- **SC-010**: 반출 이력 중 사용된 스냅샷 버전이 누락된 사례가 0건이다.
- **SC-011**: 실명 기반 데이터가 반출 패키지에 포함된 사례가 0건이다.
- **SC-012**: 승인 권한이 없는 사용자가 반출을 승인한 사례가 0건이다.
- **SC-013**: 동의를 철회한 환자가 이후 요청의 코호트에 포함된 사례가 0건이다.
- **SC-014**: 감사자가 임의의 반출 건에 대해 요청부터 승인까지의 경로를 추적하는 데
  5분 이내가 걸린다.
- **SC-015**: 미매핑 값이 임의의 값으로 채워진 사례가 0건이다.

## Assumptions

- 이 명세는 각 워크스페이스 유형이 어떤 단계를 어떤 순서로 수행하고 어디에 게이트가
  놓이는지를 정한다. 각 단계 내부의 변환 규칙, 매핑 사전, 검증 규칙의 내용은 별도
  기능이다.
- ADMET 워크스페이스는 이번 범위에서 제외한다. 원문 12.3은 ADMET을 1차 구현 대상으로
  제안했으나 제외 지시를 받았으므로, 이번 범위의 파이프라인은 SDM과 CDM 두 가지다.
  기능 001이 유형을 SDM·CDM으로 한정한 것과 일치한다.
- 워크스페이스 생성·설정·권한·삭제는 기능 001이, 실행 트리거와 상태·이력 조회는 기능
  002가, 검증 결과 표시는 기능 003이 담당한다. 이 명세는 그 위에서 유형별 단계 구성을
  정의한다.
- SDM 워크스페이스는 요청 단위로 동작하므로 기능 001의 "실행 주기" 설정을 사용하지
  않는다. CDM은 실행 주기를 사용한다. 기능 001의 설정 항목 자체는 바꾸지 않고, SDM에서는
  그 항목이 비어 있는 것으로 다룬다.
- 기능 002는 워크스페이스마다 실행 대상 파이프라인이 하나라고 전제한다. SDM의 요청
  단위 실행도 같은 파이프라인의 실행 건이며, 요청 식별자가 실행 건에 함께 기록된다.
  워크스페이스 단위 순차 실행 규칙이 그대로 적용되어 여러 요청은 대기열에서 차례로
  처리된다.
- 기능 003은 검증 지점을 적재 검증과 변환 검증 두 곳으로 정의했다. SDM은 3단계와
  6단계가, CDM은 적재 검증과 CDM 품질 검증이 각각 그 두 지점에 대응한다. SDM의 8단계
  재식별 위험 점검은 데이터 품질 검증이 아니라 반출 통제 게이트이므로 품질 리포트의
  검증 결과에 포함되지 않는다.
- 헌법 원칙 II의 "연구용 SDM만 반출 대상이 된다"는 이 명세의 7단계 가명처리 산출물을
  가리킨다. 기능 001에서 기록해 둔 용어 불일치 우려는 해소된 것으로 본다. CDM은 가명
  기반 연구용 데이터이지만 반출 경로의 대상이 아니다.
- 반출은 헌법 원칙 II가 정한 유일한 예외 경로이며, 별도 통제 절차의 구체적 내용은
  기관 정책을 따른다. 이 명세는 시스템이 강제해야 할 게이트와 기록 의무만 정한다.
- 재식별 위험 점검은 자동 판정만 다룬다. 게이트에 걸린 요청을 어떻게 조정해 다시
  시도할지(코호트 확대, 항목 축소 등)는 요청자가 새 요청으로 수행한다.
- 가명처리 이후에도 실명 기반 데이터는 워크스페이스에 남아 제한 롤 접근 대상으로
  유지된다. 실명 데이터의 삭제 시점은 기능 001의 워크스페이스 생명주기를 따른다.
- vocabulary와 모델 가중치는 헌법 원칙 I에 따라 오프라인 반입 자산이다. 이 명세는
  반입된 자산의 버전을 기록하는 의무만 정하고, 반입 절차 자체는 범위 밖이다.
- 동의 철회 시 이미 반출된 데이터에 대한 통지 의무 여부는 IRB 확인이 필요한 사항으로
  원문에 명시되어 있다. 확인 전까지 통지 기능은 이 명세의 범위 밖으로 둔다.
