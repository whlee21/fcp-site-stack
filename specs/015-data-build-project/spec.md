## Clarifications

### Session 2026-09-01

- Q: 데이터 생성 프로젝트는 필수인가 선택인가? → A: **필수다.** SDM/OMOP CDM ETL 워크스페이스의
  모든 실행이 데이터 생성 프로젝트를 경유한다. 경유하지 않는 경로를 남기면 "이 실행은 어느
  경로인가"가 매번 판정 대상이 되고, 권한·추적 규칙을 두 경로에 이중으로 유지해야 한다. 대가로
  기존 ETL 워크스페이스에 기본 데이터 생성 프로젝트를 만드는 이행이 필요하다 (FR-007, FR-061).
- Q: 데이터 생성 프로젝트와 타깃은 1:1인가 1:N인가? → A: **1:1이다.** 헌법이 "물리 스키마 하나를
  만드는" 단위로 규정한 문언을 그대로 따른다. 귀결로 연도별 동결 타깃마다 데이터 생성 프로젝트를 새로 만들어야
  하므로, **같은 워크스페이스의 확정된 다른 데이터 생성 프로젝트 정의를 파생 기준선으로 삼는 것**을 허용한다.
  그러지 않으면 해마다 같은 편집을 반복해야 한다 (FR-034, FR-062).
- Q: 데이터 생성 프로젝트 스코프 롤을 신설하나요? → A: **신설하지 않는다.** 워크스페이스 스코프
  롤이 그 워크스페이스의 모든 데이터 생성 프로젝트에 동일하게 적용된다. 롤 층위를 늘려도 통제가 늘지 않는다.
  데이터 생성 프로젝트별 최소권한 분리를 포기하는 대가이며, 어느 데이터 생성 프로젝트의 정의를 누가 저작·확정했는지는
  확정 기록으로 식별 가능해야 한다 — 기능 013이 SoD를 풀어준 영역에 붙인 보완과 같은 형태다
  (FR-059, FR-064).

## 용어 고지 — 데이터 생성 프로젝트와 연구 프로젝트

헌법 v4.2.2는 접두 없는 "프로젝트" 사용을 금지한다(MUST NOT). 어느 개념인지 매번 판정하게
되고, 그 판정 하나가 틀리면 범위 경계가 뚫리기 때문이다. 이 문서가 다루는 것은 **데이터 생성
프로젝트**이며, 기능 009의 **연구 프로젝트**와 다른 개념이다.

| | 데이터 생성 프로젝트 (이 기능) | 연구 프로젝트 (기능 009) |
| --- | --- | --- |
| 목적 | 물리 스키마를 만드는 정의 단위 | 연구 목적·요청 단위 작업 묶음 |
| 산출물 | 타깃(물리 스키마) | 추출물(Extract) |
| 소비자 | 운영 측 | 연구자 |
| 정의 내용 | 워크스페이스 공통 스크립트를 불러와 수정 | 멤버십·추출물 수명 |
| 헌법 판정 | **범위 안** (v4.2.2 명시) | **범위 밖** (연구자 대상 기능 배제) |

이 기능은 헌법 v4.2.2의 `TODO(DATA_BUILD_PROJECT_MODEL)`을 확정한다. 기능 014(Backend API)의
계획이 `G1`으로 보류한 도메인이 이것이며, 이 스펙이 확정되면 그 보류가 풀린다.

## 이 기능이 바꾸는 것

데이터 생성 프로젝트는 새 화면 하나가 아니라 **기존 스펙의 구조를 건드리는 계층**이다. 무엇이
어떻게 바뀌는지를 먼저 못 박는다.

| 스펙 | 지금 전제 | 이 기능이 바꾸는 것 |
| --- | --- | --- |
| 011 FR-022·FR-023 | 저작 대상 공통 스크립트가 **워크스페이스당 1벌** | 데이터 생성 프로젝트가 그 1벌을 **기준선**으로 파생해 자체 정의를 갖는다. 워크스페이스 기준선은 그대로 1벌로 남는다 |
| 011 FR-040·FR-041 | 워크스페이스 상태(준비중·운영 가능)가 실행 접수의 유일한 게이트 | 워크스페이스 게이트는 유지되고, 그 아래 **데이터 생성 프로젝트 단위 게이트**가 하나 더 생긴다. 데이터 생성 프로젝트를 경유하지 않는 실행 경로는 사라진다 |
| 009 | 타깃은 워크스페이스가 소유하는 장기 산출물 | 타깃에 **그것을 만든 데이터 생성 프로젝트** 연결이 추가되고, 둘은 **1:1**이다. 타깃의 소유·보존·접근은 009가 계속 소유한다 |
| 002 | 실행 건은 워크스페이스에 귀속 | 실행 건이 데이터 생성 프로젝트 정의 버전을 참조한다. 필수 귀속(타깃)은 바뀌지 않는다 |
| 013 | 롤은 전역·워크스페이스·연구 프로젝트 세 스코프 | **바뀌지 않는다** — 데이터 생성 프로젝트 스코프 롤을 신설하지 않는다(FR-059). 워크스페이스 스코프 롤이 그 워크스페이스의 모든 데이터 생성 프로젝트에 적용된다 |
| 005 | 워크스페이스가 실행에 쓸 정의 버전을 고정 | 데이터 생성 프로젝트마다 고정 버전을 갖는다. 승격 규칙은 그대로 |

**바꾸지 않는 것**: 데이터 계층 구성(`{ws}_landing`·`{ws}_work`·`{ws}_mart`·`{ws}_pseudo`), PHI
제한 범위, 워크스페이스 ID 불변성, 실행 추적 태그, 마스킹 규칙. 데이터 생성 프로젝트는 이 위에 얹히는 정의
단위이며 경계를 재정의하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 데이터 생성 프로젝트 개설과 기준선 파생 (Priority: P1)

운영 측 인원이 운영 가능 상태의 SDM ETL 또는 OMOP CDM ETL 워크스페이스 안에 데이터 생성
프로젝트를 만든다. 개설 시점에 워크스페이스의 확정된 공통 스크립트 집합이 **파생 기준선**으로
지정되고, 데이터 생성 프로젝트는 그것과 내용이 같은 자기 정의를 갖고 출발한다.

파생은 복사이지 참조가 아니다. 기준선이 나중에 새 버전으로 승격되어도 이미 파생된 데이터 생성 프로젝트는
따라가지 않는다. 기능 005가 "새 버전이 확정되어도 워크스페이스의 고정 버전은 자동으로 바뀌지
않는다"고 정한 것과 같은 논리다 — 정의가 발밑에서 바뀌면 산출물의 재현성이 깨진다.

**Why this priority**: 파생이 없으면 데이터 생성 프로젝트는 빈 껍데기다. 이 스토리만 있어도 "이 워크스페이스에
어떤 데이터 생성 단위가 있는가"에 답할 수 있고, 나머지 스토리가 얹힐 대상이 생긴다.

**Independent Test**: 운영 가능 워크스페이스에 데이터 생성 프로젝트를 개설해 파생 기준선이 정의 버전
식별자로 기록되고, 데이터 생성 프로젝트 정의 내용이 기준선과 일치하며, 이후 기준선 승격이 데이터 생성 프로젝트 정의를
바꾸지 않는 것을 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 운영 가능 상태의 OMOP CDM ETL 워크스페이스, **When** 데이터 생성 프로젝트를
   개설하면, **Then** 적재·변환·워크플로 세 종류 정의가 기준선과 같은 내용으로 파생된다.
2. **Given** 운영 가능 상태의 SDM ETL 워크스페이스, **When** 데이터 생성 프로젝트를 개설하면,
   **Then** 자유서식 비식별화 정의를 포함한 네 종류가 파생된다.
3. **Given** 준비중 상태 워크스페이스, **When** 데이터 생성 프로젝트 개설을 시도하면, **Then** 파생할
   기준선이 없다는 사유로 거부된다.
4. **Given** 관리 유형 워크스페이스(SDM 또는 OMOP CDM Vocabulary/Mapping 관리), **When**
   데이터 생성 프로젝트 개설을 시도하면, **Then** 거부된다.
5. **Given** 파생을 마친 데이터 생성 프로젝트, **When** 파생 기준선을 조회하면, **Then** 형상 관리 저장소의
   커밋 식별자로 확인된다.
6. **Given** 파생 이후 워크스페이스 기준선이 새 버전으로 승격된 상태, **When** 데이터 생성 프로젝트 정의를
   조회하면, **Then** 파생 시점 내용 그대로이고 자동으로 바뀌지 않았다.
7. **Given** 워크스페이스에 배정되지 않은 사용자, **When** 데이터 생성 프로젝트 개설을 시도하면, **Then**
   거부된다.

### User Story 2 - 파생 정의의 수정과 확정 (Priority: P1)

데이터 생성 프로젝트 저작자가 파생된 정의를 데이터 생성 프로젝트 목적에 맞게 고친다. 고친 정의는 워크스페이스 기준선을
건드리지 않는다. 수정된 정의는 dry-run과 시뮬레이션을 통과하고 확정을 받아야 실행에 쓸 수 있다 —
워크스페이스 파이프라인이 처음 등록될 때 거친 것과 같은 게이트다.

확정 권한은 그 워크스페이스 스코프의 `파이프라인 확정자` 롤이 갖고, 저작자는 자기 저작물을
확정할 수 없다. 데이터 생성 프로젝트가 늘어난다고 이 분리가 느슨해지면, 데이터 생성 프로젝트는 확정 게이트를 우회하는
경로가 된다.

**Why this priority**: 수정할 수 없는 파생은 파생일 이유가 없다. 그리고 수정을 허용하는 순간
확정 게이트가 데이터 생성 프로젝트 단위로 필요해지므로, 둘은 같은 스토리다.

**Independent Test**: 데이터 생성 프로젝트 정의를 고쳐 dry-run·시뮬레이션·확정을 통과시키고, 워크스페이스
기준선이 그대로임을 확인하고, 저작자 본인의 확정 시도가 거부되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 파생된 데이터 생성 프로젝트 정의, **When** 저작자가 변환 정의를 수정하면, **Then** 데이터 생성 프로젝트
   정의만 바뀌고 워크스페이스 기준선은 그대로다.
2. **Given** 수정된 데이터 생성 프로젝트 정의, **When** 확정 없이 실행을 요청하면, **Then** 거부된다.
3. **Given** 저작 대상 중 하나가 비어 있는 데이터 생성 프로젝트 정의, **When** dry-run 진입을 시도하면,
   **Then** 거부된다.
4. **Given** dry-run과 시뮬레이션을 통과한 데이터 생성 프로젝트 정의, **When** `파이프라인 확정자`가
   확정하면, **Then** 확정 기록에 확정자·시각·정의 버전·AI 생성분과 사람 편집분의 구분이 남는다.
5. **Given** 데이터 생성 프로젝트 정의를 저작한 사용자, **When** 자기 저작물의 확정을 시도하면, **Then**
   거부된다.
6. **Given** 확정된 데이터 생성 프로젝트 정의, **When** 내용을 수정하면, **Then** dry-run 미통과 상태로
   되돌아가고 다시 게이트를 통과해야 확정할 수 있다.
7. **Given** 확정이 반려된 데이터 생성 프로젝트, **When** 상태를 확인하면, **Then** 저작 단계로 되돌아가
   있고 반려 사유가 기록되어 있다.
8. **Given** 실데이터 표본을 쓴 데이터 생성 프로젝트 시뮬레이션, **When** 종료되면, **Then** 임시 영역이
   파기되고 그 기간 접근 통제가 해당 워크스페이스 제한 계층과 동등했음이 확인된다.

### User Story 3 - 데이터 생성 프로젝트 실행과 타깃 산출 (Priority: P1)

확정된 데이터 생성 프로젝트 정의로 잡을 실행해 물리 스키마를 만든다. 만들어진 물리 스키마는 기능 009의
타깃 레지스트리에 등록되고, 어느 데이터 생성 프로젝트의 어느 정의 버전이 만들었는지가 생성 조건
기록(provenance)에 남는다.

실행은 워크스페이스의 데이터 계층을 작업 공간으로 쓴다. 데이터 생성 프로젝트마다 계층을 새로 만들지 않는다 —
계층은 접근 통제의 단위이고 데이터 생성 프로젝트는 정의의 단위여서 층위가 다르다. 같은 이유로 한
워크스페이스의 데이터 생성 프로젝트들은 실행 대기열을 공유한다.

**Why this priority**: 산출물이 나오지 않으면 데이터 생성 프로젝트는 문서다. 그리고 타깃 연결이 없으면
"이 스키마를 누가 왜 만들었나"에 답할 수 없어 재현성이 깨진다.

**Independent Test**: 확정된 데이터 생성 프로젝트로 잡을 실행해 타깃이 레지스트리에 등록되고, 그 생성 조건
기록이 실행에 쓰인 데이터 생성 프로젝트 고정 버전을 가리키며, 실행에 `workspace_id` 태그가 붙으면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 확정된 데이터 생성 프로젝트, **When** 잡을 실행하면, **Then** 산출된 물리 스키마가
   타깃 레지스트리에 등록되고 그 타깃에 생성 데이터 생성 프로젝트 식별자가 기록된다.
2. **Given** 완료된 데이터 생성 프로젝트 실행, **When** 타깃의 생성 조건 기록을 조회하면, **Then** 용어사전
   버전·데이터 생성 프로젝트 정의 버전·원천 추출 시각·대상 표준 버전이 확인되고, 정의 버전은 워크스페이스
   기준선이 아니라 실행에 쓰인 데이터 생성 프로젝트 고정 버전이다.
3. **Given** 임의의 데이터 생성 프로젝트 실행, **When** 실행 태그를 확인하면, **Then** `workspace_id`가
   붙어 있다.
4. **Given** 동결(frozen) 상태 타깃, **When** 그 타깃을 갱신 대상으로 실행을 요청하면, **Then**
   접수되지 않는다.
5. **Given** 같은 워크스페이스의 데이터 생성 프로젝트 두 개, **When** 둘의 실행을 동시에 요청하면, **Then**
   하나가 실행되고 다른 하나는 워크스페이스 대기열에 순번을 받는다.
6. **Given** 중단된 데이터 생성 프로젝트 실행, **When** 같은 워크스페이스의 다음 실행이 시작되면, **Then**
   중단분 정리가 기능 002의 규칙대로 수행된다.
7. **Given** 데이터 생성 프로젝트 실행 로그, **When** 화면에서 조회하면, **Then** 마스킹·요약·분량 상한이
   적용된 형태이고 정형 식별자가 노출되지 않는다.
8. **Given** SDM ETL 워크스페이스의 데이터 생성 프로젝트 산출물이 가명 계층에 놓이는 경우, **When** 그
   경로를 확인하면, **Then** 기능 012의 가명처리와 기능 008의 재식별 위험 점검 게이트를 우회하지
   않는다.

### User Story 4 - 기준선 리베이스 (Priority: P2)

워크스페이스 기준선이 새 버전으로 확정된 뒤, 운영자가 데이터 생성 프로젝트를 그 새 기준선으로 옮긴다.
자동으로 옮겨지지 않기 때문에 이 행위가 필요하다.

리베이스는 데이터 생성 프로젝트의 사람 편집분과 충돌할 수 있다. 충돌을 자동으로 병합하면 아무도 검토하지
않은 정의가 확정 게이트를 통과해 버린다. 충돌 지점을 제시하고 사람이 결정하게 하며, 리베이스를
거친 정의는 미확정 상태로 되돌아가 게이트를 다시 통과해야 한다.

**Why this priority**: 리베이스 없이도 데이터 생성 프로젝트는 동작한다 — 파생 시점 정의로 계속 돌면 된다.
그러나 기준선 개선이 데이터 생성 프로젝트에 영원히 닿지 못하면 기준선을 유지할 이유가 없어진다.

**Independent Test**: 기준선을 승격한 뒤 데이터 생성 프로젝트를 리베이스해 이전·새 기준선과 실행자·시각이
기록되고, 편집분 충돌이 자동 병합되지 않고 제시되며, 리베이스 후 정의가 미확정으로 돌아가면
검증 완료.

**Acceptance Scenarios**:

1. **Given** 새 기준선이 확정된 워크스페이스, **When** 데이터 생성 프로젝트를 리베이스하면, **Then** 이전
   기준선·새 기준선·실행자·시각이 기록된다.
2. **Given** 사람이 편집한 부분이 새 기준선과 충돌하는 데이터 생성 프로젝트, **When** 리베이스하면, **Then**
   자동 병합되지 않고 충돌 지점이 제시된다.
3. **Given** 리베이스를 마친 데이터 생성 프로젝트, **When** 상태를 확인하면, **Then** 미확정 상태이고 실행
   요청이 거부된다.
4. **Given** 여러 번 리베이스한 데이터 생성 프로젝트, **When** 파생 계보를 조회하면, **Then** 최초 기준선과
   리베이스 이력이 순서대로 확인된다.
5. **Given** 리베이스한 데이터 생성 프로젝트, **When** 리베이스 이전에 산출된 타깃의 생성 조건 기록을
   확인하면, **Then** 리베이스 이전 정의 버전을 그대로 가리킨다.

### User Story 5 - 데이터 생성 프로젝트 목록·역추적과 종료 (Priority: P3)

운영 측 인원이 워크스페이스의 데이터 생성 프로젝트 목록을 보고, 임의의 타깃에서 그것을 만든
데이터 생성 프로젝트로 거슬러 올라간다. 더 이상 실행하지 않는 데이터 생성 프로젝트는 종료한다.

종료해도 정의와 이력은 남는다. 이미 만들어진 타깃의 생성 조건 기록이 그 정의 버전을 가리키기
때문에, 정의를 지우면 타깃은 출처를 잃는다. 활성 타깃을 가진 데이터 생성 프로젝트는 폐기할 수 없다.

**Why this priority**: 목록과 종료가 없어도 생성은 된다. 그러나 데이터 생성 프로젝트가 쌓이면 무엇이 살아
있는지 알 수 없게 되고, 정의를 지운 타깃은 "그냥 오래된 데이터"가 된다.

**Independent Test**: 데이터 생성 프로젝트 목록에 이름·상태·기준선·고정 버전·산출 타깃이 나오고, 타깃에서
데이터 생성 프로젝트로 역추적되고, 종료 후에도 정의·이력이 남고, 활성 타깃을 가진 데이터 생성 프로젝트의 폐기가
거부되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 데이터 생성 프로젝트가 여럿인 워크스페이스, **When** 목록을 조회하면, **Then** 각 데이터 생성 프로젝트의
   이름·상태·파생 기준선·고정 버전·산출 타깃이 확인된다.
2. **Given** 임의의 타깃, **When** 출처를 조회하면, **Then** 그것을 만든 데이터 생성 프로젝트가
   확인된다.
3. **Given** 데이터 생성 프로젝트 목록, **When** 표시 내용을 확인하면, **Then** 기능 009의 연구
   프로젝트 항목이 섞여 있지 않다.
4. **Given** 종료된 데이터 생성 프로젝트, **When** 실행을 요청하면, **Then** 접수되지 않는다.
5. **Given** 종료된 데이터 생성 프로젝트, **When** 확정 정의와 확정·편집 이력을 조회하면, **Then** 보존되어
   있다.
6. **Given** 활성 타깃을 가진 데이터 생성 프로젝트, **When** 폐기를 시도하면, **Then** 거부된다.
7. **Given** 종료된 데이터 생성 프로젝트가 만든 타깃, **When** 타깃 상태를 확인하면, **Then** 데이터 생성 프로젝트 종료
   때문에 자동 폐기되지 않았고 기능 009의 보존 정책을 따른다.
8. **Given** 조회자 롤 보유자, **When** 데이터 생성 프로젝트 구성을 조회하면, **Then** 메타데이터는 보이고
   데이터 계층에는 접근할 수 없다.

### Edge Cases

- 워크스페이스가 운영 가능 상태에 이르기 전에 데이터 생성 프로젝트를 개설하려 하면? → 파생할 기준선이
  없으므로 거부한다(FR-005).
- 파생 기준선이 가리키는 커밋이 형상 관리 저장소에서 사라졌으면? → 그 데이터 생성 프로젝트의 실행과
  리베이스를 거부하고 불일치 상태로 표시한다. 기능 005가 "저장소에 없는 정의 버전을 참조하는
  실행은 거부"로 정한 것과 같다(FR-016).
- 데이터 생성 프로젝트 정의가 워크스페이스 기준선과 한 글자도 다르지 않은 상태로 확정을 요청하면? →
  거부하지 않는다. 파생 자체가 유효한 상태이며, 차이 없음이 결함은 아니다.
- 같은 워크스페이스의 두 데이터 생성 프로젝트가 같은 물리 스키마 이름을 산출하려 하면? → 타깃 레지스트리가
  물리 스키마 1:1 대응을 보장하므로 두 번째 등록이 거부된다(FR-035).
- 리베이스 중 워크스페이스 기준선이 또 승격되면? → 진행 중 리베이스는 착수 시점 기준선을
  대상으로 완료되고, 새 승격분은 다음 리베이스 대상이 된다(FR-018).
- 데이터 생성 프로젝트 개설자가 워크스페이스 배정에서 해제되면? → 그 사용자의 데이터 생성 프로젝트 접근이 즉시
  차단된다. 데이터 생성 프로젝트 권한은 워크스페이스 배정 위에만 성립한다(FR-056).
- 데이터 생성 프로젝트 실행이 만든 타깃이 동결된 뒤 그 데이터 생성 프로젝트를 리베이스하면? → 동결 타깃의 생성 조건
  기록은 그대로 유지되고, 리베이스 이후 실행은 다른 타깃을 대상으로만 가능하다(FR-040).
- 데이터 생성 프로젝트를 통해 연구자에게 산출물을 전달하려는 요청이 오면? → 헌법 범위 경계에
  걸린다. 그 경로를 만들지 않는다(FR-057).
- 데이터 생성 프로젝트 시뮬레이션이 비정상 종료되어 임시 영역이 남으면? → 기능 011의 파기 보증이 적용되며,
  잔존 영역은 제한 계층과 동등한 통제 아래 있다가 정리된다(FR-033).
- 이미 타깃을 가진 데이터 생성 프로젝트가 다른 물리 스키마를 만들려 하면? → 1:1 대응을 깨므로
  거부한다. 새 데이터 생성 프로젝트를 만들어야 한다(FR-034).
- 이행 대상 워크스페이스에 타깃이 여럿이면? → 타깃마다 데이터 생성 프로젝트를 하나씩 만들어
  연결한다. 1:1은 이행에도 그대로 적용된다(FR-034, FR-061).
- 파생원으로 삼은 데이터 생성 프로젝트가 나중에 폐기되면? → 파생 계보의 기록은 남고 파생된
  데이터 생성 프로젝트의 정의는 영향받지 않는다. 파생은 복사이지 참조가 아니기 때문이다(FR-012, FR-063).
- 데이터 생성 프로젝트 폐기와 워크스페이스 삭제 표시(기능 001)가 동시에 걸리면? → 워크스페이스 정리 절차가
  데이터 생성 프로젝트 정의와 이력을 함께 다루며, 타깃 폐기는 기능 009의 승인 절차를 거친다(FR-052).

## Requirements *(mandatory)*

### Functional Requirements

**개설과 소속**

- **FR-001**: 시스템은 데이터 생성 프로젝트를 SDM ETL 또는 OMOP CDM ETL 워크스페이스에 귀속된
  항목으로만 생성할 수 있어야 한다. 관리 유형 두 워크스페이스(SDM Vocabulary/Mapping 관리,
  OMOP CDM Vocabulary/Mapping 관리)에는 생성할 수 없어야 한다.
- **FR-002**: 시스템은 데이터 생성 프로젝트에 고유 식별자, 소속 워크스페이스, 논리 이름, 목적
  설명, 개설자, 개설 시각, 상태를 기록해야 한다.
- **FR-003**: 시스템은 한 워크스페이스 안에서 데이터 생성 프로젝트의 논리 이름이 중복되지 않게
  해야 한다.
- **FR-004**: 시스템은 데이터 생성 프로젝트의 소속 워크스페이스를 생성 후 변경할 수 없게 해야
  한다.
- **FR-005**: 시스템은 워크스페이스가 운영 가능 상태(기능 011 FR-040)에 이르기 전에는 데이터 생성
  프로젝트 개설을 거부해야 한다. 파생할 기준선이 존재하지 않기 때문이다.
- **FR-006**: 시스템은 데이터 생성 프로젝트를 개설할 수 있는 주체를 그 워크스페이스에 배정된
  사용자로 한정해야 한다.
- **FR-007**: 시스템은 SDM ETL·OMOP CDM ETL 워크스페이스의 모든 실행이 데이터 생성 프로젝트를
  경유하게 해야 한다. 데이터 생성 프로젝트를 경유하지 않는 실행 요청 경로를 두어서는 안 된다.
- **FR-008**: 시스템은 데이터 생성 프로젝트 개설을 감사 이력에 남겨야 한다 — 개설자, 시각,
  소속 워크스페이스, 파생 기준선.
- **FR-061**: 시스템은 이미 운영 중인 기존 SDM/OMOP CDM ETL 워크스페이스를 이행시켜야 한다 —
  확정된 기준선을 파생한 기본 데이터 생성 프로젝트를 만들고, 기존 타깃을 그 데이터 생성 프로젝트에 연결한다.
  이행 기록(대상 워크스페이스, 만들어진 데이터 생성 프로젝트, 연결된 타깃, 실행자, 시각)을 남겨야 한다.

**기준선 파생**

- **FR-009**: 시스템은 데이터 생성 프로젝트를 개설할 때 워크스페이스의 확정된 공통 스크립트
  집합을 **파생 기준선**으로 지정해야 한다.
- **FR-010**: 시스템은 파생 기준선을 형상 관리 저장소의 커밋 식별자(기능 005의 정의 버전)로
  기록해야 한다. 시점 표현이나 이름으로 기록해서는 안 된다.
- **FR-062**: 시스템은 파생 기준선의 출처를 그 워크스페이스의 공통 스크립트 기준선 또는 **같은
  워크스페이스의 확정된 다른 데이터 생성 프로젝트 정의** 중 하나로 허용해야 한다. 타깃 1:1 대응
  때문에 연도별 동결 타깃마다 데이터 생성 프로젝트를 새로 만들어야 하고, 그때 같은 편집을 반복하지 않게 하기
  위한 것이다. 다른 워크스페이스의 데이터 생성 프로젝트에서 파생해서는 안 된다.
- **FR-063**: 시스템은 파생 계보에 출처의 종류(워크스페이스 기준선 또는 데이터 생성 프로젝트)와
  그 식별자를 함께 기록해야 한다.
- **FR-011**: 시스템은 파생 대상에 그 워크스페이스 유형의 저작 대상 전 종류를 포함해야 한다 —
  OMOP CDM ETL은 적재·변환·워크플로 세 종류, SDM ETL은 여기에 자유서식 비식별화 정의를 더한
  네 종류(기능 011 FR-022).
- **FR-012**: 시스템은 파생 직후 데이터 생성 프로젝트 정의를 기준선과 동일한 내용으로 두어야 한다. 파생만으로
  내용이 달라져서는 안 된다.
- **FR-013**: 시스템은 데이터 생성 프로젝트 파생과 데이터 생성 프로젝트 정의 수정이 워크스페이스의 공통 스크립트 기준선을
  변경하지 못하게 해야 한다.
- **FR-014**: 시스템은 파생 이후 기준선이 새 버전으로 승격되어도(기능 005) 데이터 생성 프로젝트 정의를
  자동으로 바꾸지 않아야 한다.
- **FR-015**: 시스템은 운영자가 데이터 생성 프로젝트를 새 기준선으로 명시적으로 **리베이스**할 수 있게
  해야 하며, 이전 기준선·새 기준선·실행자·시각을 기록해야 한다.
- **FR-016**: 시스템은 파생 기준선이 가리키는 커밋을 형상 관리 저장소에서 찾을 수 없을 때 그
  데이터 생성 프로젝트의 실행과 리베이스를 거부하고 불일치 상태로 표시해야 한다.
- **FR-017**: 시스템은 리베이스가 데이터 생성 프로젝트의 사람 편집분과 충돌할 때 자동 병합하지 않고 충돌
  지점을 제시해야 한다.
- **FR-018**: 시스템은 진행 중 리베이스를 착수 시점 기준선을 대상으로 완료해야 한다. 진행 중에
  일어난 새 승격은 다음 리베이스 대상이 된다.
- **FR-019**: 시스템은 리베이스를 거친 데이터 생성 프로젝트 정의를 미확정 상태로 되돌려야 한다.
- **FR-020**: 시스템은 데이터 생성 프로젝트의 파생 계보를 조회할 수 있게 해야 한다 — 최초 기준선과 리베이스
  이력.

**수정과 확정**

- **FR-021**: 시스템은 데이터 생성 프로젝트 정의를 워크스페이스 기준선과 독립적으로 편집할 수 있게 해야
  한다.
- **FR-022**: 시스템은 데이터 생성 프로젝트 정의의 각 편집에 편집자, 편집 시각, 편집 전후 내용을 남겨야
  한다(기능 005의 편집 이력 규칙).
- **FR-023**: 시스템은 데이터 생성 프로젝트 정의가 확정되기 전에 그 데이터 생성 프로젝트의 실행 요청을 거부해야 한다.
- **FR-024**: 시스템은 데이터 생성 프로젝트 정의의 확정 전에 dry-run과 시뮬레이션을 모두 통과하도록 요구해야
  한다. dry-run 통과와 시뮬레이션 통과가 확정을 대신해서는 안 된다(기능 011 FR-035).
- **FR-025**: 시스템은 그 유형의 저작 대상 중 하나라도 없는 상태에서 데이터 생성 프로젝트 정의의 dry-run
  진입을 거부해야 한다(기능 011 FR-023).
- **FR-026**: 시스템은 확정된 데이터 생성 프로젝트 정의를 수정하면 dry-run 미통과 상태로 되돌리고, dry-run과
  시뮬레이션을 다시 통과해야 확정 가능하게 해야 한다(기능 011 FR-036).
- **FR-027**: 시스템은 데이터 생성 프로젝트 정의의 확정 권한을 그 워크스페이스 스코프의 `파이프라인 확정자`
  롤이 갖게 해야 한다. 전역 플랫폼 운영자 롤로 한정해서는 안 된다(기능 013 FR-018).
- **FR-028**: 시스템은 데이터 생성 프로젝트 정의를 저작한 사용자가 자신의 저작 결과를 확정할 수 없게 해야
  한다(기능 013의 저작·확정 분리).
- **FR-029**: 시스템은 데이터 생성 프로젝트 확정 기록에 확정자, 확정 시각, 확정된 정의 버전, AI가 생성한
  부분과 사람이 편집한 부분의 구분을 남겨야 한다(기능 011 FR-037).
- **FR-030**: 시스템은 확정된 데이터 생성 프로젝트 정의를 형상 관리 저장소의 커밋으로 보관해야 한다.
  화면에서 본 정의와 저장소의 정의가 다를 수 없어야 한다(기능 005).
- **FR-031**: 시스템은 데이터 생성 프로젝트마다 실행에 사용할 **고정 버전**을 두고, 새 버전 확정으로 자동
  변경되지 않게 해야 한다. 변경은 명시적 승격으로만 이루어지며 승격 이력을 남겨야 한다.
- **FR-032**: 시스템은 확정 반려 시 저작 단계로 되돌리고 반려 사유를 기록해야 한다(기능 011
  FR-039).
- **FR-033**: 시스템은 데이터 생성 프로젝트 시뮬레이션이 실데이터 표본을 쓰는 동안 그 임시 영역을 해당
  워크스페이스의 제한 계층과 동등한 접근 통제 대상으로 두고, 종료 시 파기해야 한다(기능 011).

**실행과 타깃**

- **FR-034**: 시스템은 데이터 생성 프로젝트와 타깃을 **1:1**로 대응시켜야 한다. 데이터 생성 프로젝트 하나가
  타깃을 둘 이상 갖게 해서는 안 되며, 이미 타깃을 가진 데이터 생성 프로젝트의 재실행은 그 타깃의 갱신으로만
  처리해야 한다. 연도별 동결 타깃(`cdm_2024`·`cdm_2025`)은 각각 별도 데이터 생성 프로젝트가 만든다.
- **FR-035**: 시스템은 데이터 생성 프로젝트 실행이 만든 물리 스키마를 기능 009의 타깃 레지스트리에 등록해야
  한다. 물리 스키마 이름을 앱 코드나 데이터 생성 프로젝트 정의에 하드코딩해서는 안 된다.
- **FR-036**: 시스템은 타깃에 그것을 만든 데이터 생성 프로젝트 식별자를 기록해야 한다.
- **FR-037**: 시스템은 잡의 필수 귀속을 대상 타깃으로 유지해야 한다(기능 009). 데이터 생성
  프로젝트 귀속을 새로운 필수 항목으로 추가해서는 안 된다.
- **FR-038**: 시스템은 모든 데이터 생성 프로젝트 실행에 `workspace_id` 태그를 붙여야 한다. 예외는 없다
  (헌법 원칙 V).
- **FR-039**: 시스템은 타깃의 생성 조건 기록(provenance)에 실행에 실제로 쓰인 **데이터 생성 프로젝트 고정
  버전**을 기록해야 한다. 워크스페이스 기준선 버전을 기록해서는 안 된다.
- **FR-040**: 시스템은 동결(frozen) 상태 타깃을 갱신 대상으로 하는 데이터 생성 프로젝트 실행을 접수해서는
  안 된다(기능 009).
- **FR-041**: 시스템은 데이터 생성 프로젝트 실행이 워크스페이스의 계층 구성(`{ws}_landing`, `{ws}_work`,
  `{ws}_mart`, `{ws}_pseudo`)을 그대로 쓰게 해야 한다. 데이터 생성 프로젝트마다 별도 계층을 만들어서는 안
  된다.
- **FR-042**: 시스템은 워크스페이스별 실행 대기열 하나(기능 002)를 유지해야 한다. 같은
  워크스페이스의 서로 다른 데이터 생성 프로젝트 실행도 이 대기열을 공유한다.
- **FR-043**: 시스템은 중단된 데이터 생성 프로젝트 실행의 적재분 정리를 기능 002의 규칙에 따라 처리해야
  한다.
- **FR-044**: 시스템은 데이터 생성 프로젝트 실행 로그의 화면 노출본에 마스킹·요약·분량 상한을 적용해야
  한다. 전체 로그는 운영자 롤만 접근할 수 있어야 한다(헌법 원칙 III).
- **FR-045**: 시스템은 SDM ETL 워크스페이스의 데이터 생성 프로젝트 산출물이 가명 계층에 놓이는 경우 기능
  012의 가명처리와 기능 008의 재식별 위험 점검 게이트를 우회하지 못하게 해야 한다.

**조회와 역추적**

- **FR-046**: 시스템은 워크스페이스의 데이터 생성 프로젝트 목록을 조회할 수 있게 해야 한다 —
  이름, 상태, 파생 기준선, 고정 버전, 산출 타깃.
- **FR-047**: 시스템은 데이터 생성 프로젝트 목록과 기능 009의 연구 프로젝트 목록을 섞어 표시해서는
  안 된다.
- **FR-048**: 시스템은 임의의 타깃에서 그것을 만든 데이터 생성 프로젝트로 역추적할 수 있게 해야
  한다.
- **FR-049**: 시스템은 조회자 롤(기능 013)이 데이터 생성 프로젝트의 구성 메타데이터를 볼 수 있게
  하고, 데이터 계층에는 접근할 수 없게 해야 한다.

**종료와 수명**

- **FR-050**: 시스템은 데이터 생성 프로젝트 상태를 저작중, 운영 가능, 종료, 폐기 중 하나로
  관리해야 한다.
- **FR-051**: 시스템은 종료된 데이터 생성 프로젝트의 실행 요청을 접수해서는 안 된다.
- **FR-052**: 시스템은 데이터 생성 프로젝트를 종료해도 그것이 만든 타깃을 자동으로 폐기해서는 안 된다.
  타깃의 수명은 기능 009의 보존 정책이 결정한다.
- **FR-053**: 시스템은 데이터 생성 프로젝트를 종료해도 확정된 정의와 확정·편집 이력을 보존해야 한다. 타깃의
  생성 조건 기록이 그 정의 버전을 가리키기 때문이다.
- **FR-054**: 시스템은 활성 타깃을 가진 데이터 생성 프로젝트의 폐기를 거부해야 한다.
- **FR-055**: 시스템은 데이터 생성 프로젝트 상태 전환 전부를 감사 이력에 남겨야 한다 — 전환 주체, 시각,
  이전 상태, 새 상태.

**롤과 경계**

- **FR-056**: 시스템은 데이터 생성 프로젝트의 어떤 권한도 워크스페이스 배정을 우회하는 경로가
  되지 않게 해야 한다. 워크스페이스에 배정되지 않은 사용자는 그 워크스페이스의 데이터 생성 프로젝트에 접근할
  수 없어야 한다.
- **FR-057**: 시스템은 데이터 생성 프로젝트에 연구자를 소비자로 하는 접근 경로, 화면, 산출물
  전달 기능을 두어서는 안 된다(헌법 범위 경계).
- **FR-058**: 시스템은 데이터 생성 프로젝트의 산출물을 병원 내부망 밖으로 내보내는 경로를 두어서는
  안 된다(헌법 원칙 II, 예외 없음).
- **FR-059**: 시스템은 데이터 생성 프로젝트 스코프 롤을 신설해서는 안 된다. 워크스페이스 스코프
  롤(기능 013)이 그 워크스페이스의 모든 데이터 생성 프로젝트에 동일하게 적용된다.
- **FR-064**: 시스템은 어느 데이터 생성 프로젝트의 정의를 누가 저작하고 누가 확정했는지가 확정
  기록으로 식별 가능하게 해야 한다. 워크스페이스 스코프 롤이 데이터 생성 프로젝트를 구분하지 않으므로 이
  기록이 사후 확인의 유일한 수단이다.
- **FR-060**: 시스템은 데이터 생성 프로젝트 관련 권한 의미를 기능 013의 롤 카탈로그에 기록하고,
  실제 권한 판정이 그 카탈로그와 일치하게 해야 한다.

### Key Entities *(include if feature involves data)*

- **데이터 생성 프로젝트**: SDM ETL 또는 OMOP CDM ETL 워크스페이스 안에서 물리 스키마를 만드는
  정의 단위. 고유 식별자, 소속 워크스페이스, 논리 이름, 목적 설명, 개설자, 개설 시각, 상태,
  파생 기준선, 고정 버전을 갖는다. 소속 워크스페이스는 생성 후 불변이다.
- **데이터 생성 프로젝트 상태**: 저작중, 운영 가능, 종료, 폐기 중 하나. 기능 011의 워크스페이스 상태(준비중·
  운영 가능)와 직교하며, 워크스페이스가 운영 가능해도 데이터 생성 프로젝트는 저작중일 수 있다.
- **파생 기준선**: 데이터 생성 프로젝트가 파생해 온 정의 집합. 출처는 그 워크스페이스의 공통
  스크립트 기준선이거나 같은 워크스페이스의 확정된 다른 데이터 생성 프로젝트 정의다. 형상 관리
  저장소의 커밋 식별자로 표현되며, 개설 시점에 지정되고 리베이스로만 바뀐다.
- **데이터 생성 프로젝트 정의**: 데이터 생성 프로젝트가 소유하는 적재·변환·워크플로 정의(SDM ETL은 자유서식 비식별화
  정의를 더해 네 종류). 각각 상태(초안, dry-run 통과, 시뮬레이션 통과, 확정, 반려)와 버전을
  갖는다. 저작·버전 관리 규칙은 기능 005가 소유한다.
- **리베이스 기록**: 데이터 생성 프로젝트를 새 기준선으로 옮긴 기록. 이전 기준선, 새 기준선, 실행자, 시각,
  충돌 해소 내역을 갖는다.
- **파생 계보**: 최초 기준선과 그 뒤의 리베이스 이력. 각 항목은 출처의 종류(워크스페이스 기준선
  또는 데이터 생성 프로젝트)와 식별자를 갖는다. 타깃의 생성 조건 기록이 가리키는 정의 버전이 어느
  기준선 계통에서 나왔는지 추적하는 근거다.
- **데이터 생성 프로젝트 고정 버전**: 데이터 생성 프로젝트가 실행에 사용하는 정의 버전. 새 버전 확정으로 자동 변경되지
  않고 명시적 승격으로만 바뀐다. 기능 005의 고정 버전 개념을 데이터 생성 프로젝트 단위로 적용한 것이다.
- **데이터 생성 프로젝트 확정 기록**: 데이터 생성 프로젝트 정의 확정 1회의 기록. 확정자, 확정 시각, 확정된 정의 버전,
  AI 생성 부분과 사람 편집 부분의 구분을 갖는다. 반려의 경우 반려 사유를 포함한다.
- **데이터 생성 프로젝트-타깃 연결**: 데이터 생성 프로젝트와 그것이 만든 타깃의 **1:1** 대응.
  타깃 쪽에 그것을 만든 데이터 생성 프로젝트 식별자가 기록되며, 타깃의 소유·보존·접근은 기능 009가
  계속 소유한다.
- **종료 기록**: 데이터 생성 프로젝트를 종료한 기록. 종료자, 종료 시각, 종료 시점의 산출 타깃을
  갖는다.
- **이행 기록**: 기존 ETL 워크스페이스를 데이터 생성 프로젝트 모델로 옮긴 기록. 대상 워크스페이스,
  만들어진 기본 데이터 생성 프로젝트, 연결된 타깃, 실행자, 시각을 갖는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영 측 인원이 운영 가능 워크스페이스에 데이터 생성 프로젝트를 개설하고 기준선
  파생을 마치는 데 10분 이내가 걸린다.
- **SC-002**: 개설된 데이터 생성 프로젝트 100%가 파생 기준선을 형상 관리 저장소의 커밋
  식별자로 기록한다.

- **SC-004**: 기준선이 새 버전으로 승격된 뒤에도 기존 데이터 생성 프로젝트 100%의 정의가 파생 시점 내용
  그대로 유지된다.
- **SC-005**: 리베이스 100%가 이전 기준선·새 기준선·실행자·시각을 남기고, 리베이스 후 데이터 생성 프로젝트
  100%가 미확정 상태로 돌아간다.
- **SC-006**: 확정되지 않은 데이터 생성 프로젝트의 실행 요청 100%가 거부된다.

- **SC-010**: 데이터 생성 프로젝트가 만든 타깃 100%의 생성 조건 기록이 실행에 실제로 쓰인 데이터 생성 프로젝트 고정
  버전을 가리킨다.
- **SC-011**: 데이터 생성 프로젝트 실행 100%에 `workspace_id` 태그가 붙는다.
- **SC-012**: 임의의 타깃에서 그것을 만든 데이터 생성 프로젝트를 1회 조회로 찾을 수 있다.
- **SC-013**: 데이터 생성 프로젝트 목록에 연구 프로젝트 항목이 0건 섞인다.
- **SC-014**: 종료된 데이터 생성 프로젝트 100%가 확정 정의와 확정·편집 이력을 보존하고, 그 정의를 가리키는
  타깃의 생성 조건 기록이 끊기지 않는다.
- **SC-015**: 활성 타깃을 가진 데이터 생성 프로젝트의 폐기 시도 100%가 거부된다.
- **SC-016**: 워크스페이스에 배정되지 않은 사용자의 데이터 생성 프로젝트 접근 시도 100%가 거부된다.
- **SC-017**: 데이터 생성 프로젝트 실행 로그의 화면 노출본에서 정형 식별자(주민등록번호, 환자번호,
  전화번호) 노출이 0건이다.
- **SC-018**: 데이터 생성 프로젝트 산출물을 병원 내부망 밖으로 보내는 경로가 0개다.
- **SC-019**: 데이터 생성 프로젝트 시뮬레이션 임시 영역 100%가 종료 시 파기되고, 존속 기간 접근 통제가
  해당 워크스페이스 제한 계층과 동등했음이 감사로 확인된다.
- **SC-020**: 데이터 생성 프로젝트를 경유하지 않는 실행 요청 경로가 0개다.
- **SC-021**: 데이터 생성 프로젝트 100%가 타깃을 1개 이하로 갖는다.
- **SC-022**: 이행 대상 기존 ETL 워크스페이스 100%가 기본 데이터 생성 프로젝트를 갖고, 기존 타깃
  100%가 데이터 생성 프로젝트에 연결된다.

## Assumptions

명세하지 않은 결정을 기본값으로 채운 곳과 그 근거를 남긴다.

- **리베이스는 명시적이다.** 기준선 승격이 데이터 생성 프로젝트 정의를 자동으로 바꾸지 않는다. 기능 005가
  "새 버전이 확정되어도 워크스페이스의 고정 버전은 자동으로 바뀌지 않고 승격으로만 바뀐다"로
  정한 선례를 그대로 따랐다. 정의가 발밑에서 바뀌면 산출물의 재현성이 깨진다.
- **잡의 필수 귀속은 타깃 그대로다.** 기능 009가 정한 "잡 → 타깃 필수"를 바꾸지 않고, 데이터 생성
  프로젝트 귀속을 새 필수 항목으로 추가하지 않았다. 데이터 생성 프로젝트와 타깃이 1:1이므로(FR-034)
  타깃에서 데이터 생성 프로젝트가 **유일하게** 유도되고, 필수 항목을 늘리면 기능 002의 실행 접수 계약이 바뀐다.
- **워크스페이스 실행 대기열은 하나로 유지한다.** 같은 워크스페이스의 데이터 생성 프로젝트들이
  `{ws}_landing`·`{ws}_work` 계층을 공유하므로 동시 실행은 적재분 충돌 위험을 만든다. 기능 002의
  워크스페이스별 단일 대기열을 그대로 쓰는 것이 가장 적은 변경이다.
- **데이터 생성 프로젝트는 워크스페이스의 계층 구성을 공유한다.** 데이터 생성 프로젝트마다 계층을 만들지 않는다. 헌법
  명명 규칙이 계층을 접근 통제의 단위로, 타깃 물리 스키마를 산출물 보존의 단위로 구분한 것과
  같은 층위 구분이다.
- **워크스페이스 "운영 가능"의 의미는 바뀌지 않는다.** 기능 011 FR-040의 기준은 기준선 확정
  그대로이고, 데이터 생성 프로젝트별 준비 상태는 데이터 생성 프로젝트 상태가 따로 갖는다. 게이트가 두 층이 되지만 각
  층의 의미는 하나씩이다.
- **확정 권한은 워크스페이스 스코프 `파이프라인 확정자`다.** 데이터 생성 프로젝트마다 새 확정자
  롤을 두지 않았다. 기능 013 FR-018이 확정 권한을 이 롤에 배정했고, 데이터 생성 프로젝트 단위로 쪼개도 통제가
  늘지 않는다. 데이터 생성 프로젝트 스코프 롤을 신설하지 않기로 FR-059에서 확정했으며, 그 대가인
  데이터 생성 프로젝트별 최소권한 분리 포기는 FR-064의 확정 기록으로 보완한다.
- **개설 자격은 워크스페이스 배정이다.** 별도 개설 롤을 두지 않았다. 기능 009가 연구 프로젝트
  개설을 워크스페이스 멤버로 한정한 것과 같은 형태이며, 데이터 생성 프로젝트가 워크스페이스 접근 통제의
  우회로가 되지 않게 한다.
- **화면·UI는 범위 밖이다.** 이 스펙은 개념과 규칙을 정하고 조작 화면 설계는 다루지 않는다.
  저장소의 다른 스펙과 같은 경계다.
- **데이터 생성 프로젝트는 헌법 범위 경계의 배제 대상이 아니다.** 헌법 v4.2.2가 명시했다 —
  산출물이 물리 스키마이고 소비자가 운영 측이다. 이 가정이 무효가 되면 스펙 전체가 무효다.
- **성능 목표는 사람 조작 시간으로만 규정했다.** 명세에 실행 처리량·지연 기준이 없다. 기술
  목표는 plan 단계의 잠정 가정으로 두고 성공 기준으로 승격하지 않았다.

## Out of Scope

- **연구 프로젝트, 추출물, 연구 프로젝트 스코프 롤** — 헌법 범위 경계의 배제 대상이다(기능 009,
  013). 이 기능은 그 개념을 되살리지 않으며, 데이터 생성 프로젝트를 그 대체물로 쓰지도 않는다.
- **연구자용 분석 워크스페이스와 연구자 접근 경로** — 헌법 범위 경계. 데이터 생성 프로젝트가
  연구자에게 산출물을 전달하는 경로를 만들지 않는다.
- **관리 유형 워크스페이스의 데이터 생성 프로젝트** — SDM/OMOP CDM Vocabulary/Mapping 관리 워크스페이스는
  ETL 파이프라인 기준선을 갖지 않으므로 파생 대상이 없다.
- **원외 반출 경로** — 헌법 원칙 II. 예외 없이 범위 밖이다.
- **워크스페이스를 넘는 파생과 공통 조각 라이브러리** — 같은 워크스페이스 안의 데이터 생성 프로젝트 간 파생은
  FR-062로 범위 안이지만, 다른 워크스페이스의 데이터 생성 프로젝트에서 파생하는 것과 여러 데이터 생성 프로젝트가 참조하는
  공통 조각 라이브러리는 이 버전에서 만들지 않는다. 필요해지면 별도 기능으로 다룬다.
- **화면·UI 설계** — 개념과 규칙만 정한다.
- **데이터 생성 프로젝트 단위 비용 산정·쿼터** — 실행 비용을 데이터 생성 프로젝트별로 배분하는 모델은 다루지 않는다.
